# 重美术游戏 UI 动效：行业参考与 Web 落地草案

调研日期：2026-09-15。状态：公开资料调查与项目建议，**不是已批准的美术规范，也不代表产品已实现**。

用户已将方向收敛为复用基础库、清理杂乱UI与顺滑交接。Motion for React及共享CSS已有实际消费者，当前实现见[动效调用与边界](../../src/shared/ui/motion/README.md)。本文保留行业参考，高级效果不是当前施工清单，已回退的U3方案不恢复。

配套：[UI Motion：共享动作与参数](../../src/shared/ui/motion/README.md)。该审计记录项目已有能力与源码断点；本文回答参考什么、如何形成规范、是否需要引入库。本轮只修改文档，未安装依赖、导入第三方美术或修改产品代码。

## 1. 调研结论

本轮没有找到一份可以直接照搬、同时覆盖二次元美术、所有交互、全部时序及 Web 源码的通用行业标准，也未取得《绝区零》《Persona 5》的完整内部动效规范。公开资料可以组成一套可靠的参考链：

1. **用游戏开发者资料确定表现方法**：动效是角色、美术、镜头、信息层级的一部分，不是完成静态 UI 后统一加上淡入、弹簧和粒子。
2. **用设计系统确定规范结构**：同义操作一致、空间关系可理解、主要信息有落点；操作效率与表现力可以共存。
3. **用 Web 游戏工作流与 API 文档确定实现方法**：状态样式、进退场生命周期、局部时间线、资源就绪、输入与数据分别处理。

对 Abyssa 的建议是建立“统一动效设计规范 + 轻量实现层 + 真实流程样本”，而不是先选一个库再让所有东西使用相同动画。指针、点击装饰和音效可以增强识别度，但不能替代窗口、选择、结果和场景之间的联动。

## 3. 两个贴近本项目的游戏案例

### 3.1 《绝区零》：角色展示与信息布局是同一个设计问题

官方访谈 [S01] 中，制作人李振宇说明：团队早期约十人，需要谨慎分配动画和美术资源，于是在高频使用的角色养成界面尝试以高质量视觉包装配合少量动画转场，突出不同角色的特点。

关于构图，访谈明确提到：不仅考虑完整角色动作，还要用适合的镜头角度定义角色；右侧信息密集，左侧角色展示就需要相对舒展，让整体平衡。

这对 Abyssa 的启发是：

- 人物页、主菜单可以有鲜明表演，但文字区和操作区应有稳定的阅读位置。
- 切换角色时，可以共同设计人物姿态、构图、名字与属性区的显隐关系；不能只给整页统一套缩放。
- “统一”不等于角色表演相同。相同的是选择反馈、信息落位与可操作规则，不同的是角色姿态和情绪。
- 不能从该访谈推导出“所有菜单都应强弹性、加故障闪烁、相同毫秒数”。本轮没有测量游戏实机曲线或输入锁定时间。

### 3.2 《Persona 5》：动效主动引导视线，并服务于作品识别

会议报道 [S02] 介绍了以下具体做法：

- 主色、标题标识和关键字体共同建立作品识别；UI 同时承担图形表现与信息传递。
- 打开菜单时，用中央白色线条引导视线；进入下一层时调整布局与角度，帮助理解层级。
- 动态改变不同区域的明度，让高优先级信息更亮、次要信息退后。
- 先做布局，再由动作设计师制作姿态并在专用工具中配置；3D 动作确定后，使 2D 定格插画尽可能接上最后姿态。
- 设计师交付坐标指定资料，并与各模块 UI 程序员现场进行像素与帧级调整。报道提及上千页纸面规格，但这不是要求我们也采用纸面流程。

对 Abyssa 最有价值的不是复制红黑配色和斜切，而是复制其工作方法：**先确定观众该看哪里，再安排框架、人物、装饰和文字的到达顺序，并共同校准终态**。

例如标题已有的双菱形内收、按钮受压、文字阴影变化，就是可扩展的“同一个对象受力，各层随之响应”。洋馆窗口打开后，背景让位与信息落位也应按一段完整演出来定义。

### 版本与适配陷阱

- 旧的 [GameUIComponents][S19] README 已声明弃用，指向新版 Gameface UI。不要再把旧包当作默认新项目选型。
- 新版 Gameface UI 的 [MIT 许可][S20] 适用于该仓库软件；不等于 Gameface 商业运行时或其他游戏美术也可任意使用。使用代码仍须保留相应版权与许可声明。
- Gameface 运行时能承载 React，不代表其新版 SolidJS UI 套件可以直接作为 React 组件使用。
- Gameface 文档中的 `playFromTo()` 是其扩展，不是普通浏览器 WAAPI 的通用方法；其 Lottie Light、SVG、CSS 支持限制也属于该引擎。
- 本项目是浏览器 React/Vite，应使用浏览器实际支持的 API 与渲染测量。不能把“Gameface 原生 CSS 管线”的性能叙述直接变成“浏览器中 CSS 一定快于所有 JS／WAAPI”。

## 5. 应形成怎样的规范

以下是结合资料与项目审计提出的规范结构，不是从某个游戏泄露或复刻的内部文档。

### 5.1 先定义两种使用节奏，再定义对象材质

借鉴 Carbon 的功能型／表现型区分 [S06]，但保留游戏表现力：

- **操作型**：按钮、焦点、选择、页签、工具提示、重复开关窗口。即时反馈、短路径、可中断；不因装饰尚未结束而阻塞下一次有效操作。
- **表现型**：首次场景呈现、角色展示、关键奖励、剧情与战斗演出。可以有更大幅度、错拍、镜头和定格；明确观看目的、可跳过边界及重复访问策略。

在这两种节奏内，再定义金属控件、纸页／面板、菱形标记、人物、环境各自的受力方式。可以共享阶段和参数命名，不必共享同一条曲线。

“所有动效都安静克制”不是二次元游戏通则；“所有东西都弹起来”也不是。Abyssa 可以让操作层精确、环境层安静、关键人物与事件更鲜明。

### 5.2 统一的是状态语法，不只是外观

| 状态／动作 | 必须表达什么 | 不能混淆什么 |
| --- | --- | --- |
| hover／focus | 当前可操作对象；键盘也有等价反馈 | 悬停不是已选择，焦点不是成功 |
| press／release | 输入被目标接收、控件有触感 | 按下不是购买成功或奖励已到账 |
| selected | 选择持续存在，关联详情与操作对象一致 | 不依赖一次播放完就消失的光效 |
| busy | 正在等待，哪些操作仍可用 | 不用装饰动画的结束伪造业务完成 |
| confirmed／failed | 已提交结果及其具体影响，或明确失败 | 回执恢复、读档不能重复演出奖励 |
| entering／exiting | 对象从何处出现／回到何处；输入和焦点如何交接 | CSS 有退出样式不等于 DOM 实际保留到了退出结束 |

### 5.3 联动以一个意图或已提交事件为起点

联动不是让所有组件同时播放，而是由同一个操作或结果驱动有主次的响应：

1. 输入对象先给即时反馈。
2. 选择标记、面板或角色明确承接该操作。
3. 关联内容变化，保留稳定的空间锚点。
4. 业务结果在真实接纳后表达；金额、物品或生命值等相关对象响应。
5. 装饰与环境恢复，不残留忙碌、光效或输入锁。

背景压低、装饰错拍、音效触发都应订阅同一段语义阶段。不同层不应各自用延迟猜测“主动画应该播到哪里了”。音效若后续加入，需分别定义焦点移动、输入接纳、成功、失败的声音；静音不应损失状态信息。

局部页面／场景拥有自己的编排。全局层只协调路由、模态、教程和可见性等共享资源，不把所有 hover 与人物动作送入一个串行大队列。

### 5.4 空间、连续性与注意力

Carbon 明确区分语义一致性与空间一致性，也允许有意的不一致表达不同含义 [S07]。对本项目建议：

- 抽屉遵循所属边缘；窗口保留来源入口；返回时恢复来源焦点和选择。
- 列表切换可以移动同一个选择标记；无关区域不因选中一项而重新入场。
- 角色切换维持名字、主要操作等稳定锚点，表演区允许差异化。
- 关键动作占据注意力中心时，降低环境、循环发光和次要提示的强度。
- 错拍必须有总时长上限，不能因为列表有几十项就等待数秒才可用；长列表优先分组或只处理可见项。

不要照搬 Carbon 的“永不斜向运动”或“禁止弹跳”：那是 IBM 的网格与品牌要求。Abyssa 的菱形、地图纸片、人物表演可以采用其他路径，前提是其用途和力度明确。

### 5.5 时长与缓动的来源必须可追溯

Carbon 的公开 token 示例是 70／110／150／240／400／700ms [S06]，用于从微交互到大变化的不同场合；它同时要求按运动距离、尺寸和风格调整。这证明“按语义分档”有成熟参考，**不证明这些数值适合直接作为二次元游戏标准**。

Abyssa 原审计的按下 70–100ms、悬停／焦点 120–180ms、面板进入 220–320ms、退出 140–220ms、错拍 30–50ms，仅保留为原型候选。统一规范应记录：

- 名称、用途、适用对象、时长、距离／幅度、缓动、允许例外。
- 位移属于 Stage 设计坐标、元素局部坐标还是屏幕坐标。
- “立即反馈”指没有人为起播等待，不是把完整动画时长设为零。
- 同一语义可以因距离而调整时长；首次展示、重复进入、减弱模式分别配置。
- 参数由同一来源供 CSS、WAAPI 与 GSAP 消费，避免修改视觉时长却忘记输入解锁计时。

## 6. 可交付的动效规格单

借鉴 Persona 的设计／程序协作方法 [S02]，建议每个共享配方和关键流程都有以下字段。目标不是堆很多文档，而是让设计与实现能对同一个状态和同一个终态验收。

| 字段 | 应写清的内容 |
| --- | --- |
| ID、场景与所有者 | 例如 `inventory.open`；由谁编排、谁释放输入锁 |
| 目的与触发 | 输入意图还是已提交事件；用户当前应看哪里 |
| 前置／终止条件 | 数据与素材就绪、禁用态、关闭、路由离开、重复请求 |
| 分层对象与关键姿态 | 背景、遮罩、框架、人物、标记、文字、特效；最终构图 |
| 时间线 | 每轨起止、相对标签、缓动、错拍总上限；声音与视觉的接触点 |
| 属性所有权 | 谁写 transform／opacity；多个效果是否使用独立包装层 |
| 输入与焦点 | 可开始操作的时点、取消规则、键盘／手柄／触屏差异、返回焦点 |
| 打断与恢复 | 反向、接续当前值、直接到终态或丢弃；旧任务不得覆盖新任务 |
| 减弱模式 | 移除哪些空间运动，保留哪些信息；完成事件如何结算 |
| 资源与性能 | SVG／纹理／序列帧等格式、尺寸／缩放、透明区、循环条件与测量场景 |
| 验收证据 | 可运行样本、正常与快速操作录屏、性能记录、失败／取消用例 |

### 一个可以进入原型的样例：打开仓库

下表是 **Abyssa 的试验时间线**，不是行业数据或最终参数。可用现有控件与资产实现后对比；不需要为试验先加全局鼠标特效。

| 轨道 | 试验起止（相对有效打开指令） | 目的 |
| --- | --- | --- |
| 来源控件 | 0–90ms | 表面受压／复位，立即确认输入 |
| 环境与遮罩 | 0–180ms | 降低次要运动与背景对比度 |
| 窗口框架 | 0–260ms | 从所属方向小幅位移并稳定，不缩放整块正文 |
| 标题／栏目 | 80–220ms | 在主体进入过程中接入，强调信息层级 |
| 当前内容 | 100–260ms | 整组接入；不逐个延迟数十个物品格 |

实施约束：有效打开时立即启用模态输入隔离；在焦点目标已可见且可操作时交接焦点，不等待最后一颗装饰粒子。数据未就绪时显示真实加载态，不为等待动画伪造内容。关闭试验可用 160ms，但关闭中重开必须使旧退出任务失效，并从当前表现接续或进入明确稳定态。

减弱模式取消窗口位移和分批飞入，保留清晰的遮罩、标题、选中态；根据批准策略直接切换或短淡入，并同步缩短完成等待。它不是把每轨都变成 0.01ms 却保留 260ms 的逻辑锁。

另一个独立配方 `inventory.equip.confirmed` 应由装备结果回执驱动，再更新装备格、详情和相关属性提示。它不能绑定在 `pointerdown` 或 `inventory.open` 上。

## 7. 是否需要统一动效库

需要统一能力，但“设计系统”“项目封装”和“第三方动画引擎”是三件事。

| 工作 | 对 Abyssa 的建议 | 参考依据 |
| --- | --- | --- |
| 语义参数、强度、减弱与暂停政策 | 建立项目级共享层 | [S06] [S07] [S10]；审计已发现跨模块差异 |
| hover／focus／press／selected | 继续用共享 CSS 状态配方 | [S17]；简单状态不必每帧通过 React 更新 |
| 通用弹窗退出、可取消元素动画 | 先明确 presence／完成／取消契约，现有 CSS／WAAPI 可以起步 | [S09] [S12]；不因保留 CSS 就忽略生命周期 |
| 多对象错拍、角色／框架／镜头编排 | 优先评估现有 GSAP 的局部 timeline；保持属性所有权独立 | [S08]；不强行把所有 CSS 迁为 JS |
| 大量动态列表布局、共享元素与 React presence | 当重复实现成本明确时再评估 Motion for React | [S09]；比较接入体积、维护成本、快速重开与降级行为 |
| 美术直接制作的奖励／标志演出 | 确有资产生产需求时评估 Lottie 或序列帧 | [S18]；先测试导出特性与运行成本，不把普通按钮转成动画资产 |
| 地图、战斗、AVG 的业务演出顺序 | 保留各自状态机，共用政策与完成协议 | 项目审计；动画库不拥有 gameplay 或存档事实 |

现有栈已能覆盖第一批问题。本轮没有证据支持“一次性换库就能统一质感”，也不把“不增加依赖”定成永远不能改变的原则。先用共享窗口与一条关联流程验证，再基于实际维护缺口决定是否加入 Motion。

## 8. 鼠标、点击与输入联动

本轮公开来源没有证明“自定义鼠标 + 全局点击光效”是这类游戏的必备标准。建议把它们作为共享状态和窗口联动稳定后的可选品牌增强。

- **指针是操作语义的一部分**：默认、可点击、文本、拖动、禁止、忙碌必须可分辨。MDN 明确区分仍可操作的 `progress` 与阻塞操作的 `wait` [S11]。
- **优先系统级 CSS 光标**：显式热点与必要的系统关键词回退；MDN 建议控制在 32×32 像素左右，浏览器上限与平台行为另行验证。不要用迟滞跟随的装饰点替代精确热点。
- **点击反馈归属于目标**：控件受压为主，菱形角线或细光为辅；空白点击、禁用、拖拽结束不能播成成功。
- **跨输入设备等价而非相同**：键盘／手柄采用同一焦点和选择配方；触屏用目标反馈，不制造悬停鼠标。光标只作用于游戏区，不覆盖制作工具中的文本和精确操作语义。
- **若增加效果宿主**：不接收指针事件，规定叠层与并发上限；Stage 坐标和 client 坐标显式转换；遵守减弱动效、后台和前景演出政策。

原生光标本身不承担所有演出。点击光效、控件反馈、选择标记、业务成功可以共享形状与色彩，但仍要保持不同含义。

## 9. 实施顺序与验收

建议顺序：

1. 先定状态语法、操作型／表现型节奏、规格单和少量材质配方；不先扫全仓修改毫秒数。
2. 优先解决共享模态退出、全局减弱动效、完成／取消与输入解锁时钟。这些是审计中的真实缺口。
3. 在现有组件目录／Storybook 中完成“入口—仓库或日志—内容选择—关闭返回”垂直样本，比较正常、重复和快速操作。
4. 样本通过后推广到高频窗口、页签和选择；再安排人物／战斗／场景的表现型配方。指针和点击装饰与样本对照，不作为前三步的前置依赖。

验收至少覆盖：

- 快速连点、连续切换目标、退出中重开、路由离开、组件卸载；旧回调不误删新窗口。
- 键盘／手柄焦点和鼠标选中一致，触屏无悬停依赖，Stage 缩放后热点准确。
- 失败、加载较慢、素材未就绪、读档、回执重放；视觉完成不等于业务提交。
- 系统与玩家减弱偏好、前后台切换、主演出占用注意力；降级后不丢状态或留下等待。
- 在约定参考设备、分辨率和典型复杂场景录制性能轨迹，查看长任务、布局／绘制、丢帧与内存趋势 [S13]。若以 60fps 为目标，约 16.7ms 是整帧预算，不是 UI 可独占的预算；本轮没有完成该测量。

动态验收必须包含真实输入与完成／中断过程，不能只凭静态截图判断“联动已统一”。

## 10. 本轮修订对原审计的影响

- 保留“已有局部语言，但缺少跨模块系统”的判断及已记录的源码证据。
- 将“整体安静克制”修正为分层分场合：操作精确，环境安静，关键展示允许更鲜明。
- 将“指针和点击值得加入”改为可选增强；先解决交互语法、真实联动和生命周期。
- 原毫秒数明确标为项目试验值，不包装成行业标准；不将 Carbon 的品牌禁令迁入游戏。
- 统一库改为能力选型：沿用现有栈起步，满足明确条件后再评估 Motion 或美术资产运行时。
- 补充设计交付规格单、具体流程时间线、来源等级、平台／版本／许可边界。
