日期：2026-09-15。性质：现状审计与设计建议；同日补充公开行业资料调查后修订。仅修改文档，未实施产品动效修改。

## 结论

项目已经具有清楚的局部动效语言：标题的金属缎带与菱形、菜单的分层装配、AVG 的人物动作、战斗的蓄力／命中／恢复，以及洋馆的安静景致。但通用交互、动效生命周期、减弱动效与跨模块协调尚未形成全项目共用的设计系统。

依据最新范围，先移除重复、装饰性与过强的普通 UI 动效，再收为少量基础预设。当前规划推荐 Motion for React 处理共享进退场与状态切换，统一 CSS 控件配方承担简单反馈；GSAP／Three.js 保留于地图等专用场景。无需手写新的通用动画引擎，也不通过全部换库重做剧情和战斗演出。

定制鼠标指针和装饰性点击效果属于可选增强，不是本轮调查确认的行业必备标准。基础控件反馈与完整联动应优先：输入响应、对象响应、内容变化、结果确认。规范需要同时容纳高频操作的效率与关键展示的表现力，不把所有场景统一成安静淡入或同一种弹簧。

## 行业参考带来的校准

- [《绝区零》官方访谈](https://zenless.hoyoverse.com/en-us/news/123577)强调以高质量视觉包装与少量转场突出角色，并让角色动作、镜头、右侧密集信息与左侧构图共同平衡。它没有公布可直接套用的 UI 时长和曲线。
- [《Persona 5》开发者会议报道](https://www.famitsu.com/news/201711/13145540.html)记录了线条引导视线、明暗区分主次、布局／角度说明层级、3D 动作接 2D 定格，以及设计与程序逐帧协作。应借鉴这些方法，而非复制配色或加动效数量。
- [Carbon 动效编排](https://carbondesignsystem.com/elements/motion/choreography/)支持按语义与空间关系统一、通过连续对象和错拍引导；其品牌特有的网格路径和禁弹跳规则不移植为本项目禁令。
- [Coherent Web 游戏 UI 工作流](https://guide.coherent-labs.com/getting-started/introduction/)提供较完整的工程参考；新版组件采用 SolidJS，旧库已弃用。借鉴流程和能力分工，不替换本项目 React/Vite，也不把 Gameface 的专用 API 当成浏览器标准。

详细来源、可复用范围及试验规格见配套调研。以下材质与参数仍是 Abyssa 设计建议，不是行业定稿。

## 主要断点

### 1. 通用参数只有缓动基底，缺少操作语义

`shared/ui/styles/tokens.css:24` 提供一个共用缓动，但没有按“按下、悬停、选择、面板进入、面板退出、内容切换”建立共用时长与幅度。

例如 `components-controls.css:22` 的缎带用 120ms 提亮／100ms 变换，六边形按钮在 127 行用 120ms／90ms；`components-dialogue.css:167` 另一组为 100ms／80ms；洋馆工具入口在 `mansion-chrome.css:338` 用 160ms；标题则单独管理表面、文字、阴影和菱形。

这些数值并非各自错误。问题在于它们没有共同命名、适用条件和例外说明，调整一类控件的手感需要逐处定位。不同形状可以保留不同受力方式，但同一操作应共享响应逻辑。

### 2. 共享弹窗的设计注释与生命周期不符

`shared/ui/primitives/RpgModal.tsx:165` 在 `open === false` 时直接返回 `null`。因此 `data-open="false"` 从不出现在这棵已挂载的 DOM 中。

`shared/ui/styles/items.css:295` 为遮罩定义 200ms 过渡，面板在 315 行定义 180ms 淡入和 220ms 位移；注释宣称关闭也有过渡，但节点已经被移除，退出无法执行。首次挂载直接是打开态，也缺少保证 transition 起始样式先被绘制的机制。

此外，`game-client/campaign-journal.css:108` 又给日志面板添加 220ms 的挂载入场，而其他共享模态没有这条补充规则。这会使使用相同外框的窗口出现不同的进场表现。

这项应优先修复：共享层需要真正的 entering／open／exiting／closed 生命周期，并协调关闭中输入、焦点归还、快速重开和动画取消。

### 3. 减弱动效没有统一含义，也没有全局设置入口

- 全局 UI CSS 在 `tokens.css:40` 将多数运动压缩到 0.01ms。
- 正式战斗在 `useManorBattlePresentation.ts:40` 将阶段等待压到最多 60ms，并对部分教程事件直接跳过旋转。
- RP 席位在 `SeatActor.tsx:54` 保留 300ms／240ms 淡入淡出，移除大位移。
- 独立骰局在 `dice-accessibility.css:21` 特意恢复完整掷骰、定相发光与金币飞入。
- 地图 `createMapScene.ts:320` 的 GSAP 弹性入场、398 行的镜头移动、435 行的点按回弹没有减弱动效分支；CSS 媒体查询不能关闭这些 Three.js 对象上的运动。
- `apps/settings/SettingsPage.tsx:62` 使用页面局部 reducer，86 行只给本页挂减弱动效属性；这不是所有游戏页面共用的偏好。

应定义“保留结果与状态，减小或移除空间位移、抖动和持续装饰运动”的共同政策，再为不同媒介提供明确表现。保留信息不要求保留完整旋转。

### 4. 动画结束与输入解锁存在分散的时钟

`game-shell/GameShell.tsx:77` 等待 560ms 合幕，112 行固定等待 620ms 或 1850ms 揭幕。相近常量又存在于 `shared/transition/TransitionProvider.tsx`，而 CSS 分别定义可见过渡。

`transition.css:469` 在减弱动效下将黑幕过渡缩到 100ms，并取消面板下落，但游戏壳的等待保持原时长。因此“画面已稳定”和“允许下一次输入”可能相隔一段时间。

战斗支持特效也在控制器与 CSS 中分别写入 90／120／240／300ms；`SceneSequence` 的时长同样由 TS 和 CSS 分别维护。洋馆将同一 TS 参数投影给 CSS 的做法可以复用。优先统一来源和完成／取消协议，具体场景状态机继续各自拥有业务顺序。

### 5. 同一作品的物理感尚未被明确分配

标题偏金属、漆面与细小错拍；主菜单偏组装到位；地图使用 1.25–1.35 秒弹性回弹，点击地标还有 0.85 秒 elastic；洋馆偏缓慢淡入和低强度景致；战斗是短促冲击；AVG 有人物化的摇摆和跳跃。

战斗与 AVG 的差别有明确叙事理由。早期曾考虑为地图保留纸片弹性；最新精简计划先移除地标入场和点击过冲，保留纸片的静态美术、位置与选择反馈。普通 UI 先采用无过冲基础配方，人物和战斗动作不在这轮一并压平。

### 6. 联动已有局部成果，尚未成为共用交互能力

标题、菜单、战斗和 AVG 都已有明确联动。通用窗口、列表、库存详情则更多依赖各自的挂载、状态 class 或局部 keyframe，没有统一的反馈阶段与并发优先级。

`EnemyMist` 已实现前景优先，`TutorialProvider` 已处理场景／弹窗遮挡与暂停；但地图运行时 `map-scene-runtime.ts:22` 只在销毁时停止自己的 RAF，没有同类显式可见性／活动状态政策。浏览器会自行节流隐藏标签页，这不等于项目已统一处理暂停、恢复和计时。

### 7. 鼠标指针与点击特效尚未形成系统

本轮未发现 `cursor: url(...)`、隐藏原指针的替代绘制或全局点击特效实现。当前主要使用 `pointer`、`default`、`grab`、`grabbing` 等系统指针；标题两侧的菱形是菜单选择指示器，并非鼠标指针。

首晨已有 `game-client/morning-sound.ts` 的少量离线拟音占位，并按剧情 beat 触发。它不是全局交互音效系统，不能把旧设置文件“没有任何音频代码”的注释当作当前事实。

## 建议的动效语言

建议以当前资产已经呈现的“暗色底材、金属边缘、菱形定位、有限回弹、缓慢环境”作为材质基础，但分别定义操作型与表现型节奏：前者用于高频控件与窗口，后者用于人物、首次展示和关键事件。环境的安静不能成为限制角色与重要演出的通用强度上限。

| 对象 | 推荐表现 | 强度和用途 |
| --- | --- | --- |
| 金属／浮雕控件 | 边缘提亮、1–2 个设计像素的下压、短促复位 | 高频交互，立即响应 |
| 面板／抽屉 | 从入口或所属边缘进入，小位移、充分减速；退出更短 | 说明空间关系，避免文字大幅缩放 |
| 选择指示 | 菱形／角线沿真实选项移动或收拢 | 兼容键盘焦点，持续选择态清楚 |
| 信息变化 | 关联内容轻淡入，结果对象短暂强调 | 不让所有行与文字逐字跳出 |
| 场景进入 | 前景收束、遮挡、场景就位、主体出现、文字接入 | 首次可完整，重复访问更简洁 |
| 战斗／事件 | 预备、接触、结果反馈、恢复 | 主要动作可更强，其他运动降低存在感 |
| 人物表演 | 沿用情绪映射和独立动作层 | 保留角色差异，不套按钮的机械节拍 |
| 环境 | 云雨、光源、呼吸缓慢且低强度 | 模态、关键演出或后台状态下让位／暂停 |

以下只保留为 Abyssa 原型候选，未经实测批准，也不是二次元行业标准：按下 70–100ms；悬停／焦点 120–180ms；普通面板进入 220–320ms、退出 140–220ms；相邻元素错拍 30–50ms。来源调查支持按语义、距离、对象大小及使用场合分档，不支持把所有组件设成相同毫秒数。错拍要限制总时长；场景、人物、掷骰和战斗阶段按其语义单独校准。

## 共享层的合理范围

最新计划建议在 `src/shared/ui/motion/` 中集中普通 UI 的基础能力，尚未创建。下面是能力边界，不要求额外建设通用编排框架：

1. **语义参数**：控件响应、面板、内容切换、环境各自的时长、幅度与缓动；TS 与 CSS 同源。重要演出仍允许显式局部配置。
2. **统一政策**：系统偏好与玩家设置、页面可见性、前景繁忙、装饰动效暂停；同时提供 CSS 和 JS 消费方式。
3. **进退场生命周期**：保留退出节点、允许取消／重开、卸载清理、完成回调与焦点交接；优先用于共享弹窗和抽屉。
4. **交互反馈配方**：hover／focus、press／release、selected、busy、confirmed／failed，使用现有组件的材质与主题色。
5. **局部编排工具**：阶段、完成与取消协议；各场景调用共享能力，页面业务顺序继续由原场景控制。无需让所有页面动作排入一个全局大队列。

最新普通 UI 路线为 Motion for React 的项目封装与统一 CSS 控件配方；页面只消费预设，不分别选择动画引擎。现有专用 WAAPI 演出与 GSAP／Three.js 地图不在第一批强迁，共用政策和生命周期边界即可。

本阶段不增加多对象复杂时间线。不同执行方式不应同时写同一元素的同一属性；需要并行动作时沿用独立层所有权。采用 Motion 仍必须满足退出保留、完成／取消结算和焦点交接，动画库不自动解决这些产品语义。

共享层保持与 gameplay／存档无关。正式游戏继续使用已提交事件驱动结果演出；旧组件示例的 `BattleScreen` 播放器与正式战斗控制器用途不同，不在这轮设计统一中盲目合并。

## 鼠标指针与点击反馈

共享状态与窗口联动稳定后，可试验清晰、紧凑的箭头／菱形指针，使用现有冷银、象牙与少量旧金。优先原生 CSS 光标、明确热点与系统回退，避免跟随延迟影响点选；是否保留以可读性和操作验证决定。

- 初期处理默认、可交互、忙碌三类；文本编辑、拖拽、精确点选继续保留明确的光标语义。
- 样式仅作用于游戏区域；制作工具与编辑字段以精确操作为优先。
- 点击反馈以目标控件受压为主，可配一次短暂的菱形角线／细光脉冲；强度低于选中态与结果反馈。
- 空白、禁用控件、拖拽结束不播放“成功”效果；接受点击与业务成功必须区分。键盘触发获得等价的控件反馈，触屏不出现悬空鼠标光标。
- 首版不需要拖尾或高频粒子。若后续确需独立效果层，应使其不接收输入、由单一宿主管理并发数量、遵守黑幕与教程层级。
- 按 [MDN 光标语义](https://developer.mozilla.org/en-US/docs/Web/CSS/cursor)区分仍可交互的 progress 与阻塞操作的 wait；不能为了统一样式覆盖文本、拖动、禁止等含义。
- 项目使用 1600×900 Stage 与嵌套世界缩放。控件位移按设计像素定义；鼠标热点按屏幕坐标定位。局部效果必须经过 Stage 坐标换算，不能直接混用 clientX／clientY。

## 联动应如何落地

三个适合最先验证的真实流程：

1. **打开日志／仓库**：入口受压并确认选中；场景背景安静下来；窗口主体进入；标题与当前内容接入；关闭后窗口退出，来源入口重新可操作并恢复焦点。
2. **选择人物／骰子／目标**：当前控件立即反馈；选择标记移动；相关操作与目标同步突出；无关信息保持稳定；选择变化本身不冒充行动完成。
3. **领取／购买／战斗结果**：按钮收到输入后显示忙碌；收到已提交结果时，相关金额／物品／生命对象同步反馈；请求失败显示对应状态；回执重放、读档和恢复不再次播放获得奖励的演出。

以上是建议流程，不表示所有步骤当前均已实现。其视觉主次为：当前操作和结果最清楚，关联对象辅助响应，环境只作陪衬。

每条流程需补充同一份规格单：触发与前置条件、分层对象、关键姿态、相对时序、缓动与坐标、属性所有权、输入／焦点、完成／取消、减弱模式、资源与验收。配套调研提供“打开仓库”的试验时间线；该示例不是已经批准或实现的流程。

## 实施优先级与验收

以下为调查阶段提出的较宽顺序；实际执行已收敛为配套计划 U1 清理、U2 基础库、U3 普通 UI 迁移、U4 残留清理与验收，不将下面的表现型扩展作为本阶段完成条件。

1. **先收口共同规则与真实缺口**：确定操作型／表现型节奏、状态语义与规格单，再校准参数；修复模态生命周期；接通全局减弱动效；让地图与场景输入解锁遵守同一政策。
2. **做一条可比较的垂直样本**：复用标题现有材质、共享按钮和洋馆的一组入口—窗口—内容选择—关闭返回，在现有组件目录／Storybook／Loading 实验中对照。指针与轻点击装饰可作附加对照，不作为样本前置。
3. **扩展到高频 UI**：仓库、日志、整备、页签、列表、工具提示、人物／目标选择。先统一操作手感，再调整大场景的首访／返回节奏。
4. **整理场景专用动效**：逐步将重复时长、取消逻辑与暂停政策提取；保留人物、战斗、地图纸片和序幕镜头各自的表现。

验收应关注快速连点、关闭中重开、键盘触发、拖拽、缩放、减弱动效、切入后台与返回、路由离开、请求失败和回执重放。核对同类操作是否一致、焦点和输入是否正确、视觉是否重复、目标是否被特效遮挡。对实际发生的位移和资源开销做浏览器验证，静态截图与规则测试不能替代动态观察。

本次产物是勘探与建议。上述优先级、参数和指针样式尚未实施，也未被视为用户已经确定的美术定稿。
