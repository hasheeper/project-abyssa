# 委托实物奖励与交付修复

本次补的是既有巡守委托的实物链：接单 → GM 冻结物品与领取条件 → 实际战斗奖励 → 携带 → 返程持有 → 明确交付。

## 实现范围

- 新出征计划显式启用 `commissionRewardVersion: 1`。每项已接巡守必须安排恰好一件对应模板的物品，唯一挂到原委托目标节点。漏项、重挂、改变作者目标、修改物品原名和添加价格等字段都会被拒绝。
- GM 选择 `room-cleared`（目标战斗胜利）或 `layer-banked`（目标层完成）以及符合原文的发现方式。现有药箱、巡路板和帆布都有作者约定的层数，继续保留这些约定；没有开放任意移动目标层或自由创造战斗装备。
- 出征时把已确认计划转成冻结奖励清单。清单保存在真实副本运行状态和出征事实中，回放会与 GM 计划核对。
- 同一套副本奖励执行器创建 `CommissionItem` 唯一实例并提交 `commission-item-found`。重复打开、继续对白或再次结算层不会补发；跳过叙事不等于跳过战斗，也不影响已经满足的奖励条件。
- 委托背包与普通随机战利品分开：完成所在层并安全撤回／通关才带回；团灭全部遗失，失败反馈后可重试。普通战利品的随机数、入袋、半损规则和首通报酬继续沿用原实现。
- 返程在同一存档事务中登记真实持有实例。交付要求正确委托、正确远征、正确实例仍处于 `owned`，并原子转为 `delivered`，保留不可重复消费的交付凭据。没有物品不能交付。
- 前端显示出征物品安排、获得提示、独立委托背包、返程待交付物品或遗失记录；日志／任务面板读实物状态。副本 GM 的执行上下文也收到实际物品与返程结果。

## 兼容与使用

旧版已开始的远征保持原冻结规则，不能在途中凭空补一件任务物品。下一趟新计划自动启用；尚未出发且带有委托的旧计划会提示更新，必须通过「更新出征依据」重新生成实物安排后才能出征。历史无清单的运行状态、交付记录和提示词不被改写。

本次处理的是任务交付物；原作者的 `memory-only` 交付报酬没有被变成额外金币或装备。新能力仅用于现有作者巡守战斗目标。

## 验证

- 正式应用真实接单、出征、战斗、撤回、交付和存档回放通过；取得实例一次、持有实例正确、重复交付不重复消费，删改持有记录会被拒绝。
- 引擎真实战斗覆盖两种奖励条件、取得并入袋后再团灭、目标前失败和无清单的旧运行结构；核对普通掉落仍等于原算法结果。
- GM 契约测试覆盖遗漏物品、重复挂载、移动目标、改名／非法字段以及旧计划兼容。
- 战利品投影及任务 UI 集成测试通过，普通掉落／教学物品／D5 进度回归 49 项通过。
- 真实委托背包／返程结算组件、出征入口 UI、旧对白闭环与次日 GM 交接回归通过；TypeScript 两套检查、模块边界、游戏构建与产物检查通过。
- GM 与对白使用测试输出；本报告不把它们当作线上模型生成质量或人工浏览器游玩验证。
