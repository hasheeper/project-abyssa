# D4 克雷格旧庄园五层、千金与首通：勘探及实施计划

> 日期：2026-09-06；版本：v0.3；状态：**D4 工程闭环与本轮自动验证完成；缺图、人工试玩及完整发布验收待补**。
>
> 总入口：[D0–D6 实施计划](DEMO_CHARACTERS_AND_OLD_MANOR_IMPLEMENTATION_PLAN.md)；实施记录：[D4 实施与验证](../audits/2026-09-06-demo-d4-implementation.md)；勘探证据：[D4 勘探审计](../audits/2026-09-06-demo-d4-exploration.md)；实际前置：[D3 原界面接入与验收边界](../audits/2026-09-06-d3-ui-correction.md)。
>
> **用户约束：样式不能改，内容要改成庄园。** D4 继续使用当前共享战斗界面；增加宴会厅、千金、事件和结局内容，不重设计页面。

## 1. 目标、决策效力与停止边界

D4 的玩家闭环是：**初始五人出征 → 三层出口选择深入 → 宴会厅 → 千金战 → 解线救离 → 庄园接管与一次奖励 → 回馆 → 维护委托再出征**。第三层撤离与全灭仍各有合法回馆结果。

本文区分三类条款：

| 标记 | 效力 | 例子 |
| --- | --- | --- |
| 继承／既定 | 用户定稿、D0 契约或已实施且需保持的规则 | 先首通再回忆开放玛、原 UI、三重锁、失败仅损本趟 |
| 本阶段选型 | 本计划提出的具体工程及机制方案；实施按此落地并记录调整 | 新版本 reader、终局事务、补席时序、首通凭证 |
| 配平候选 | 用于启动模拟和试玩，不能称为用户定稿或已验证 | 千金 HP、初始席位、召唤预算、赏金和后两层倍率 |

**D4 不实施 D5**：不制作本尊回忆战、不实现玛铭约重排、不开放玛亲征、不发成长／装备。首通只建立回忆的前置资格和手写引入；回忆尚未发布时，不出现可点击却无法运行的挑战入口。维护路线在首通后即可使用，不强迫玩家等 D5 才能再出征。

继续排除分餐侍从、旧衣橱守门人、纯家具长桌 Boss、刻仪兽首发、其他三地牢及完整经营系统。玛丽埃塔是既有洋馆成员，首通救离时是叙事角色，不临时塞入操作队伍。Abyssa 独立完成规则、事实、存档与反馈，D4 不依赖 rp-style-lab 或 LLM。

## 2. 规划时基线与 D3 尾项

D3 已用 `abyssa.demo.manor-segment` 发布前三层；“新的开始”默认进入庄园。三小怪、管家、两个事件、七选四配给、第三层撤离、结算及第二趟已经接通。原 JSX 已提取为 `ExpeditionBattleSurface`，庄园和旧裂隙共享它。

已记录的证据包括一趟真实三层流程、40 项浏览器检查、四组类型检查和 19 个原表现文件的哈希比对。**这些不是五层配平或 D3 全量发布验收**；本轮规划没有重新运行它们。

| D3 尚缺证据 | D4 如何承接 | 最迟关口 |
| --- | --- | --- |
| 固定种子数值矩阵、管家封锁／落幕覆盖 | 先采前三层基线；用于确定进入第四层时的 HP、锈和物资分布 | 冻结 D4 敌群和 HP 前 |
| 不少于五趟人工试玩，含失败恢复 | 在保留三层档回归的同时补齐；五层试玩另列结果 | 完整庄园发布前 |
| 全部故障注入与恢复矩阵 | 补上原三层尚未覆盖项，再增加召唤、首通及剧情恢复 | 切换新档默认包前 |
| 同机性能对照 | 原三层与新满席场景分别采样，不拿测试执行秒数充当帧率 | D4.8 |

可以先做 D4 文档、版本边界、纯规则与素材准备；若基线暴露损档、重复结算、错误意图或原界面回归，先修复再集成。不得把尾项全部勾掉，也不以“D3 未全验收”为由重新设计已确认的页面。

## 3. 内容发布与版本隔离

### 3.1 本阶段选择：完整庄园使用显式第三版

源码目前把 schema／protocol 与 rulesVersion 绑定为 1 或 2。D4 将新增动态意图、召唤来源、解除退场、通关终局及 Campaign 首通账本，已经超出 D3 的严格状态结构。本计划选择 **schema／protocol／receipt／archive／fact 3，rulesVersion 3**；完整包使用 D0 预留的 `abyssa.demo`，首版 `contentVersion: 1`。

这是对 D0 早期“完整包 rulesVersion 2”目标的工程修订。已发布的 D3 包保持原身份、digest、字段和解释。版本号变化不表示重做六人规则，也不表示另建战斗页面。

| 档案 | Catalog／规则 | reader 与玩家行为 |
| --- | --- | --- |
| legacy | 原包／1 | 原流程、原黄金轨迹继续 |
| D3 三层 | `abyssa.demo.manor-segment`／2 | 原三层可继续、结算、导出和再次出征；出口仍不通第四层 |
| D4 新档 | `abyssa.demo`／3 | 五层首通及维护；仍是 `profile.demo.first-run`、初始五人 Lv.1、空装备 |
| 未知版本、缺包、digest 错误 | 不猜读 | 沿用不可用状态与诊断导出，不覆盖原档 |

D4 不自动迁移三层档、不继承不存在的首通、不改写进行中的远征。新档默认切到完整包的操作放在集成验收末尾；旧档继续按其冻结引用运行。以后如要把旧档资产迁入新包，另写显式迁移契约，本阶段不附带实现。

### 3.2 控制实现体积

- 保留 v1／v2 的严格 reader、请求解析、事实载荷和运行行为；增加 v3 注册，不把所有版本都当新结构解析。
- v3 复用现有角色配置、骰面、牌型、铭约顺序和纯计算能力，只为新持久结构与新行为增加必要模块。确需抽取公共纯函数时，旧版本轨迹和序列化回归同时通过；不复制一整套 UI 或六人内容。
- 新增内容定义文件与 v3 装配，避免直接修改 `demo-v1/manor.ts` 或它引用的共享角色表，导致 D3 digest 悄悄变化。
- registry、`AnyGameRecord`／receipt、默认创建、归档导入、pending request、恢复分类、角色／地图／战斗查询同时登记第三版。协议号与 schema／rules 各自有显式映射，不继续扩散隐式 `else = v2`。
- 仍用现有存储 Port、IndexedDB、CAS 和幂等回执；不新增第二个存档库或另一套持久事务系统。

## 4. 五层首通路线与维护路线

### 4.1 首通路线 `old-manor.first-clear`

沿用 [D0 稳定 ID](../design/DEMO_D0_SCOPE_AND_CONTRACTS.md)。下表 room 简写的完整前缀为 `room.old-manor.`。每趟仍生成不同实例 ID。

| 层 | 舞台／房间 | 内容 | 完成后的去向 |
| --- | --- | --- | --- |
| 1 | 迎客门厅；`first.foyer → first.register` | 候席客×3；迎宾簿沿用读／略过 | 入袋；玩家继续 |
| 2 | 服务走廊；`first.service → first.relic` | 侍者＋女佣＋候席客；遗物事件沿用现行规则 | 入袋；玩家继续 |
| 3 | 服务走廊；`first.butler → first.exit` | 落幕管家沿用 HP16、封锁／3伤落幕交替 | 入袋；明确选择撤离或深入 |
| 4 | 宴会厅；`first.banquet → first.seats` | 候席客×3＋女佣；空席核对 | 入袋；玩家继续至千金 |
| 5 | 宴会厅；`first.heiress` | 千金＋初始宾客 | 核心解除、末层入袋、通关终局与首通事务 |

第三层深入前沿用原弹层说明“下一段通向宴会厅，完成末层前没有主动出口”。切页、查看角色或刷新都不构成撤离；第四层不能增加隐形撤离捷径。前四层保留场间配给窗口，战后不满血、不清本趟临时锈。

**路线收尾必须改规则，不能伪装成出口。** 当前验证器要求每条路线最后一个房间为 exit；v3 增加有限的路线完成策略：`all-enemies` 的维护末战完成，或 `release-boss` 的千金末战完成，均可结束路线。第三层 exit 仍独立。末层胜利不要求玩家再选择一次“是否首通”，不在 D0 的房间表后私加假战斗／假第六层。

### 4.2 空席核对机制卡

| 项 | 本阶段选型 |
| --- | --- |
| ID／位置 | `event.old-manor.seats`；第四层战后 |
| 选项 | `read` 核对；`skip` 继续。均免费、无抽骰、无额外战斗回合 |
| 展示正文 | “白布下的椅子被登记作宾客，主位却仍空着。‘还差一位。’这句话越过你们，朝走廊深处重复。” |
| 读后信息 | 席位宾客会增强举杯；被吊住的千金也在服从规约；主位仍是陷阱 |
| 权威结果 | 持久记录房间实例、选项和已读信息；不减 Boss HP、不送奖励、不直接接管 |
| 卦签 | 只揭示这张卡没有费用／随机判定及其选项结果范围；不消费未来战斗 RNG |

略过信息不妨碍通关。Boss 开战时原意图区仍提供足够机制说明，不能把“曾读事件”变成正确看到伤害数字的前置条件。前三层事件的强弱保全判定、2G 费用与 4G 成功回报保持现行口径。

### 4.3 第四层考题与维护编队候选

第四层先采用已有三客一佣，让玩家决定先清攻击者还是切断修复；不新增精英、封锁或规则免疫。进入该层的残血与物资必须来自真实前三层分布，不能全满血调出一场孤立战斗就宣布配平。

首通后查询给出 `old-manor.maintenance`；出征命令也校验接管凭证。原地图侧板改委托名称、简介和敌群信息，保持布局。

| 维护层 | 房间／舞台 | 编队候选 |
| --- | --- | --- |
| 1 | `maintenance.layer-1`；门厅 | 候席客×3 |
| 2 | `maintenance.layer-2`；走廊 | 侍者＋女佣＋候席客 |
| 3 | `maintenance.layer-3 → maintenance.exit`；走廊 | 侍者×2＋女佣；胜利后可撤离／深入 |
| 4 | `maintenance.layer-4`；宴会厅 | 候席客×3＋女佣 |
| 5 | `maintenance.layer-5`；宴会厅 | 侍者×2＋女佣＋候席客；清场完成维护 |

维护是清理失去中央权限的支线残余。无原管家、无千金、无再次补齐主人；不重复救离／接管。未完成回忆时初始五人仍能跑完维护。首通后正常入口不再提供有真实奖励的首通路线重演，查看结局属于只读回顾。

## 5. 千金完整机制卡（P08）

### 5.1 身份、循环与数值

| 字段 | 本阶段方案 | 状态 |
| --- | --- | --- |
| 定义／遭遇 | `enemy.old-manor.puppet-heiress`／`encounter.old-manor.first.heiress` | 沿用 D0 |
| 身份 | 被吊线控制的伪女主人；战胜语义是解除控制 | 既定 |
| 生命／普通赏金 | HP18／18G；赏金只在成功解除时计入本层散金 | 配平候选；对比 HP16／18／20 |
| 初始阵列 | 候席客 A — 千金 — 候席客 B | 编排候选 |
| 席位 | 初始 2，上限 3；Boss 不占宾客席 | 配平候选；最大同时 4 个敌人 |
| 行动循环 | 第一轮举杯，第二轮补席，之后交替 | 本阶段选型 |
| 举杯 | 一条攻击意图，伤害 `2 + 存活席位宾客数`；只攻击一名队员 | 公式既定；目标范围本阶段选型 |
| 目标 | 回合公布时从存活队员中均匀抽取并锁定；执行时已力竭则落空，不改目标 | 沿用已有攻击目标原则 |
| 补席 | 每次至多 1 位；从右端入列；当轮不行动，下一轮获得意图 | 本阶段选型 |
| 整场补席储备 | 最多生成 6 位；满席不消耗储备；储备耗尽的补席轮公开显示空过 | 配平候选；限制实体增长和无限补怪 |
| 状态 | 不新增免疫；定身跳过行动且保留循环游标，缠线／挣脱沿 D1 | 本阶段选型；生产初始五人不依赖提线 |
| 结局 | 千金解除即胜利；余客解除并退场，不要求全部击杀 | 延续规格建议并在本阶段收口 |

宾客计数只包括**当前遭遇中仍在场、HP>0、明确标记为席位宾客的候席客实例**。背景画中的白布椅、女佣、千金、其他房间实例、已退场者都不计。定身只影响行动，被定身宾客仍占席。女佣修复不复活，因此普通 HP 恢复不改变宾客数。

初始宾客有普通 3G 赏金；补出的宾客无赏金。击败千金后自动解除的余客无击杀赏金。通关奖励另列，不混进每次伤害或死亡事件。

### 5.2 一份意图计算，贯通预览和结算

v3 攻击意图保留稳定身份、锁定目标、独立格挡和公式来源。建议身份由 encounter／round／enemy／ability 生成；数字是核心投影，不能把 `value` 当成唯一权威。

`原始伤害 = 2 + 当前席位宾客数`

`结算伤害 = max(0, max(0, 原始伤害 - 已生效的威压修正) - 本意图累计格挡)`

威压是否生效及其数值遵循现有回合边界，不因重算宾客改抽目标、刷新格挡或重跑铭约。所有攻击选择器、护符／格挡目标、日志和实际扣血调用同一个核心计算函数。UI 不另数 DOM 中的敌人。

| 状态变化 | 举杯原始伤害 | 格挡 | 实际伤害（无其他修正） |
| --- | --- | --- | --- |
| 3 位宾客，已格挡 2 | 5 | 2 | 3 |
| 玩家杀死 2 位宾客 | 3 | 2 | 1 |
| 同一意图期间合法增加 1 位宾客的规则夹具 | 4 | 2 | 2 |
| 剩余宾客全清 | 2 | 2 | 0 |

第三行用于验证共享计算，不代表本卡在举杯轮额外补席。意图为补席时显示补席数量／空位和储备；不伪装成 0 点攻击，也不能作为格挡目标。下次举杯预测可以附在已有说明中，不能与当前意图混为一条。

击杀宾客产生刀排碎裂和意图数值变化。玩家下一个输入窗口打开时必须已看到正确数字；读档直接呈现提交后的状态。补席轮已无当前举杯时，席位／刀排数量立即更新，下一举杯按最新状态计算。

### 5.3 召唤和行动队列

1. 回合开始公布已有敌人意图；按既有阵位语义生成当轮行动队列，开始执行后不改其成员和顺序。
2. 千金轮到补席时，在同一事务检查存活、未定身、空位和储备；成功才生成新实例并扣储备。
3. 新实例记录 `source=summoned`、召唤者、出生回合、递增序号和席位标记。ID 从本遭遇持久序号派生，不能用当前数组长度、时间或新的随机数。
4. 新实例进入右端阵位，当前 intent 为空，不能加入正在消费的 `enemyOrder`；下一回合才公布攻击。
5. 满席或储备耗尽也算本次补席步骤完成，循环转回举杯；定身跳过则不推进循环。
6. 候选储备下，整场最多 9 个历史实体（Boss＋2 初始＋6 补出），不依靠放宽数组上限承接无限增长。将来改预算必须同步校验、记录体积与性能门槛。

恢复／重试必须得到相同实例和同一队列游标。验证器检查初始编队及合法召唤来源，不再要求历史实体数组永远等于初始 `enemyIds`；也不能改成“只要 definition 存在就放行任意敌人”。

### 5.4 终击、同批死亡与撤回

- 一次行动／一次铭约效果已经锁定的主目标和邻位先结算完；不能因先打中 Boss 就吞掉本批合法波及。宾客若在这批中被实际击杀，按其来源给一次赏金。
- 本批后千金 HP 为 0 且仍有队员存活，进入不可追加玩家操作的终击收束；其余宾客标记 `released`、清意图并退出阵位。`released` 与 `defeated` 分开，保持剩余 HP，不伪造杀死宾客。
- 手动终击仍按 D1 执行一次最终 end-turn／成牌／铭约收束；敌方目标已解除时，后续伤害效果无目标，治疗等合法效果仍按原顺序。不能再发一份额外牌型收益。
- 若由 end-turn 内铭约击倒 Boss，完成该批已锁定伤害后解除余客，继续既定四约顺序，最终判定一次。不会再进入宾客敌方回合。
- 同批双方全灭优先判 `wipe`，不写首通、救离或 Boss 成功解除赏金。当前内容不主动制造这个情况，但状态与结算测试必须有明确结果。
- 沿 D1 最后击杀门槛，终击后不再提供战斗撤回；终击前普通行动仍可撤回。撤回同时还原血量、阵位、格挡、席位投影、散金和事实，不能只恢复画面。

v3 的 formation 只包含 `active` 实体，胜利验证按 encounter 的完成策略检查。不能仅把“有活敌不能胜利”检查删掉；普通战斗仍要求全部打败，千金战要求正确 Boss 解除及余客退场。

## 6. 从三重锁到救离：必经进度与脚本

### 6.1 必经拆除证据（本阶段叙事接线方案）

锚点是本趟房间完成的语义证据，不增加一套收集钥匙玩法，也不要求玩家随机拿到某件道具。建议由 run 中的房间胜利记录推导，不再维护可独立改写的五个布尔值。

| 必经胜利 | 已拆除的执行节点 | 说明方式 |
| --- | --- | --- |
| 第一层门厅 | 迎宾支线 | 敌群停止后，入口处吊线松弛；迎宾簿补充权限信息 |
| 第二层服务走廊 | 修复支线 | 该区不能继续替主干补线；保全遗物仍是可选支线 |
| 第三层落幕管家 | 封门支线 | 通往后半区的屏障解除；玛可继续接近核心区域 |
| 第四层宴会厅 | 补席的外围执行支线 | 核心被分区隔离；千金仍有卡片明确限定的本地补席储备 |
| 第五层千金 | 主人权限核心的最后控制连线 | 解除吊线，旧家宴程序停止；此后才可安全接管 |

这条路径通过分区拆除让旧程序停止，不是给女仆凭空补一条主人命令。全程无需玛坐上主位，也不通过暴力拔主干毁掉遗物。可选事件略过／遗物保全失败不影响必经证据。第三层撤离只带回本趟成果，重试不继承上趟未完成的主干拆除；成功接管才是永久进度。

### 6.2 首通段落草案

脚本 ID 沿用 `story.old-manor.release`。以下新增旁白是**本轮写作草案**，用户原定两句台词与动作顺序保持。

| 拍 | 画面／正文 | 数据条件 |
| --- | --- | --- |
| 0 核心失去控制 | “一路拆开的支线不再回织。最后的重量，落在吊住她的几束红线上。” | 五层必经胜利凭证齐备 |
| 1 解线 | 玩家终击落在吊线；线失张力垂落，刀排化灰，少女与桌体解除 | 成功解除；不播放少女爆裂／碎尸 |
| 2 救离 | 少女脱落沉睡。玛从已安全的通路抵达，抱起她，替她合眼：“家宴结束了，小姐。您可以离席了。” | 她未占操作队伍席，不补演一轮攻击 |
| 3 接管 | 空桌边，她把主位椅子推回桌下，合上三百年未敢合的登记簿：“今天没有客人。” | 旧规约已停止；不是接受陷阱主位 |

不指定少女的真实家族身份或灵魂来历，不用 a7 本尊素材替换千金第二阶段，不把 `thread_execution` 写成救离。剧情没有会改变胜负或奖励的隐藏选择；只提供继续、跳过和之后的回顾。

## 7. 首通账本、奖励与恢复

### 7.1 最小持久结构

| 所有者 | v3 新增／修订 | 不变量 |
| --- | --- | --- |
| Catalog | 完成策略、席位／召唤参数、奖励表、route 前置、事件类别 | 纯数据；无 UI 回调、AI 指令或自由脚本 |
| Encounter | 动态意图来源、循环游标、召唤序号／储备、敌人来源与退场原因 | 来源可追溯；队列冻结；席位有上限 |
| Run | 完成房间／遭遇证明，末层完成原因 | 必经证据来自当前 run；可选事件不冒充核心胜利 |
| Terminal | `outcome: extracted / wipe / cleared`，完成策略证据、普通层账本 | `cleared` 必须来自合法末层；首通与维护由 route 区分 |
| Campaign | `progress.old-manor.takeover` 的完成凭证；`reward.old-manor.first-clear` 发放凭证 | 引用同一成功首通 terminal；不会因 UI 状态为真就开放 |
| 故事呈现记录 | storyId／内容版本／结果凭证引用／已确认段落或跳过 | 可保存和回顾，但无赋予进度、资产或角色权限的能力 |

回忆可用资格由接管凭证派生；生产可挑战还必须有已发布 chapter。玛可出征仍需 D5 的 `unlock.marietta.sortie`，不能用 takeover 替代。

### 7.2 提交顺序与一次性语义

1. 战斗收束并提交末层胜利证明；普通自动续步记录房间完成、末层入袋，形成不可再战斗的 `cleared` terminal。每步已有稳定身份，刷新按保存位置续行。
2. 对 `cleared`，恢复分类自动发起带 terminalRef 的内部结算；不等待动画回调，也不自动替玩家决定第三层出口。
3. **一个原子提交**内：普通远征到账、剩余配给返还、结算记录、时钟推进一次、清 activeRunRef；首次完成时同时写接管、首通奖励到账凭证及待播放结局引用。
4. 只有第 3 步提交成功后才能展示“已接管／已领奖”及完整救离结局。存储失败停在可恢复的终局状态，不显示已经到账；演出失败不回滚已提交结果。
5. 故事继续／跳过只更新呈现记录，不推进时间、不重复结算。不需逐动画帧存档；刷新从最后确认的段落恢复，默认可续播，已完成可只读回顾。

原有第三层撤离／全灭仍保留结果确认和回馆交互。v3 明确分类“必须结算的通关后续”和“等待玩家出口选择”，不扩大自动续步到事件或道具消费。

| 去重对象 | 键／证据 | 重放行为 |
| --- | --- | --- |
| 层入袋 | runId＋layer | 返回／保留同笔层结果 |
| 普通远征 | runId＋terminalRef | 重复请求不加钱、不多推进相位 |
| 首通 | saveId＋epoch＋`progress.old-manor.takeover` | 已完成不得再次进入领奖分支 |
| 首通奖励 | saveId＋epoch＋`reward.old-manor.first-clear` | 金额从内容表取；与首通凭证同事务 |
| 剧情 | storyId＋completionRef＋storyVersion | 继续／跳过幂等，重看无奖励 |

导入复制必须重定位这些类型化引用，并保留已完成／已发放状态及原始来源。复制到新 saveId／epoch 不会恢复首通领奖资格。保持提交、事实、撤回锚点及终局引用一致，禁止全文件字符串替换。

### 7.3 配平候选与资金校验（P10）

- 保持现有一次层倍率公式与整数舍入；牌型层累计上限先沿用 +200%，本轮不改牌型和铭约本身。
- 五层倍率候选：100／125／150／175／200%；后两层待模拟。
- 三小怪 3／5／3G、管家 12G 沿用；千金 18G、初始候席客各 3G 为候选；召唤和解除余客 0G。
- 首通额外候选 **20G 到队伍资金**，固定发放一次，不乘深度／牌型／尘世，不放进散金。叙事接管是核心奖励，不附送晶石、Lv.2／3 或装备。
- 维护按五层普通战斗赏金入袋，`reward.old-manor.maintenance` 引用该路线奖励表，本轮不再叠加额外整趟奖金。撤离与失败沿 D0 范围。

### 8.3 取景与性能验收

在 1600×900 与 1280×720 比对基线，检查初始三敌、满席四敌、召唤右端入列、解除退场和角色检视往返。Boss 画布可以宽，点击区和意图锚点不能遮住邻客；目标连线仍指向相应实体。舞台内部标定解决问题，不挤压骰池或缩小整张页面。

同机、同构建模式各采至少 30 秒：连续投骰／固定／重掷／行动／归位，叠加满席、雾、数字变化和碎刀。记录主线程 >50ms 长任务、交互延迟、帧间隔 p95、内存及资源数量，明确设备／DPR／窗口尺寸。相对同机基线出现明显退化必须定位；初始预警线可设 p95 增幅 20%，不是已承诺的 FPS。

动态意图只在相关状态变化时计算；避免每帧重建查询、整份档案扫描或对每个配给目标做命令试跑。长场记录和满召唤历史纳入查询开销对比。复用现有雾实例，不给每名宾客叠一个高分辨率 canvas／模糊滤镜。隐藏页暂停可丢弃效果；降动效和无 WebGL 都有静态、可操作的结果。

## 9. 可见事实、记事与本地回馆反馈

v3 用封闭 payload 定义注册新事实，保留 source head、originRef、run／encounter 身份及 visibility。不要用“字段都是 JSON”代替载荷验证。

| 事实建议名 | 必须携带的依据 | 展示／用途 |
| --- | --- | --- |
| `banquet-seats-changed` | encounter、原因、宾客实例、before／after 数量、相关意图值 | 刀排和数字的提交后演出 |
| `enemy-summoned` | source／new instance、definition、出生轮、序号 | 补席日志与恢复审计 |
| `enemy-released` | 实例、Boss 解除原因、bounty=0 | 余客退场，不计作处刑 |
| `manor-program-stopped` | route／terminal、必经完成引用、release result | 救离和旧规约结束 |
| `manor-takeover-completed` | 首通凭证、terminalRef | 长期记事、维护／回忆前置 |
| `reward-granted` | rewardId、金额／资金域、claimRef | 一次发放账本 |

这些是工程候选事件名。设计语义 `banquet_guests_cleared` 对应本场实际清客，`manor_program_stopped` 对应成功解除；`thread_execution` 继续只指绞杀消费缠线并击杀，D4 初始五人不会凭空产生它。名称映射要显式登记，不能同义字符串并行生成两份事实。

回馆使用本地手写模板，由提交的终局和事件结果选择：第三层撤离说明成果保全；失败说明本趟损失；遗物成功才说保全；首通后玛说“今天没有客人”；维护完成说支线清理。不预写未发生的英雄行为，不用通用“通过管家”描述维护或千金首通。

当前 `manorLog` 在离开 active run 后返回空；因此长久反馈应从结算／首通凭证与未撤回事实投影，不能依赖当前战斗缓存。D4 只做纯映射和既有页面呈现，不扩建 LLM 上下文管线。未来 AI 可读公开事实表达结果，无权发奖励、解锁或改状态。

### 11.2 配平执行
