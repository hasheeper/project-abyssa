## 1. 已定稿的方向

1. `rp-style-lab` 是开发期的创作、调试与执行审计工具，也是正式创作内容、状态、修订和审定记录的权威来源；不随 DEMO 打包，不是玩家游玩时的必需服务。
2. Abyssa 发布物仍是静态网页、游戏规则和已审定的内容；浏览器完成事件调度、分支选择、变量处理、记忆记录与 IndexedDB 存档。
3. 定稿内容发布器属于rp制作端的AIRP后端应用：按已固定的来源与发布选择清单，读取精确楼层／分支／检查点及稿件，在rp侧完成校验、转换与正式内容包导出。Abyssa只接收已导出的包，不从楼层结果自行选稿、批准或重新编排剧情。
4. 创作最低流程为大纲生成与文本展开／润色两次独立模型调用；一条提示词中的 `<planning>` 不能替代两阶段流程。不需要自主 Agent 循环。
5. 复用 rp 的原生 Thread／Branch／Floor／Checkpoint、Workflow、模型槽位、提示资源、State Updater 和审计机制；不在浏览器或`llm/`复制另一套叙事状态、分支树或运行数据库。
6. 普通构建、CI、网页启动和玩家操作不触发模型调用。生成、审定、内容导入、网站构建是显式分开的操作。
7. 变量底座复用rp；开发期记忆是其上的AIRP应用能力。硬变量由规则程序维护，小模型只提交授权叙事字段的更新提案；开发期记忆与玩家实际经历分开，不随静态包复制。

这条路线是“制作期 AI 创作、游玩期规则驱动”，不是把模型能力编译进离线网页。发布后的内容可按已定义条件选择和组合，但不会针对任意自由输入现场创作；实时 AIRP 若未来重新提出，另立阶段，不能计入本轮承诺。

原计划的公共生成网关、试玩鉴权／额度、运行时生成任务与公共模型服务部署退出AIRP-4；这不排除rp本地制作后端的应用开发和导出接线。原有实验接口不删除、不接成当前发行依赖；没有网络生成不等于删除本地记忆与变量功能。

### 2.1 原生结构与AIRP的映射

| rp结构 | 开发期AIRP语义 | 边界 |
| --- | --- | --- |
| Application／Artifact Version／Release | 版本化任务、预设、人物资料、作者骨架、状态Schema；固定创作配置 | 不从浏览器未保存的表单重建正式配置，不改已冻结Release |
| Session／Root Thread | 一组连续创作任务及其根上下文 | 是创作容器，不是每位玩家的线上存档 |
| Floor | 一次语义明确的创作／状态提交，例如一个场景的生成 | 不机械对应每句对白或每次模型调用 |
| Workflow／Run | 楼层内大纲→写作及必要任务；节点结果和尝试谱系 | 同一Floor可以包含多次调用，不另造外层编排 |
| Branch | 从确定检查点试写替代方案，隔离候选后续状态 | 不是自动可发布的游戏选项；废弃分支不混入定稿 |
| 子区／Child Thread | 有独立上下文和状态链的局部场景／旁支创作 | 不是父楼层内的消息分栏；确有隔离需求才使用 |
| Checkpoint／State／Ledger／View | 该时点的创作变量、连续性记忆、变更依据和授权切片 | 状态来源唯一；不由发布器扫描聊天文本重算 |

首条样本可只用Root／Branch／Floor与Workflow，不强制创建子区。启用Fork时沿用原生terminal且restorable检查点约束；普通续作读取直接前一个terminal Checkpoint，不自行寻找“最近成功楼层”来绕过失败状态。

Child创建记录精确父Branch／Floor／Checkpoint及状态模式：`isolated-initial`、`snapshot-copy`或`frozen-readonly-reference`。父区后续变化不静默传入已冻结子区。子区结果要影响父级创作状态，必须通过父Interaction的`trustedEntryInput`等原生接收链与CAS提交；发布器不能复制Child JSON直接覆盖父State。独立子区稿可单独被发布清单选中，但不得据此声称它已回写主线。

rp分支与AVG选项分离：一个Branch可能只是被放弃的修稿。成为玩家可选路线时，作者必须在版本化绑定中明确其场景、条件与选项对应；不把整个rp分支树自动编译成游戏流程。

### 2.2 正式来源、编辑与浏览器缓存

正式创作上下文由“版本化作者资源＋指定Branch的精确Checkpoint及授权View＋当前任务／前序节点产物”组装，经rp既有编译与执行证据冻结。不能把页面最近显示的楼层、当前active分支或IndexedDB中的快照默认当作上下文；需要分页的原生查询必须完整解析目标，不能只取首屏或最后一项。

本地世界／人设源文件继续作为作者输入保留；导入或更新到rp版本化资源后，正式任务引用该精确版本。合法玩法快照和作者fixture也须显式导入为有来源的制作输入，并由rp记录实际使用的内容／hash；不在每轮生成时悄悄抓取浏览器存档作为唯一来源。

人工修订与审定采用AIRP应用级数据契约，存入rp的版本化JSON资源／Artifact，而不是新建底层审批系统：

| 应用级记录（待实现） | 固定内容 |
| --- | --- |
| 作者绑定 | 情境、场景／骨架版本、演员与槽位、玩法条件／选项映射及预算 |
| 文稿修订 | 源Thread／Branch／Floor／Checkpoint／Result引用、人工修改后的正文、原文与修订hash；原始Result不变 |
| 定稿与发布选择 | 明确选中的场景及来源、修订版本、授权状态切片引用、最终编译预览hash、检查项／备注、转换器版本与批准状态 |

先保存rp Draft，再固定为Artifact Version，正式导出只认固定版本。以上是待新增的AIRP数据与校验，不是声称rp已有专用“批准／发布”API；实现复用现有资源写入／版本化入口及并发校验。原创作Release和后续审定Artifact版本分开引用，必要的新Release不能回填或改写原运行上下文。

修改稿件不自动修改State。若变更影响后续连续性，须通过新的原生Interaction／Floor校验提交，并让审定记录引用相符的状态锚点；不能仍沿用被改掉的模型细节。子区回写另须满足父子接收约束。

浏览器与本地文件只保存可丢弃的缓存、未保存草稿、只读快照和派生预览；关闭窗口不应丢失已经保存到rp的正式稿件／审定。只改本地`approved`字段不能获得发布资格。既有O1-W本地审稿机制保持独立，不冒充AIRP原生审定来源。

这不迁移玩家存档：发布后玩家选择、阅读进度和变量仍由Abyssa合法命令在本地保存；它们有契约和事实来源，不是开发期第二个叙事数据库。发布器不把rp中某次模拟的State当成所有玩家的初始经历。

### 2.3 后端发布职责与现有扩展缺口

正式发布必须在rp后端完成来源、固定审定记录与最终内容的一致性核验。编辑界面或命令行只提交明确来源／修订／发布选择，不能以自带`approved`、自算hash或任意路径直接取得发布资格。人工判断仍由作者作出，后端负责绑定准确的审定对象和执行规则，不以自动校验替代文风／内容审读。

rp宿主负责通过现有服务Port解析版本、谱系和授权资料，并提供最小的受控导出支撑；AIRP应用负责领域规则和导出适配器。适配器只接收已解析的只读来源及显式版本配置，生成待校验内容，不直接查库、改State、调模型或执行网站构建。AIRP专属逻辑不塞入通用Route／Conversation／State引擎。

现有Application Archive面向开发配置迁移，不等于公开内容白名单；现有Package Server Extension也不能自行注册HTTP路由、访问数据库或后台任务。需要在4A定义、4B接通最小宿主导出Port及应用扩展边界，而不是仅移动目录或让Package绕过SDK。具体接口／契约编号待实现时确定，不预建通用CMS或无界发布任务系统。

游戏格式由Abyssa维护，通过版本化纯契约、校验与兼容清单供rp侧适配器消费；不直接导入相邻游戏仓库内部TS或整个Vite项目。场景槽位、分支、分页和情绪归一等语义转换必须先于最终审定完成。Abyssa导入后只复验、注册和构建，不再重拆对白、猜槽位或改变剧情；确需修改须回到rp生成并审定新包。

## 3. 创作模型、预设与上下文定稿

### 3.1 三类模型用途

| 逻辑用途 | 任务与输入 | 产物 |
| --- | --- | --- |
| 大推理模型 | 作者任务、人物／世界摘要、受控情境、可见记忆、目标和边界 | 可交给写作阶段的大纲、动机、因果与节拍 |
| 文本模型 | 上述必要上下文、大纲、独立文风预设、对白骨架约束 | 前置填充式创作记录与正文／情绪 |
| 小推理模型 | 已完成的创作结果、当前创作状态 View、更新政策 | 基础连续性记忆／变量更新提案，由 rp 校验提交 |

三类是用途，不强制三个不同型号；分别建立槽位、角色、Task、参数和提示资源。基本组合为两节点 Workflow，再由 State Updater 整理创作状态。固定审稿节点可后加，不能替代人工定稿，不引入无界自我修改循环。

Workflow 走 rp 原生 Session／Floor 执行容器，不通过外层串联多个 Manual Invocation 重造执行状态。Session 是创作运行容器，不表示必须做角色聊天。模型与预算在真实验证前显式配置，不在文档中预填供应商或假定原生 JSON Schema 能力。

### 3.2 类酒馆预设的适配边界

以用户提供的 `/Users/liuhang/Downloads/Kemini_Dramatron_v3.0.json` 为提取参考，保留源文件，不执行内置脚本。提取提示模块、启用状态、有效顺序、宏依赖、上下文插槽及确实影响送模历史的处理；输出为 rp 原生提示资源。不是完整酒馆兼容层，也不是把整个 JSON 当作 system prompt。

- 基础层：任务、人物与世界事实边界、可见性、上下文位置、变量／宏的显式解析、输出约束。预设配置宏与游戏剧情变量分开。
- 文本特化层：人物口吻、视角、叙事节奏、自然对白、反机械复述、必要的创作检查。不能把“少数字”“不分析”等写作条款套给状态更新模型。
- 保留正常虚构创作所需的反说教、反过度净化、复杂人物冲突与自然结尾要求；不强制人物温顺、和解或输出现实劝告。
- 删除 NSFW、越权／绕过硬安全限制、防截断填充及无关显示脚本；混合条款按句拆分，不能把全部 COT 或反说教内容一起删除。
- 前置填充式创作记录属于显式可见的创作检查，不索取、导出或宣称控制模型隐藏推理。记录格式由任务定义，不能只用它冒充已完成大纲阶段。

`llm/` 保留既有 O1-W 七场任务、双语格式、候选与人工审稿流程，以及预设提取／转换和离线试验。AIRP 独立配置，不覆盖 O1-W，不默默继承其双语或槽位约束。

### 3.3 情境与两类记忆

每个制作任务在rp中显式冻结情境 ID、来源内容版本、作者骨架、可用角色、Agenda／Bond／Locus 切片和资料摘要。来源可以是合法玩法得到的去标识化快照，或明确标为作者测试情境的fixture；均先形成可追溯的原生资源／输入记录，不把模拟经历伪称已发生的玩家事实。后续创作状态以rp检查点链为准，不与浏览器双向自动同步。

创作期记忆用于连续写作与版本内一致性，保存在 rp。发布时只带明确审定的剧情资源、规则引用与必要初始定义，不复制 rp Session、试跑变量或某个测试档案。

未定稿候选的连续性资料须限定在该候选／分支作用域，不能污染已审定的公共创作事实；废弃候选不能被后续任务当成正典。正式连续性记录引用获准稿件的身份和摘要，人工修订后需复核，不能沿用被改掉的模型细节。

玩家期记忆由实际已提交的事件与选择生成。静态内容按作者定义的条件引用相关对白；没有匹配变体时使用已审核的通用文本或不触发，不能拼入尚未发生的经历。首版沿用既有分支／再提供变体，不枚举所有历史组合，不建设通用语义检索系统。

### 3.4 变量与记忆处理定稿

本节为待实施的应用规则，不是现成Memory API或新增玩家存档格式。结论是“rp变量底座足够，记忆语义需要补齐”，不是“加一个摘要字段就已有完整记忆系统”。

#### 3.4.1 已有能力与职责边界

rp的State Schema V2已支持标量、object、list、stable-ID collection；Node Policy可限定namespace、writer与操作，Candidate Engine强制执行类型、权限、预算和原子校验。State Updater只提出结构化修改，经Proposal／Validation与Candidate Engine结算；当前状态仍来自Branch的Floor／Checkpoint链，不是独立Variable Store。详见[状态架构](../../../../rp-style-lab/docs/architecture/narrative-state-system.md)。

| 内容 | 定稿归属与写入规则 |
| --- | --- |
| 世界观、人设、规则和作者骨架 | rp版本化作者资源；明确导入版本，不每轮从聊天重新抽取 |
| 硬变量 | 任务推进、奖励、资源、关系阶段等由规则程序或明确作者操作确定；模型正文／摘要不能授予效果 |
| 创作连续性与记忆 | 当前分支State中的有界结构化集合；小模型仅对授权叙事namespace提出更新，服务端校验后提交 |
| 原始依据与审定 | 原生Entry／Result／稿件Artifact Version／Checkpoint及已有执行证据；原文与历史不因摘要或改稿被覆盖 |
| 本轮送模上下文 | 从固定资源、授权状态与有效记忆派生的切片；保留选择依据与实际输入证据，不成为第二套可编辑状态库 |

变量表示“当前是什么”，记忆表示“发生过什么、谁知道、哪些细节要延续”，执行历史提供核查依据。三者不能互相替代。故事事实、人物认知和创作计划必须区分：人物可能说谎或误解；大纲中的未来安排、前置创作记录和未采用方案不自动成为已发生事实。

#### 3.4.2 最小记忆契约

以下是4A需固定的语义字段，不预占接口名或schema编号：

| 字段组 | 必须表达的内容 |
| --- | --- |
| 稳定身份与类别 | 稳定条目ID；事件、承诺、人物认知或表现连续性等类别；不按摘要文本生成唯一身份 |
| 内容与定位 | 有界摘要、涉及人物、规范主题键；区分客观事实、人物相信的内容与作者计划，计划不得进入已发生经历集合 |
| 故事时点 | 发生／适用时点；与模型生成时间、编辑时间分开，未来计划不伪装成过去经历 |
| 知情范围 | 公共或明确知情人物，以及相应依据；叙述者／规划任务的权限与角色本人知情分开 |
| 来源与作用域 | 精确原生来源、稿件修订版本及必要hash，所属情境／分支和事件范围；继承由原生谱系解释 |
| 有效性 | 有效、被替代或失效及其替代关系／原因；保留来源，不靠覆盖旧历史解释修订 |

候选与已审定资格由精确来源和rp版本化审定记录判定，不另建记忆审批数据库，也不相信模型写出的`approved`。条目引用来源稿件／结果；审定记录再绑定相符的状态锚点，不能制造“当前State引用自己的未来Checkpoint/hash”的循环依赖。

长期原文留在原生记录，State只保存当前续写需要的有界条目和引用。若增加阶段摘要，必须记录覆盖范围和来源；摘要只是派生资料，不能覆盖精确事实或把前一轮摘要当作唯一依据继续递归总结。首版不要求无限历史自动压缩／归档，达到容量上限须显式停止或经审查整理，不静默删除关键记忆，也不转存到浏览器绕过预算。

#### 3.4.3 抽取、提交与改稿

1. 从明确Branch／Checkpoint和版本化资料组装上下文，执行原生大纲→写作Workflow；大纲、创作记录与实际正文分别保留。
2. 小模型读取本轮实际正文、可信输入、现有授权记忆和更新政策，提出新增／更新／合并提案；不能把计划、推测或修辞直接升级为事实。创作候选的文学细节只在相应候选／事件范围内有效。
3. 应用层补齐或核验可信来源，检查引用、类别、作用域、知情依据及重复处理身份，再交原生状态提交链。通用schema校验不证明摘要忠实于原文；语义冲突须显式保留问题供审定，不能自动以“最新文本”覆盖。
4. 沿用rp的accepted-change／accepted-noop／rejected与原生失败语义，不另造重试／审计引擎。依赖记忆更新的连续创作Action应将该步骤设为required；若设为advisory，失败必须可见，不能假定状态已更新后继续引用。需要恢复时走新的合法执行，不扫描“最近成功楼层”绕过失败检查点。
5. 同一来源重复处理不得重复新增记忆。在采用新稿或作废决定的创作分支内，失效或替代相关条目；依赖旧条目的摘要、后续候选及批准记录也须复核。新状态经新Interaction／Floor提交，不能只改稿件而保留冲突记忆。新建替代稿不追改其他分支、旧检查点或已发行包；复核结果登记为新版本，旧批准不得挪用于新稿。

未审定稿可以在自己的分支内形成连续性，但不得污染其他候选或已审定来源。Fork继承固定快照，Child仍遵守§2.1的隔离／导入／可信回写规则；公共创作事实的提升须明确审定和原生接收，不能把跨分支记忆JSON直接合并。硬变量更新与记忆更新分别授权，修改叙事摘要不能顺带发奖、推进任务或改变关系阶段。

#### 3.4.4 受控召回与三类模型上下文

rp的[View实现](../../../../rp-style-lab/server/src/narrative-state/domain/view.ts)按schema tag裁剪字段，对collection成员应用同一字段投影；不提供按条目知情人、主题、故事时间或相关性自动筛选的完整记忆检索。因此不能只添加`knownBy`字段或提示“不要泄露”就宣称完成隔离。

AIRP应用层在送模前依次检查：原生分支／继承范围、来源与修订有效性、任务允许的候选／审定范围、故事时间、知情权限，再按场景／人物／主题筛选。采用必需条目优先、明确时序和稳定ID排序，应用条数、逐条及总预算；必需条目不可用或装不下时明确失败，可选条目按固定策略省略并记录。不要先把完整私密集合送给写作模型再让其自筛。

| 模型用途 | 记忆输入与权限 |
| --- | --- |
| 大推理／规划 | 作者明确授权的事实、相关经历、未解决事项和必要秘密；标清角色知情范围，不把规划者知道当作所有角色知道 |
| 文本展开／润色 | 大纲、独立文风预设、场景必要记忆和视角边界；不常驻全量历史。首版共享对白切片使用在场者共同可知内容，私有切片另行明确授权 |
| 小推理／状态整理 | 本轮实际正文、可信输入、现有授权状态及更新政策；用于抽取和对照，不继承写作模型的自由发挥权限 |

派生切片记录所用源版本／状态锚点、条目ID、筛选策略版本、顺序、省略情况及hash，并纳入rp实际输入证据。具体接入rp输入／投影的扩展点在4B验证，不把浏览器传来的任意JSON冒充原生State View。相同冻结输入和策略应得到相同切片；策略或来源改变需重新组装并复核相关产物。

Abyssa已有[知识条目](../../../src/game-core/contracts/airp.ts)、[上下文组装器](../../../src/game-core/session/airp-context.ts)与[知情／预算测试](../../../src/game-core/session/airp.test.ts)，可复用其语义和测试案例。现有来源是玩家Fact／head，开发期需要适配为rp原生来源；这不是已经接通rp记忆，也不是照搬玩家存档为创作State。

#### 3.4.5 首版范围与发布边界

首版只补四项：记忆契约、抽取更新、受控召回、改稿失效。契约／抽取规则／筛选策略属于rp上的AIRP应用资源与领域模块，存储、校验、分支、检查点和审计继续归rp；发布器消费获准状态切片和来源，不成为记忆服务。具体代码位置在原生扩展点核对后确定，不跨仓库导入内部实现。

不新增向量库、通用Memory服务、无限历史压缩、自动知情传播、全量知识图谱或自主Agent循环。也不要求玩家部署后端：发布包只携带审定剧情、条件和必要定义；玩家记忆由实际游戏命令产生，不能复制开发期候选记忆或某个测试档案。无匹配经历时使用审核过的通用变体或不触发，不能现场编造回忆。

## 4. 发布器的最小输入与输出

本节名称为待实现的数据契约，不是现有类型或可用 CLI。先支持一条委托，不建设通用内容管理平台。

### 4.1 输入：结果与作者绑定分离

| 输入 | 必须包含 | 约束 |
| --- | --- | --- |
| 来源引用 | rp Application／创作Release、Session／Thread／Branch、Floor／Checkpoint ID和hash、Workflow节点／Run／Result；Child另有父锚点 | 按原生归属逐项复验；禁止默认取latest／active分支或整个会话最后一段文本 |
| 模型正文 | 显式创作记录、按顺序的文本与单一情绪；多人时有可验证说话者 | 只解析已声明格式；不猜未知标签，不接受任意脚本 |
| 作者绑定 | rp中固定的任务／情境、骨架版本／hash、目标内容兼容范围、演员／槽位／玩法条件映射、预算 | 编辑者定义并保存为版本化资源；模型不生成跳转、奖励、目标或运行身份 |
| 状态依据 | 创作所用及修订后适用的Checkpoint、授权View／Entry、记忆切片来源与筛选策略及其身份／hash；涉及回写时含父级接收依据 | 按Schema／权限读取，复核来源修订与记忆有效性；不导出原始State，也不从文本重算缺失字段 |
| 定稿与发布选择 | rp中固定的清单Artifact Version／hash、所选稿件修订、候选／最终预览hash、批准检查项与转换器版本 | 本地review不构成批准；改正文、绑定、骨架、状态依据或转换规则后必须新审定 |

正式导出由rp后端通过原生服务Port核对固定发布清单及其完整来源闭包；AIRP应用／适配器不直接读取数据库，不仅凭`/runs/:runId/result`认定归属。清单显式列出入选场景，不因active分支切换、源分支继续创作或出现更新稿而重新选取；无法解析所需版本或发生混用时失败，不降级为latest。Abyssa导入端不再查询原生楼层来替代这一步。

本地只读快照和fixture仅用于离线解析／预览／测试，不创建正式批准、不绕过来源核对。rp暂不可用时允许dry-run，但不产生新的正式定稿包；已经获准导出的包仍可在无rp环境下构建和游玩。人工输入先保存成rp中的可追溯修订，不能伪装成原始模型输出。

仅当 Workflow 及所需执行阶段真实成功，才允许把模型候选送入定稿。失败、截断、取消、中断、required Updater／审稿失败，不能凭某个节点已有 `outputText` 绕过整体失败。advisory 失败须在预览中显式列出并由审稿确认；不伪造成功状态或自动续跑。

### 4.2 模型格式与游戏格式分离

模型侧仍保持“前置填充式创作记录＋文本＋情绪”的最小要求。说话者和槽位可由既有任务绑定，若文本包含说话者则必须与绑定相符；缺失／多余内容明确报错，不把段落位置猜成分支身份。

rp侧执行固定版本的Abyssa导出适配器，按游戏消费契约填入作者骨架的稳定节点、演员、舞台及引用。它只替换获准的文本与情绪槽，不新建任意选项、跳转、条件、资产或奖励。该转换在最终审定之前完成，不留给游戏导入器重做；原主角控制规则和 `{{user}}` 占位符继续生效。

情绪白名单以[共享情绪契约](../../../src/shared/domain/presentation/emotion.ts)为准，当前正好14个：

`neutral`、`smile`、`joy`、`sad`、`angry`、`surprised`、`serious`、`closed`、`wry`、`flustered`、`displeased`、`confident`、`confused`、`panicked`。

允许明确的现有别名转为规范 ID，并在预览中展示规范化结果；未知情绪应阻断发布，不能靠播放器回退为 neutral 隐藏错误。表情、气泡和动作继续由现有逐角色映射解析，不要求模型输出三套参数。

长稿不自动截断、任意分页或重编号来迎合旧契约。先由作者明确分页／槽位；确需扩大 AIRP 场景预算或结构时，走新契约与新内容版本。保留旧版 reader，不能静默放宽所有历史内容。

### 4.3 三类产物，两个边界

| 产物 | 内容 | 是否进入静态发行物 |
| --- | --- | --- |
| rp创作与审定记录 | 原始结果、创作记录、State／谱系、作者绑定、人工修订和固定发布选择；本地可缓存副本 | 否；权威记录在rp，缓存不授予发布资格 |
| 已审定内容包 | 最小 manifest、编译后的剧情数据、资产／规则引用、兼容版本与内容 hash | 是；先进入版本化内容源，再随构建打包 |
| 开发来源索引 | 由rp批准清单派生的包hash、精确来源闭包、转换器／骨架与审定版本 | 开发侧保留，可重建；不成为独立可编辑的叙事事实库，玩家不依赖rp在线 |

公开 manifest 只包含包身份、格式版本、目标兼容身份、声明的文件／场景与 hash。通过字段白名单从数据重建，不复制整个 rp Result、Archive 或候选目录。hash 用于一致性和追溯，不冒充数字签名或作者真实性认证。

不发布 Provider 凭据、连接头、完整提示词、内部审计、原始测试存档、本地绝对路径、未选稿和可见创作记录。模型结果只进入文本字段，不执行 HTML／JS／CSS，不接受远程资源或包内逃逸路径。

## 5. 最小处理流程与发布门禁

按“rp解析来源／保存修订→rp执行适配转换→原播放器预览→rp固定审定／发布选择→rp正式导出→Abyssa导入复验→静态构建”执行。发布器不在校验失败时自动调用模型修复。

1. **rp读取来源**：后端解析Application／Release／Thread／Branch／Floor／Checkpoint与执行产物的精确关系，按授权View取得状态依据；需要Child结果时同时核对父锚点及必要的回写证据。不改原始执行事实。
2. **rp形成候选**：AIRP应用解析正文与已保存的作者绑定。界面中的人工修改可暂存，但须经后端保存为文稿修订Artifact Version才能定稿；影响连续性的变化另走原生状态提交，不把手改稿回写为原始Result。
3. **rp转换与校验**：固定适配器／消费契约／兼容清单版本，按骨架映射获准槽位，检查14情绪、人物、文本、引用、覆盖与目标版本。复用提取为纯契约的游戏／AVG校验规则，缺槽、多槽、未知角色、预算超限、主角越界均拒绝。
4. **原播放器预览**：rp提供带确定身份／hash的转换结果和字段差异，由Abyssa原播放器在隔离的制作预览中呈现，检查分页、情绪差分、选项和舞台表现。不另造播放器；本地改动仅是草稿，须回到rp保存／重编译后再审定。
5. **rp固定人工定稿**：默认 `pending`。作者检查事实／知情、文风、主角边界、情绪／分页、分支和静态通用性；AIRP后端核对审定所指的来源、转换版本和最终内容后，沿资源版本化入口固定批准清单。只有精确版本为`approved`且与后端生成的最终内容／预览hash一致才进入导出，不只信任界面上传的通过标记。保存冲突须重读复核。
6. **rp正式导出**：后端重新解析固定批准清单及所选来源，验证相同适配器产物与审定对象一致，按公开字段白名单构造不可变内容包并提供下载／显式复制。同一身份同一摘要可幂等复用，不同摘要须换版本；失败不覆盖已定稿包，不推进Branch、不合并Child，也不直接写Abyssa仓库或部署目录。
7. **Abyssa导入并构建**：导入器独立复验包格式、文件白名单、引用、hash及目标兼容版本，拒绝开发Archive、未定稿预览或不支持的契约；通过后显式注册新内容版本。不得重排对白／分支或重做语义转换。普通构建只消费已导入内容，不连接rp、不启动`llm/`服务。

人工定稿绑定来源闭包与编译预览而不只绑定模型原文，防止“审核后换分支／换骨架／变分页”。导出前重新计算相同确定性产物；转换器变化也需复验。公开包hash不包含导出时间、机器路径等非确定字段，不与私有批准记录形成循环摘要依赖，相同冻结输入应产生相同可发布内容。

第6步“内容包发布”指rp制作端生成获准内容包，不是第7步的网站构建，更不是上传网站、提交Git或更改生产地址。网站部署仍由Abyssa独立、明确授权地执行。

## 6. 版本、旧档与随时更新

- 本轮不预占下一 `contentVersion`、AIRP 契约号或场景来源枚举值；实施时先核对注册表。现有内容8／9及其摘要保持不变。
- 现有 `source: handwritten` 需在新契约中区分已审定的制作期生成内容；来源只描述制作方式，不授予额外游戏权限。旧版字段与 reader 保持有效，不对旧档批量改名。
- 已经开始／显示的场景、阅读位置、选择和奖励身份保持冻结；新稿不能替换玩家已经保存的对白。新版本对新档或允许显式续接的边界生效。
- 发布包不含开发机 Session 或测试玩家状态。运行时实例 ID、证据、记忆、变量仍由实际游戏命令产生。
- 首版采用“内容入仓库版本目录→显式注册→重新静态构建”，不建设远端内容 CMS、浏览器动态拉取 latest 或无校验热更新。
- 更新遵守既有资源清单、哈希、旧页资产保留和整包原子部署。恢复网页旧发行物不等于把新存档强行降级；版本不兼容时保留存档并明确提示。
- 可回看的文本与恢复所需身份应在既有存档导出策略中完整保留。制作期审计不进入游戏记录，仍遵守当前 AIRP 及整档容量限制。

## 7. 代码归属与首版范围

撤销在Abyssa的`llm/publisher/`建设主发布器的建议。正式发布器及其来源／审定门禁位于rp仓库的AIRP后端应用模块；通用宿主能力与应用规则分开实现。具体目录、接口和扩展注册方式在4A核对后确定，不把现有Package SDK描述成已经支持任意导出服务。

| 代码／资源 | 所有权与依赖 |
| --- | --- |
| 通用来源解析与最小导出支撑 | rp宿主；复用Applications／Conversation等公开服务Port，负责受控读取与通用交付机制，不内置AIRP领域定义 |
| AIRP创作／记忆／修订审定／发布模块 | rp侧AIRP应用；作者绑定、文稿修订、发布选择等schema沿原生资源保存，不复制数据库或状态引擎 |
| Abyssa消费契约、纯校验与导出适配器 | 格式及游戏兼容性由Abyssa维护；通过版本化纯模块／契约交付给rp应用，适配器在rp侧执行且受审定版本绑定 |
| 导入、包复验与原播放器预览 | Abyssa开发工具；只接收获准包或明确标识的预览，不读取rp楼层来重组内容，不负责批准或正式导出 |
| 游戏与静态网站构建 | Abyssa；只依赖已导入内容及游戏资产，不依赖rp服务、开发期应用代码或`llm/` |

两仓库不直接导入相邻内部TS实现。公开纯契约不依赖React、IndexedDB、rp数据库或Provider；通用14情绪通过纯契约／一致性测试共享，不让core反向依赖UI。兼容清单提供明确的骨架、演员、资产／规则引用和目标版本，不让rp适配器扫描游戏工作树推断当前格式。发生契约／适配器变更时发布新版本并重新编译审定。

rp应用只通过原生Interaction／Candidate Engine修改创作状态，不因部署在后端就直接改表或私自apply patch。导出适配器保持只读、确定性，无模型调用或状态副作用。Abyssa的`llm/`保留既有O1-W及预设试验，不作为AIRP发布权威；若保留辅助命令，仅用于导入／复验／预览，不保留第二套正式导出入口。

rp保管正式导出产物与私有来源索引；Abyssa显式导入的公开产物建议落在`src/content/generated/airp/<release-id>/`，发行包ID与rp创作Release ID分开。由明确Catalog入口消费，不扫描目录启用全部候选。制作缓存／预览不授予发布资格；只有获准公开内容及安全的最小来源摘要进入游戏仓库，不把完整来源闭包、原始提示或审计随网站打包，也不允许手改导入目录绕过重新审定。

首版不做：通用图形化 CMS、浏览器任意拖入不可信包、全量酒馆导入、自动生成游戏逻辑、多人协作审批平台、签名分发基础设施、全历史组合预生成、向量记忆库／通用Memory服务、公共模型网关或桌面打包。

## 10. 已决事项与实施时参数

已决：纯静态发行；rp是开发期叙事内容、状态、分支谱系与审定记录的权威源；正式发布器归rp的AIRP后端应用，通用核心只供机制，Abyssa仅消费内容并构建网站；消费契约由Abyssa维护、适配器在rp侧锁版本执行，批准后不再语义改写；不造第二套状态；变量／记忆、固定Workflow、三类预设、14情绪、人工审定和旧档保护决定不变。

实施时收口而不重开所有权：rp宿主最小导出Port与AIRP应用扩展位置、消费契约的纯模块交付方式、新内容／契约编号、获准槽位与预算、可见创作记录模板、来源／资源版本化／状态提交字段、记忆类别／容量及召回接入点、实际模型与制作预算。4A固定契约，4B验证后端接线；不能因缺少现成发布或Memory接口，把正式门禁放回Abyssa脚本、浏览器缓存或不受控Package代码。
