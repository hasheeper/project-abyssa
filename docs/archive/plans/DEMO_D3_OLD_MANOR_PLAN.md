## 1. 目标、交付和停止边界

D3 让玩家从正常新档入口，用凯尔与勇者四人、Lv.1、无装备，完成**备包 → 庄园前三层 → 击败落幕管家 → 主动撤离 → 一次结算 → 回馆 → 再次出征**。另走一条全灭回馆路径，证明失败不会卡死补给。全部流程由 Abyssa 的规则、存档和手写内容独立完成。

当前 D1 已提供正式角色规则，D2 已提供真实角色页；但生产写会话、地图发令和 Battle 仍运行 legacy。D3 需要交付版本化的可玩链路，不能把换背景等同于副本接入。

| 本阶段必须交付 | 后续阶段 |
| --- | --- |
| 独立且引用闭合的三层阶段内容包；生产构建可正常创建、继续、导入导出 | 完整五层包在 D4 发布 |
| 候席客、执盘侍者、缝补女佣、落幕管家 | 千金、席位联动和救离演出归 D4；刻仪兽不入本次主线 |
| 两张手写事件卡、七种常备道具、四槽备包 | 扩大事件池、完整生产和商店不属于 D3 |
| 层入袋、第三层出口、失败、返还、时间推进和第二趟 | 首通接管、维护路线归 D4 |
| 正式规则的 Battle 交互、同档跨页、恢复、素材取景与性能验收 | 回忆、玛亲征、成长获得及两件装备的领取／装卸归 D5 |

三层撤离只生成「完成前三层并撤离」，不写庄园首通、接管、回忆或玛亲征开放。不得把第三层当作五层路线的最后一层来复用通关奖励。

### 1.1 不重开已经确定的讨论

- 用户已定：先通庄园，再完成回忆开放玛；Lv.3 封顶；只做备用短刃、应急药囊两件空面装备；玛重排敌方阵位。
- [D1 实施口径 R01–R08](../design/DEMO_CHARACTER_RULES_REVIEW.md#11-d1-实施口径记录2026-09-06)继续有效，包括最后击杀后一次收束、四约顺序、沉眠可行动、下一场 1 HP／雨夜下一层至少 2 HP、临时锈选面规则。
- [D0 资金与配给契约](../design/DEMO_D0_SCOPE_AND_CONTRACTS.md#6-资产配给与奖励契约)已确定：零货币开局；出征补足绑定配给；失败只损失本趟资产；结算推进一个当下相位。不是本轮待选方案。
- 分餐侍从、旧衣橱守门人、纯家具长桌 Boss 均已废弃；不能进入引用表或测试主线。
- 五枚好感晶石、连线／进度槽、右侧状态区、三格私约、简介布局继续保留。规则封顶与缺数据不构成删面板的理由。
- 保留已确认的战斗配色、低亮度红线、悬吊顶栏、骰子自然滚动与小幅归位、敌后雾气。

## 3. 阶段内容发布与新旧档策略

### 3.1 三层内容单独发布

本阶段选型：新增 `abyssa.demo.manor-segment`，首版 `contentVersion: 1 / rulesVersion: 2`，路线 `old-manor.segment-3`。这是**前三层内部试玩包**，正常构建和正常存档使用它，不是测试 fixture。

- D0 的完整目标 `abyssa.demo`、`old-manor.first-clear`、`old-manor.maintenance` 继续保留给完整内容；本阶段不发布引用不全的五层路线。
- 三层包复用 D0 预留的 `room.old-manor.first.*`、`encounter.old-manor.first.*`、事件和敌人定义 ID；路线身份、范围及奖励能力独立。
- 标题「新的开始」在 D3 集成验收后创建阶段包的 `profile.demo.first-run`。入口清楚说明目前可玩前三层，不展示内部 Catalog 字符串。
- 第三层出口提供真实「撤离回馆」；可显示后续区域尚未开放的说明，不提供能提交的深入命令。完整出口的 leave／continue 能力用隔离路线夹具验证，D4 才向玩家开放深入。
- 不用本地 feature flag 把同一个已保存 Catalog 临时截成三层；不能换一台机器就改变终局含义。

### 3.2 保留玛资料，封住未完成的执行能力

本阶段推荐明确「可出征角色／仅资料角色」，而不是删掉玛的页面或将她的铭约静默置空：

1. 同一正式六面源表提供六人定义；阶段包中的玛声明为 `dossier-only`，profile 仅开放初始五人。
2. 铭约绑定使用可区分的「无铭约／已实现引用／延期能力声明」。凯尔属于无铭约；玛属于延期能力，明确关联 D5 的能力声明与未开放原因，不能伪装成无能力。
3. 所有可执行引用必须完整；延期声明不是 effect handler，也不能加入可执行引用图。Catalog 校验拒绝初始队伍或任一可用 profile 含延期角色；出征校验再拒绝一次，不能只隐藏按钮。
4. 角色查询保留玛的六面、资料与现有私约容器，说明亲征及铭约尚未开放；不把尚未实现的重排效果写成已生效。
5. D5 发布完整实现时，以新内容版本替换能力声明并接真实开放账本。内部玛动作测试继续使用明确标识的测试包。

这是 D3 的正式能力契约扩展，不能通过向 `validateDemoContent` 传「忽略缺引用」名单发布生产包。若实施时发现扩展影响超出预期，先回写本节替代选型；不得降级为删除角色页或导入 fixture。

### 3.3 存档保证

| 档案类别 | 处理 |
| --- | --- |
| 已有 legacy 玩家档 | 原 Catalog、schema／protocol 1 继续；黄金轨迹和旧结算不变 |
| D1／D2 测试档 | 未发布夹具，可随 D3 契约重建并提升 fixture 内容版本；不冒充生产迁移 |
| D3 阶段玩家档 | schema／archive／protocol／receipt 2；同一 `abyssa-game-v1` 数据库，冻结阶段 Catalog 与 digest |
| D4 完整庄园 | 新包或新内容版本；保留阶段包 reader，使已有三层档仍可继续，不能原地换五层 |
| 未知包、旧测试夹具或错误 digest | 明确不可用，允许诊断导出；不清档、不换包猜读 |

规则 2 尚未面向玩家发布，D3 可以在首次发布前调整它的状态结构。**首次产生阶段玩家档之后**，结构或规则的不兼容变化必须走显式版本及 reader 决策。当前 registry 将 schema 与 rules 版本等值绑定，这只是现有两版实现限制，不能在以后靠维持数字 2 掩盖破坏性变更。

## 4. 最小状态模型与推进时序

### 4.1 规则／会话职责

建议将 v2 的持久运行实体整理为 Expedition：`snapshot.campaign + snapshot.expedition`。Expedition 唯一持有 run，当前节点按判别联合保存战斗、事件、房间完成、出口或终局；不再用假 encounter 容纳事件房。

| 所有者 | 字段与职责 |
| --- | --- |
| Catalog | Layer／Room 定义与次序；战斗／事件引用；层结算前置节点；合法出口；供应与奖励表；artId／sceneId 的语义键 |
| Campaign | 既有资金／时钟／成长；绑定配给库存；活动运行引用；已应用结算凭证与最近结果 |
| Expedition run | 冻结配置、残血／临时锈／雨夜标记；room／layer 实例进度；物资与胃口；本层散金／牌型累计；入袋记录；事件选择和已揭示情报；RNG |
| 当前节点 | `in-encounter`、`event-choice`、`room-complete`、`exit-choice`、`finished` 等互斥状态；战斗状态仅在需要时存在 |
| Encounter | 敌人实例／阶段游标、阵位、已冻结执行顺序、意图目标、骰池、回合道具计数、undo |
| 待结算结果 | runRef、terminalRef、结果原因、最深层、入袋凭证、实际损失和剩余物资；终局产生后不可由 UI 重算 |

`roomInstanceId` 与 `encounterInstanceId` 独立；definitionId 不能作为某趟完成／领奖的去重键。`completedRooms`、`layerSettlements` 保存凭证，验证它们和实际路线游标一致，而非只检查数字非负。

战斗 engine 可继续以 run＋encounter 作为计算上下文，adapter 临时组装后返回权威更新；持久层不同时保存两份可变 run。D2 查询跟随新的拥有者取数据，输出语义尽量保持稳定。成长 progress 仍须等于合法 profile，不为放入物资而放宽其校验。

### 4.2 边界执行表

| 转换 | 必须完成 | 必须等待／保留 |
| --- | --- | --- |
| 最后敌人死亡 | 关闭额外行动；按 D1 完成一次 end-turn／铭约收束，再确认胜利 | 不在击杀瞬间重复发一份牌型收益 |
| 遭遇胜利 → 房间完成 | 记录战斗结果，清本场敌方状态、格挡和 undo | 保留残血、整趟锈、胃口、携带品、本层散金和累计牌型 |
| 房间完成 → 下一房间 | 玩家 `advance-room`；校验当前实例及顺序 | 允许在走廊使用合法道具；不借自动恢复跳过准备窗口 |
| 进入事件房 | 建立未选择事件与参与者候选 | 等待 choose-event，刷新不默认选第一项 |
| 事件结果 → 房间完成 | 同事务提交费用、判定、结果和奖励；结果可重读 | 不因播放文字再次抽骰；结果确认只推进，不再领奖 |
| 层前置节点全完成 | 自动生成一次层结算凭证、重置本层散金与牌型累积 | 不把清层当整趟终局；不回满血 |
| 管家胜利并完成第三层入袋 | 到 `exit-choice` | 等待主动撤离；出口决定不自动选；出口本身不作为入袋的前置，避免循环等待 |
| 进入下一遭遇 | 力竭者基础归队 1 HP；建立新骰池／首回合共鸣 | 进入同层事件时不提前复活；存活者不自动治疗 |
| 进入下一层 | 雨夜标记者恢复至至少 2 HP，上限为其 maxHP，清标记 | 不降低现有更高 HP；同层第二战只归队 1 HP |
| 全灭 | 清本层未入袋收益，计算本趟入袋金币折损，生成 wipe 终局 | 不进入下一场自动复活，不追加伤病／住院系统 |
| 确认回馆 | 一次结算、返还实际剩余物资、推进一个相位、清活动运行 | 结果留 Campaign；动画结束、刷新、重试不再到账 |

第 1、2 层均没有主动撤离指令。关闭页面、进入角色页或打开洋馆只是导航，活动远征仍保留；不能因此返还物品、恢复 HP 或开第二趟。

## 5. 命令、原子性与恢复

### 5.1 对外命令

沿 D0 命名，必要字段以严格解析器为准：

| 命令 | 玩家输入 | 原子结果／校验 |
| --- | --- | --- |
| start-expedition | routeId、partyIds、四槽 item definition 选择、运行身份 | 校验可出征与最多四种、不重复；补差额＋预留＋冻结配置＋启动一次完成 |
| battle-command | runRef、动作与目标 ID | 按 v2 合法选项执行；玩家不能指定最终伤害或调用内部 resolve-next-enemy |
| use-item | runRef、itemInstanceId、目标域／ID，必要时 faceId 或情报范围 | 效果、充能、胃口、本轮次数、必要 RNG 一起提交；失败不扣任何一项 |
| choose-event | runRef、roomInstanceId、choiceId、actorId（若需） | 验证候选、代价与一次判定；不得提交 success、奖励金额或骰值 |
| advance-room | runRef、当前 roomInstanceId | 只能从已完成房间走唯一合法下一节点；不能越层／跳出口 |
| choose-exit | runRef、exitInstanceId、leave／continue | 第三层凭证和已开放分支成立才接受；阶段包拒绝 continue |
| settle-expedition | runRef、terminalRef | 服务端式应用逻辑从凭证计算到账／返还／时间；相同终局只应用一次 |
| undo | 当前 runRef | 仅当前战斗合法回退；同步恢复资源、RNG、骰和回合计数，撤回对应事实 |

这里的「应用逻辑」仍在本地确定性服务内，不要求服务器。新建和导入也通过版本化 runtime；旧独立 Battle 格式仅按 legacy 导入规则处理。

### 5.2 去重与失效输入

- 传输幂等：`saveId + epoch + clientRequestId`，校验完整 fingerprint。业务幂等：层入袋按 run＋layerInstance、事件按 run＋roomInstance、终局按 run＋terminalRef、结算按 run。
- 失败写入不显示成功，不先导航；相同原请求重试获得原回执。换 requestId 再点事件／出口／终局也不会重复奖励。
- 物资实例任一时点只在库存或一趟远征中。切换选项、刷新地图不写配给，不存在独立「领取」按钮反复加库存。
- user command 遇 CAS 冲突先读取新状态并提示重新选择；不能用新 head 偷重放原操作。只有内部确定性续步可重新分类。
- 导入保留规则／来源语义，新 save／epoch；显式重映射 room、encounter、enemy、物资、选择、入袋／终局／结算凭证及其引用。原结算记录保留「已应用」，不能复制后再领。
- 截断、伪造库存归属、非法游标、重复层结算、future room 事件和错误 terminalRef 均应拒绝。

### 5.3 自动续步分类

runtime 查询应返回「有确定性步骤／等待输入／已终结」及原因，而非由页面猜状态：

| 状态 | 恢复动作 |
| --- | --- |
| 敌队列 cursor 未到尾 | 只执行当前敌方一步；读回 head 后再分类 |
| 敌队列结束且战斗继续 | next-round，停在待 ROLL |
| 最后击杀后尚未收束 | 完成唯一 end-turn；生成遭遇／房间结果 |
| 清层条件满足但尚无入袋凭证 | 确定性 settle-layer；之后停在走廊或出口 |
| event-choice、room-complete、exit-choice | 不自动选择、不推进，恢复原输入窗口 |
| finished，未结算 | 显示实际终局，等待玩家确认回馆；已有结算 pending 则重试原请求 |
| 已应用结算 | 显示已返回结果；旧 battle 链接可回馆，不重新结算 |

保留 D2 角色页只读会话：读取不清 pending、不派发、不续步。版本化执行会话负责恢复，不在 Battle、Map 各复制一份循环。

替代现有「最多六步」的原则：每步必须使执行 cursor、阶段或凭证严格前进；同一 head／同一续步身份重复即报诊断。按一批有限工作让出事件循环，重新读取并继续；测试覆盖超过六步的合法队列。保留总工作保护，但根据可达状态和敌人数上界制定，不靠盲目加大数字掩盖死循环。

pending 需同时绑定版本、档案、epoch 与运行；终局已结算后 activeRunRef 会清空，不能在核对原回执之前就把成功请求当作「旧 run」丢弃。只有确实属于另一趟且没有匹配完成回执的输入才失效。回放／恢复不重播完整滚骰、伤害或奖励动画。

## 6. 前三层内容与敌人机制卡

### 6.3 落幕管家（P08 首段候选）

- 单体，HP **16 作为模拟起点**，同时对比 12／20；赏金候选 12G。没有额外免疫、召唤或第二条生命。
- 两个执行阶段循环：**闭门（封锁）→ 落幕（攻击 3）**。落幕在该轮玩家 ROLL 前完整预告；不额外插入一整轮无行动的「预告阶段」。这是对旧建议循环的细化，需试玩验证压力。
- 闭门轮开始时，从存活队员中等概率锁定一人，敌回合执行后为其安排下一轮封锁；本轮不附带伤害。
- 封锁仅阻止下一轮该骰的投掷、行动、成牌与持约资格；不扣 HP，不封整队。持续到该轮结束，或被合法净化解除；跨遭遇不保留。
- 落幕攻击目标在落幕轮开始时另行锁定；显示 3 伤及已格挡后的值。目标倒地则落空。不会在玩家结束回合后才突然指定目标。
- 被定身跳过的阶段不前进；下一轮仍预告该阶段。与 D1 的保留蓄力／挣脱规则一致；生产首通不依赖未开放的玛。
- 击败后只开放门扉出口，不结束家宴；专用闭门／举臂帧未提供时，先用清晰意图、轻量状态表现和现有立绘验证，不能标成完整姿态动画。

配平必须记录多少局实际遇到封锁和落幕、选择了何种解法、是否被连续压到无法操作。若大量对局在第一次落幕前结束，应调 HP／节奏并重新测，不以强制无敌回合或好骰保证教学。

### 7.2 使用语义

- 战斗 `roll`／`act` 中才接受相应道具，敌方队列、收束、提交和演出锁期间不插入输入；每轮最多两件，净化补掷仍只计一件。
- 场外不虚构回合；受实际充能及整趟胃口约束。终局后停止使用，按真实剩余返还。
- 治疗满血、作用于力竭者、没有攻击意图却用护符、没有临时锈却用保养工具，均拒绝且不消费。不能借无效道具推进业务计数。
- 食物成功使用才加该成员的胃口次数；场间不归零。药水不计入食物胃口。
- 幸运符增加的是额度而非立刻重掷。无可重掷骰时拒绝，固定／已用／封锁骰不因此变为可重掷。重掷上限验证改为「基础 2＋本轮合法授予额度」，不能继续硬编码最大 2。
- 战斗内可撤回的道具与动作共用 undo 边界，恢复全部充能、胃口、计数、骰和 RNG；不只退 HP。查看情报、选择事件及跨房间不能撤回，且关闭此前战斗 undo，避免先看隐藏信息再免费返还物品。

### 7.3 圣水与投骰后解除封锁

D3 的友方可净化负面先只登记 `status.sealed`；其余负面尚未实现，不新增假中毒或假减益。圣水找不到封锁及任何已实现白名单目标时拒绝；临时／基础／永久锈均不属于圣水净化，保养工具只清临时锈。

当前 D1 被封骰在 ROLL 时没有面。推荐规则：

1. ROLL 前解除：清封锁，随后正常全池 ROLL 包含它。
2. ROLL 后解除，且该骰 `faceIndex = null`：同一次 use-item 事务从 combat RNG 给它**补掷一次**，保存结果并只产生该 owner 的滚骰演出。无需消耗普通重掷次数。
3. 已有面的骰保留原朝向／固定／已用语义，不借净化免费重掷或恢复行动。
4. D1 艾洛拉现行在 end-turn 的净化仍按既有规则；不回到玩家行动，不重算已经冻结的牌型，不触发上述玩家窗口补掷。

补掷、消费和净化必须一起恢复。用例需覆盖刷新时已解除但回执未显示的情况，不再抽第二次。

### 8.2 遗物整理

## 9. 层经济与失败结果（P10）

### 9.1 计算候选

继承 D0：只有本层散金可支付昂贵治疗；Campaign 旧存款不参与战内结算。建议奖励采用一次深度放大，定义如下：

`L = 本层击杀赏金 + 本层事件奖励 − 已实际支付的本层费用`

`B = min(2.00, 本层各已收束回合的 adjustedBonus 之和)`

`层入袋 = roundHalfUp(L × (1 + B) × depth × earth) + fixed`

| 参数 | D3 候选 |
| --- | --- |
| 基础赏金 | 候席客 3、侍者 5、女佣 3、管家 12；击杀时不乘深度 |
| depth | 第 1／2／3 层：1.00／1.25／1.50 |
| earth | 冻结队伍有 D1 尘世共鸣则 1.10，否则 1.00；按队伍资格，不因临时倒地重算阵容 |
| 牌型收益上限 | 整层加成最多 +2.00；同层多战共享，不是每场重置 |
| fixed | D3 为 0；不额外授予晶石、成长、首通奖励或装备 |

使用整数 G 和百分比／基点运算，只在层入袋末尾四舍五入一次，0.5 向上。中间乘法不逐项舍入。昂贵治疗沿 D1 扣 `min(当前散金, 10)`，余额不为负；不把费用重复计入两次。

**收益上限是本轮新增配平建议。** 当前逐回合 handBonus 累加本身没有经济上限，女佣或持续防御／治疗可能使拖延刷收益成为最优解。这里限制的是层经济，不改变 D1 牌型判定、显示或铭约触发；达到上限后的实际牌型仍正常结算战斗。模拟比较 +1.5／+2.0／+2.5，再冻结实际值。

旧规格公式提过水杯 +10G，但水杯属于已排除的专属小件；D3 不登记、不发放、不隐含加钱。以后真有固定奖励时才加在乘法后；当前 `fixed = 0` 的测试必须成立。

核算例（只证明公式，不代表玩家实测收益）：

- 第 2 层 11G 赏金，不选付费事件、不用昂贵治疗；牌型累计 +0.6，尘世有效：`roundHalfUp(11 × 1.6 × 1.25 × 1.1) = 24G`。
- 三层都无牌型加成、无事件收支、无战内金币消耗且尘世有效：10＋15＋20＝45G。
- 相同条件而每层均到 +2.0 上限：30＋45＋59＝134G。重复空过不再增加层经济。

### 9.2 入袋与最终结算分开

- 每层只在必经战斗和事件节点完成／略过后入袋。中间一场胜利不清空 L／B；清层凭证完成后才重置。
- 撤离：保留本趟已入袋金币和实际剩余配给。
- 失败：丢当前未入袋收益；**本趟已入袋金币保留 `floor(bankedGold / 2)`**，其余记为损失。奇数向下是本轮推荐舍入。原 Campaign party/public/crystals 不扣。
- 例如馆内原有 100G，本趟已入袋 31G、当前散金 7G 时失败：本趟带回 15G，损失已入袋 16G＋未入袋 7G；最终 party 为 115G。
- 本次不产生材料奖励；状态和结果若支持材料，失败仍遵循 D0 的已入袋非货币材料保留，不虚构物品填充面板。
- 最终 settle 同时完成资金、未耗配给返还、结算凭证、活动运行清空和时间推进：dawn→day→dusk→night→次日 dawn。无需等演出结束才推进。
- 下一趟按照正常开战规则从满 HP、无上趟临时锈开始；这不等于战后或中途跳页可回满。

D3 的金币是已验证的冒险成果；完整消费经济留后续。零成本配给已保证再尝试，不为了制造金币用途临时加商店或收费回血。

### 10.3 性能与样式保护

- 已固定／已用骰只在真实变化时更新；普通 reroll 动画只取回执中实际参与的 ownerIds，圣水补掷只动一颗。
- 新回合回到待 ROLL 时保留已确认的小角度、平滑归位；检视角色、刷新查询、跨标签同步不触发滚骰。
- 静态六面、角色图和 SVG 保持稳定 props／memo；无逐帧 React setState，无每帧完整存档验证或全量 clone。
- 雾继续使用现有共享 canvas、24Hz 绘制节奏和隐藏／低动效处理；不为每个敌人新建 WebGL，也不靠全屏模糊蒙版替代。
- 动画仅消费已提交回执；replayed 或恢复时直接投影保存结果。长内容进度不要求等全部动画播完才成为可恢复状态。
- 开工先在独立端口记录当前 Battle 截图与性能；完工按同机、同尺寸、同操作复测，不能拿 D2 角色页的短采样充当 Battle 基线。
- 验收尺寸 1600×900、1280×720；记录连续 30 秒 ROLL／固定／重掷／使用／归位、封锁解除、治疗线和雾并行的 long task、掉帧与 React 更新。逐一解释新增 >50ms 长任务，必要时优化；不凭测试通过宣称恒定 60FPS。

## 11. 事实、回馆反馈与未来 LLM

保留 `adventure / simulation` 来源、originRef、head、可见性和撤回过滤。D3 新增的是真实业务事实：

| 事实组 | 最少上下文 |
| --- | --- |
| expedition-started | run／route、冻结 partyIds、成员配置摘要引用；补齐 D2 缺失的生涯参与者证据 |
| room／event | layer／room 实例与定义、选择、actorId、实际判定与成本／结果；不包含未发生分支 |
| enemy repair／seal | 敌方 actor、目标域与实例、实际 HP／封锁变化；不得当成角色治疗高光 |
| item used／information revealed | 实际物品实例／来源、目标、消耗及揭示范围；流水和可见剧情分开 |
| layer banked | 基础散金、经济加成／倍率、舍入、入袋金额与凭证 |
| expedition finished／settled | run、route、结果原因、成员、最高层、损失／到账／返还、terminal／settlement 引用 |

当前 fact mapper 从提交后的 activeRunRef 取运行身份；结算会清空它。新事实必须携带转换自身的旧运行上下文，不能在到账事务后生成 `runRef = null` 的无归属结果。时间也明确区分事件发生相位和结算后的相位。

finish 与 settled 在角色记事中仍合并为一次冒险结果。路线与事件默认是队伍经历；只有真实 actorId 才写个人行为。若记录分区处置，不将第三层成果翻译成「家宴结束」。回馆文字用本地模板匹配实际结果，反馈播放失败不阻塞结算或第二趟。

以后 rp-style-lab 只消费经裁剪的已提交事实和手写背景，返回可丢弃的表现文本；不能写库存、奖励、判定、进度或驱动 continuation。D3 不接 LLM、复杂上下文编排或联网生成管线。

## 13. 验收矩阵与配平方法

| 类别 | 必测行为 |
| --- | --- |
| 生产路径 | 新建阶段档→五人 Lv.1 无装备→选四件→前三层两事件→管家→撤离→结算→馆内→换备包再出征；全过程无 fixture 注入 |
| 失败路径 | 第一层与已入袋后分别全灭；只有本趟损失、实际返还；零存款仍可再出征 |
| 路线边界 | 同层两战夹具：中途不入袋，累计牌型／锈／胃口保留；每场首回合独立；1HP／雨夜2HP分开；第一二层拒绝撤离；未打管家不能造出口 |
| 出口 | 第三层入袋一次；刷新等待选择；阶段包拒绝深入；隔离完整路线夹具可深入，选择恢复不重复执行 |
| 敌人 | 女佣满血整理／锁定目标死亡／修复不超疗；侍者定身保蓄力；管家跳过阶段不丢游标；攻击预览与扣血一致 |
| 道具 | 同 request 重放只耗一次；本轮第三件拒绝；四槽重复／超槽拒绝；胃口第三次拒绝；永久锈不可清；幸运符正确增加额度；圣水在 ROLL 前后各自正确 |
| 事件 | 成功／失败／绕行／费用不足；沉眠强判定、醒面弱判定和两种万能；失败不跳主线；重复点选和换 actor 不再判；卦签不预知 RNG |
| 经济 | 两战共享一层；倍率仅一次；正好半单位舍入；封顶后拖延不再增钱；昂贵治疗只扣实际散金；奇数折半；旧余额无损；配给不换钱 |
| 原子性 | 在出征、物品、事件、房间完成、入袋、出口、结算前后注入写失败／丢响应；重试、双标签 CAS 后无丢失／重复／越权选择 |
| 恢复 | 所有等待窗口和敌方队列中刷新；已提交但未播放恢复；超过六步合法链；错误 epoch、run、digest；旧运行 pending 不执行到新运行 |
| 导入／历史 | 含事件、待结算、已结算的归档复制；所有新实例引用闭合、不会重领；终局事实归属原 run；个人记事过滤 simulation、撤回和敌方行为 |
| 视觉 | 默认五人、少员、四敌测试阵容和单体大管家；两背景；名字／意图／物品可读；好感晶石与私约区完整；固定骰不旋转，补掷只动一颗 |
| 性能／发布 | 独立端口内的实际构建；根路径与 `/abyssa/`；reduced-motion、隐藏恢复、无 WebGL 降级；无远程图床／fixture 生产依赖；legacy 轨迹与玩家路径继续通过 |

配平使用默认五人 Lv.1、无装备作为唯一生产首通基准；另测低补给、无艾、少员和一次误用道具。玛／高等级测试只证明规则，不冒充生产可达条件。

先跑固定的 100 个种子、先攻／先保命两种可解释策略，记录每层成功率、回合数、HP／力竭、封锁与落幕触发次数、消耗、牌型收益、净入袋及再次出征能力；再人工试玩不少于 5 趟，含一趟失败恢复。100 个种子是首轮比较样本，不是玩家胜率保证。发现新问题后扩样本，不为追求绿色反复只测最优策略。

实际执行阶段验收命令沿项目基线：`npm run typecheck`、`npm run boundaries:check`、`npm test`、`npm run test:build`、`npm run check:entries`、`npm run check:core:import`、`npm run build:game`、`npm run check:output -- game`、独立端口的 game＋storage smoke。若共享 UI API 有变化，再跑 UI 包发布和 Storybook 检查。
