## 1. D1 要交付什么

D1 交付可脱离页面执行、可保存恢复的正式角色规则，以及供角色页、编队和战斗共用的配置查询。六人 36 面、Lv.1–3 解析、两件空面装备的配置效果、四名勇者的两阶铭约、玛的六面动作、共鸣都进入本阶段的规则验证。

本次勘探确认：S0–S3 的确定性执行、事务、回执和恢复可以继续使用，但现有玩法仍是 legacy。正式内容不能只换角色数据表；必须补版本分流、配置模型、回合收束和遭遇边界。

三项主要方向已经定稿，不再作为备选重开：

- 初始勇者队先通庄园，再完成回忆，开放玛丽埃塔亲征。
- 首发 Lv.3 封顶，仅备用短刃、应急药囊；包含现行铭约与既定凯尔团队成长。
- 玛的重排作用于敌方阵位。已生成的执行队列不随阵位移动而改变。

本文第 2 节保留勘探时的差距，第 5 节保留实施推荐的依据；实际接口和交付以实施报告为准。当前采用细则已写回规则记录第 11 节，区别于用户此前逐项确认的三项范围决策。

| 内容 | D1 必须交付 | 后续负责 |

## 2. 勘探后的关键结论

| 现状 | 对 D1 的影响 | 处理位置 |
| --- | --- | --- |
| Catalog、应用协议／记录／事实和 runtime 都按版本 1 装配 | 仅把 `rulesVersion` 改成 `1 \| 2` 会让新数据进入旧执行器 | D1-A：信封路由、严格版本分支和注册装配 |
| FaceDef 只有动作、强度、pip、quality 等旧字段 | 无法表达沉眠可行动、自然花色和成长后的稳定面身份 | D1-B：正式面与已解析配置 |
| 成牌忽略命数，没有同花，也未返回已确定的万能代点 | 不能直接用旧最高牌型触发正式铭约 | D1-D：快照、候选比较和独立图案检测 |
| `wild` 只接攻击／格挡；治疗拒绝 wild；UI 对友方点击默认选格挡 | 凯尔和诺玛必须具有三种明确可选动作 | D1-C：动作能力与命令描述；D3 接交互 |
| 原子效果系统存在，但生产反应处理器未承载正式铭约 | 不能只在内容里填一个 reaction ID 就认为能力生效 | D1-C/D：有限的纯规则处理器与装配校验 |
| 赏金在攻击前按基础强度预判，伤害修正另在 resolver 发生 | 顺劈、绞杀、铭约击杀必须按实际 HP 转变只奖励一次 | D1-C：统一击杀结果路径，金额由奖励策略提供 |
| 敌阵横排取自 enemies 数组；行动队列另有 enemyOrder／cursor | 可以隔离阵位与队列，但死亡收拢、召唤入列须共享一个规则 | D1-C：存活敌阵顺序与目标快照 |
| 最后敌人死亡可发 layer-cleared；遭遇 ID 按层号生成 | 同层两战会错认清层，并发生身份碰撞 | D1-A/E：独立 encounter 结果；层完成交给 session |
| 临时锈只记 rustLevel；归队只在 startLayer 中处理 | 无法精确清某一面，也无法区分下一场／下一层 | D1-B/E：来源、faceId、生命周期 |
| runtime 和编队视图读取全局 legacy 常量 | 即便 core 正确，页面也可能展示旧六面或发错协议 | D1-F：按 record 查询；D2/D3 消费相同投影 |

这不是对 S1 抽取结果的否定：旧规则现在有明确边界和回归基线。D1 应在边界处新增规则 2，而不是改变旧档含义。

## 3. 版本与代码组织方案

### 3.1 先路由，再验证和执行

沿用 D0 版本矩阵：`abyssa.demo/content 1/rules 2`；应用记录、归档、命令、回执、事实版本为 2；legacy 保留原值，独立 Battle schema 4 只服务旧包。IndexedDB 的 `abyssa-game-v1`、物理版本 1、saves／receipts 保持。

```mermaid
flowchart LR
  Raw["原始记录／请求"] --> Envelope["有界信封解析"]
  Envelope --> Registry["版本与 Catalog 注册表"]
  Registry --> V1["legacy reader + rules 1"]
  Registry --> V2["DEMO reader + rules 2"]
  V1 --> Commit["应用事务／CAS／回执"]
  V2 --> Commit
  Commit --> View["按已提交 record 生成查询"]
```

注册表由 runtime 显式注入，不放在 core 全局变量中。以 schema、Catalog ID、contentVersion、rulesVersion 找 reader 与执行器，再严格验证 digest 和完整引用。命令的 protocolVersion 必须与目标记录匹配；不知道版本、缺内容或摘要不符时返回错误，不猜默认包。

新建档案由已注册的创建 profile 选择内容；公开入口不能接受任意 initial 覆写来生成满级、全员开放或额外装备。内部夹具走独立装配。旧版已有创建／导入语义继续保持。

建议将 `GameRecordV1 | GameRecordV2`、`CommandRequestV1 | CommandRequestV2` 等建成判别联合。旧严格 reader 不增加一堆 optional 新字段；版本分支完成后再调用各自规则。存储读取边界应反映原始值需要验证，不能靠 `as GameRecordV2` 代替验证。

### 3.2 最小代码落点

以下是拟新增位置，不代表本轮已创建；已有目录继续使用，不再整理根目录。

| 位置 | 职责 | 复用／隔离原则 |
| --- | --- | --- |
| `src/game-core/contracts/demo.ts` 及版本化 catalog validation | 规则 2 内容契约；公开出口仍是 contracts/index.ts | 保留旧 Catalog 形状和摘要；正式内容只导入公开类型 |
| `src/game-core/battle/domain/demo-state.ts` | encounter 的回合、阵位、意图和结算状态 | 不把规则 2 强转成旧 ExpeditionState |
| `src/game-core/battle/rules/v2/` | 正式配置、动作、成牌、铭约、生命周期 | 按职责拆文件；不复制完整旧引擎再改角色名 |
| `src/game-core/battle/demo-engine.ts` | 规则 2 create／restore／dispatch／select | 通过 battle/index.ts 导出，和 legacy 执行器显式区分 |
| `src/game-core/session/v2/` | Campaign、run、room 和 encounter 所有权、冻结配置 | D1 做必要状态及场间边界；D3/D5 填内容流程 |
| `src/game-application/versions/` | 版本 reader、请求解析、事实映射、导入重映射 | 共用事务原则；应用层不重新计算战斗规则 |
| `src/game-runtime/catalogs.ts`、现有 create-runtime/views | 实际 Catalog 注册与按档案查询 | 不向 apps 输出可变当前 Catalog |
| `src/content/gameplay/demo-v1/` | 六人、四约两阶、成长、两件装备和共鸣的纯数据 | 不含函数、React、图片导入或服务调用 |
| 现有 `testing/` 与 `*.test.ts` | 版本夹具、规则用例、兼容验证 | 不注册到生产入口，不改旧黄金期望 |

RNG、JSON 限制、摘要、纯数值修正、确定性排序以及事务 CAS 是优先复用点。旧 resolver 的具体状态读写、layer-cleared 事件和生命周期不能未经检验直接复用。需要抽取共享原子操作时，只抽与状态形状无关的部分，并同时验证旧路径。

沿用依赖门禁：core 只依赖 core；application 只依赖自身和 core 公共入口；gameplay 只引用纯数据与公开契约类型；runtime 负责装配。新公共类型从现有三个 index 出口提供，不放宽应用层深层导入限制。

### 3.3 不完整内容怎样验证

D1 尚未拥有正式庄园遭遇、奖励及玛铭约完整策略。不能为满足旧 Catalog 的必填路线、召唤怪和狂暴字段，把 legacy.rift 或假 Boss 注册成正式庄园。

采用两层验证：角色等内容模块可独立校验；完整可执行 Catalog 必须检查所有可达引用和处理器。D1 的完整执行验证使用 `testing/` 内独立 fixture Catalog（拟 ID：`abyssa.fixture.demo-d1`），组合正式已完成模块与显式测试遭遇。玛六面夹具明确不宣称包含已完成的葫芦铭约。

正式 `abyssa.demo` 模块逐步形成，但在内容引用闭合、玩法入口具备交互之前，不加入玩家默认创建列表、不生成可持续流转的生产新档。内部 schema 2 的创建、读写和导入仍须通过应用层验证；测试数据与普通档案不可混用。

这解决 D1 规则先完成、D3 内容稍后进入的问题。D1 验收分别写“规则能力已完成”和“生产内容尚未开放”，不以空 handler 或测试解锁冒充完成。内容摘要在正式发布时冻结；发布后修改必须登记新内容版本并保留活动档案所需旧包。

## 4. 正式数据与查询契约

### 4.1 骰面身份和配置解析

沿用 D0 的 `face.<characterId>.01` 至 `.06`。内部数组索引可为 0–5，但保存的面身份与对外面位 1–6 不混用。

| 概念 | 建议表达 | 约束 |
| --- | --- | --- |
| 面身份 | faceId、slot | 一角色恰六面；全局唯一；成长不换 ID |
| 点数 | naturalPip 或命点万能的判别类型 | 凯尔 .06 无原生点；诺 .01 固定为 1；不用 0 表示沉眠 |
| 命数 | awake／asleep | 影响成牌资格，独立于能否执行动作 |
| 花色 | 四种自然花色之一 | 行动万能不改花色；铭约按朝上面花色，共鸣按角色主副色 |
| 动作 | actionId、参数、可选分支 | 玩家选择攻／挡／治属于命令；不是成牌代点 |
| 品质 | plain／gild／rust；锈带来源 | 基础可除锈、永久锈与本趟退化分别记录 |
| 角色元数据 | 主副花色、身份、基础 maxHP、成长与铭约引用 | 由 Catalog 定义，不能从中文姓名猜规则 |

查询按以下顺序执行：基础定义 → 已应用成长奖励 → 合法装备改写 → 本趟临时覆盖。Campaign 等级由已应用奖励推导；进入远征后保存不可变的已解析配置及来源引用，馆内修改不能影响这趟。快照用确定性重算和摘要校验防止字段互相矛盾。

`resolveCharacterConfig` 至少返回六面、maxHP、铭约阶段、装备适用性及每项变化来源；`resolvePartyConfig` 校验凯尔必带、最多五人、成员开放和共鸣。只读调用不抽 RNG、不改奖励记录。

两件装备在本次 D1 采用“全部原生空面”改写口径，见规则记录第 11 节 R07；不新增 faceId 选面输入。无空面的凯尔和玛返回不适用，装备不唤醒、不改点数／花色／品质；同一通用槽只能装备一件。实际获取和装卸事务留 D5。

### 4.2 Lv.1–3 必须覆盖的变化

| 角色 | Lv.2 | Lv.3 |
| --- | --- | --- |
| 尤斯缇丝 | 醒 6、金 5 | 同花铭约伤害 2–4 |
| 艾洛拉 | 醒 4、金 3 | 治疗 1–2 名各 1，净化最低血者一项负面 |
| 柯萝萝 | 醒 3、金 5 | 1–2 名各受 3 伤 |
| 诺玛 | 醒 3、金 4 | 2–3 刀，每刀 1 伤 |
| 玛丽埃塔 | 醒 5、金 2 | 现行重排阶段可解析；实际策略在 D5 完成 |
| 凯尔 | 无个人好感等级 | 任意两名成长角色 Lv.3 后，面 4 素→金一次 |

Lv.3 不套 Lv.4 全醒。凯尔护卫品质变金不使强度额外 +1；可除锈面也不因此除锈。阶段切换替换初铭，不同时执行初铭和现行。玛阶段标识可供内部配置查询，但生产能力未实现时不得显示“可执行完整铭约”。

### 4.3 状态分区与恢复单位

| 状态 | 唯一所有者 | 生命周期 |
| --- | --- | --- |
| 成长领取、装备归属、篇章解锁 | Campaign | 跨趟，应用命令提交 |
| 冻结队伍配置、残血、临时锈、散金、下一层归队标记 | Expedition/run | 本趟；当前回忆以后使用自己的局部状态 |
| 当前房间、遭遇实例身份与结果 | Room／Encounter | 同层多场各自独立 |
| 存活敌阵位、意图和执行队列、缠线／挣脱 | Encounter | 本场；队列与阵位不同字段 |
| 已掷面、已用／固定、定身、格挡、成牌快照 | Round | 本回合；新回合清理按定义执行 |
| 已结算手牌与铭约结果、执行游标 | Round 的收束记录 | 保存／恢复不重新抽数、不重发效果 |

Campaign 的 `activeRunRef` 标识唯一活动 run，远征与回忆互斥；D1 只执行当下规则夹具，memory 操作尚不开放。不要为了“预留”而接受未经实现校验的任意 memory payload。

## 5. 规则细则的实施推荐稿

本节承接 R01–R06，给下一次实现提供具体输入；不是新增一轮世界观或成长范围争论。下表口径尚需在对应实现前写回[规则讨论单](../design/DEMO_CHARACTER_RULES_REVIEW.md)，其中已由上位规格确定的部分继续优先。

### 5.1 行动、成牌、铭约资格

- 行动：玩家回合、骰主存活、已掷、已固定、未用、未封锁，且存在合法动作。沉眠不阻止动作；空面没有原生动作。
- 成牌：骰主存活、已掷、未封锁、命数醒。固定、已使用、动作为空不排除成牌。
- 铭约：持约者在收束快照中存活、未封锁且已持有对应阶段；不要求其骰面贡献最高牌型。触发集合一次冻结，艾后续净化不补触发本次原来不合格的持约者。
- 最后敌人被玩家动作击杀后，推荐立即锁住额外玩家输入，沿唯一结束回合路径结算手牌和已触发的铭约；允许已触发治疗正常收尾，不开放额外掷骰、道具或手动治疗窗口。

“立即收束”必须由 core 的合法命令校验保证，不能仅靠 client 稍后自动发 end-turn，留下异步空档可继续操作。

### 5.2 牌型、万能与宽判

推荐首发加入四个自然同色面的同花，暂取基础 +0.6 做验证；同花顺不进入 D1 首轮实现。点数牌型保留既有基础表作为起点。数值与范围在 R02 写回后才进入正式内容；旧规则表原封保留。

候选先比基础加成，再比最终贡献面的品质修正，再按固定牌型优先表、已解析点数组、固定花色顺序、开战队伍槽位和面位稳定破平。品质只计算贡献者；加成不低于 0。五枚同色时同花选四个最优贡献者。

成牌求解返回明确的万能代点与全部有效骰快照，即使最终胜出的是同花。凯尔最多枚举六种代点；该值锁定后，所有铭约用同一个值。诺的行动万能不进入点数枚举。成牌求解不使用 RNG，也不以触发更多铭约为隐藏破平标准。

品相将经济加成抵到 0 时也保留快照和图案结果；倍率没有增加不等于铭约不触发，不能沿用旧 closingHand 为空就跳过新铭约的判断。

最高牌型用于经济；铭约独立从同一快照检测：

- 两对宽判：两组不同对子，或四条／快艇；葫芦自然满足。
- 三条宽判：至少三个同点。
- 小顺：存在四个连续点，大顺包含小顺。
- 同花：至少四个自然同色有效面，不靠万能改变花色。
- 诺的额外空面条件：推荐取存活、未封锁骰主的当前战面；允许沉眠空面；被装备改写后不再是空面。
- 玛葫芦是否包含四条加单张／快艇保留 R03 的提案状态，随 D5 完整重排卡收口，不成为四约的虚假依赖。

至少覆盖 `1112`、`1122`、`11122`、`1111`、`11112`、`11111`，以及四有效面加沉眠空面的情况。

### 5.3 动作与击杀

| 动作 | 实施口径 | 关键例子 |
| --- | --- | --- |
| 三向万能 | 命令明确 action choice；合法目标由 core 给出 | 同一诺 .01 可攻／挡／治，成牌仍为 1 |
| 凯尔护卫 | 面 .04 自护 2、护他人 3 | 不把舍身 +1 泛化到招架或万能面；以当前正式 36 面表为准 |
| 昂贵治疗 | 治 2；扣 `min(本层散金, 10)`；余额不足仍可治疗 | 散金 3、入袋 100，只扣 3；无合法治疗则不花钱、不耗骰 |
| 左右顺劈 | 命令合法时锁定主目标和当时相邻存活 ID，先主后邻 | B 死亡后仍击中原 C；最右目标右劈只打主目标 |
| 提线 | 当前 HP 门槛；严格低于半血才用重伤档；上限 6 | 玛 maxHP 3，敌 6/12 不可提，6/13 可提；重伤 7/20 不可提 |
| 定身／缠线／挣脱 | 定身本轮且保留蓄力；缠线到消费或实例结束；挣脱本场 | 被定身意图跳过后仍推进游标；再次提线仍可挂线，不再次取消行动 |
| 绞杀 | 有线命中时 4+2，并消费该目标的线 | 被拒绝不耗线；合法命中后即消费，不以实际扣 HP>0 为前提 |
| 红线迷宫 | 对当前每条存活敌人攻击意图各加 2 格挡 | 两敌各攻 3，预览均剩 1；不是给全队一个通用盾 2 |

伤害、死亡、清除相关状态、取消意图、赏金归因共用一个结算路径。先读取修正后的实际伤害和 HP 转变，再决定击杀结果；同一敌人只能产生一次击杀奖励。主目标、顺劈波及、绞杀及铭约不各写一套奖励逻辑。

正式 P10 金额尚未冻结时，测试注入明确奖励策略，验证归因与一次性；不把旧 `maxHP × 10 × 层倍率` 静默定为庄园赏金。

### 5.4 四约初铭与现行

阶段效果沿已定表，以下自动目标／随机顺序是具体推荐：

| 约 | 初铭目标 | 现行扩展及边界 |
| --- | --- | --- |
| 尤 | 当前修正后、扣格挡前最高单条攻击威胁；同值按敌阵位；无攻击则最低 HP | 均匀抽伤害 2–4；没有目标不抽 |
| 柯 | 可被本次 3 伤击杀者中 HP 最大，之后威胁、阵位；都不能击杀则最低 HP | 均匀抽数量 1–2；每次读取剩余合法敌人，目标互异；不足不补、不加入 Lv.5 溢伤 |
| 诺 | 每刀从当前存活敌人均匀随机，允许重复 | 初铭 1–2、现行 2–3 刀；先抽刀数，逐刀抽目标，死亡后重新取候选；目标清空即停 |
| 艾 | 受伤且存活友方按当前 HP 升序，平局按固定队伍槽位 | 均匀抽数量 1–2，治疗互异目标各 1；不足不重复治疗 |

艾现行净化需独立实现，不能随着“无可治疗目标”一起提前 return。推荐在艾这条约开始时锁定最低当前 HP 的存活友方，治疗后净化该人的一项允许清除的负面；满血但有允许负面时仍可净化。最低者无可清除项则空过，不暗中跳到别人。

净化采用明确允许表：首轮验证包含当前封锁及其对应状态投影；不清沉眠、永久锈、可除锈、临时退化或敌方挣脱。以后道具新增负面时由 P07 补清除优先级。最低血排序时点、允许名单和这一空过策略需写回 R06，不能在 D3 圣水里再定义一份冲突语义。

执行顺序暂沿尤→柯→诺→艾。集合读取收束快照，目标读取前一效果完成后的战局。每约一次、阶段互斥、派生不递归；combat RNG 随提交保存，拒绝／回放不得多抽。

抽取统一约定：相应效果没有任何合法目标时不抽；有目标再抽数量／强度。艾只有净化可执行而没有治疗目标时不抽治疗人数，净化仍继续；诺的剩余刀遇到全灭立即结束，不再抽空目标。随机范围和抽取顺序作为规则语义纳入恢复测试。

推荐一次 end-turn 提交完整的“手牌收益＋四约结果＋敌方待执行队列”，内部依次结算，无需为每刀增加数据库往返。队列在收束入口基于已公布意图冻结，执行时跳过已死亡或定身者；之后新增的阵位重排不能暗中改变这份顺序。敌方现有恢复节奏仍保留。事务失败全部不生效；提交后演出逐条消费事件，刷新不重放收益。

### 5.5 归队、退化与共鸣

推荐保留“下一场 1 HP”和“雨夜下一层至少 2 HP”两条边界：同层第二战按基础 1 HP；进入下一层再消费雨夜标记，不降低已经恢复的更高 HP。归队夹在新 encounter 创建与首回合意图生成之间；当场复活道具另由 D3 定义。

临时退化推荐沿有效品质“素先于金、同品质面位升序”选第一张未临时退化的面，每次实际力竭一次；已有基础锈或临时锈不重复选，全部不可选则不增加。保存 faceId、来源和 run 生命周期，而不是增加一个无法解释的 rustLevel。保养之后重新显露成长／装备之前的正确底层品质。

雨夜加挡推荐为其他存活成员附加本场“格挡动作 +1”，同一成员不叠层、不追补已施加格挡；不会把角色盾数当作第二份伤害真相。当前六人中有雨夜时玛不在队，暂不存在雨夜与玛全意图格挡叠加的问题。

共鸣资格来自开战冻结队伍：默认勇者四人＋凯尔触发尘世与雨夜；玛替换任一人触发尘世与四席威压；圣辉四票不可达。四席威压在每场第一回合的意图计算生效，不能只在每层第一场触发；尘世的 +10% 作为清层结算输入，D3/P10 决定金额组合和舍入。

### 5.6 重排现在应预留到什么程度

D1 建立 `enemyFormation`（存活敌人 ID 顺序）及合法排列校验：无遗漏、无重复、无陌生或死亡实例。敌人实体按 ID 查；死亡移出阵位，召唤追加右端。顺劈读取这一阵位；UI 后续按相同顺序摆放。

已经生成的执行队列与 cursor 保留原值；阵位变更不改变意图目标、HP 或缠线。在 D1 用内部合法排列夹具验证这些不变量，不开放玩家手动拖拽，不注册无效果的玛铭约。

需要交给 D5 的实际问题是：铭约发生在玩家回合结束，顺劈已经执行完；因此重排的收益主要落在下一玩家回合。推荐排列持续到后续死亡／召唤／再次重排，而不是回合结束立即重置。自动策略必须只使用已知战局，不预读下一次骰点；初铭与现行怎样产生可感知差异仍由机制卡给出。本尊作用侧也保持待设计，不能由“敌方阵位”推导为它一定移动玩家队伍。

## 7. 应用层、页面和 LLM 边界

### 7.1 提交、恢复与导入

- 保留 `expectedHead`、`clientRequestId`、指纹、CAS 和快照／回执同事务。被拒绝的动作不消耗骰、金钱、线或 RNG。
- 当前回合结算、敌方执行游标、冻结配置、阵位、状态、临时锈必须进入 schema 2 和 undo checkpoint 的严格校验；只保存一次权威值。
- 新导入采用显式映射表，覆盖实际存在的 run／room／encounter／敌人实例／状态目标／事实／claim／checkpoint／待结算引用。相同定义 ID 不重命名，运行实例按新档身份映射；导入不重新发成长和装备。
- 导入来源与 adventure／memory 语义分开；D1 验证已实现的当下分支，D5 新增 memory 时补完同样约束。
- `resume`、待发送请求和 scene／run 定位按记录版本处理，不能仍固定 protocolVersion 1。过期 URL 不推进另一场战斗。
- 无动画、跳过动画、保存失败、页面卸载都不能改变战斗真值；已提交终局按原恢复原则继续结算。

### 7.2 页面查询交接

| 查询 | D1 给出的内容 | 消费阶段 |
| --- | --- | --- |
| CharacterRulesView | 六面、来源、等级／下一档、铭约阶段、三槽适用性 | D2 |
| PartyRulesView | 可用角色、队伍冻结配置、主副色票数、共鸣及缺席原因 | D2/D3 |
| BattleRulesView | 当前有效面、成牌资格、合法动作与目标、禁用原因、意图预览 | D3 |
| RoundResolutionView | 万能代点、贡献者、触发集合、效果结果、已提交事件顺序 | D3 表现；D5 加玛重排事件 |

查询按传入 record 的 CatalogRef 和 head 生成；如需缓存，以完整内容引用＋head／冻结配置身份为键。旧档仍读 legacy 查询。不要用全局 `gameContent` 给新档补字段，也不要让 UI 按 verb 自行决定万能面是治疗还是格挡。

D1 可以接最小内部交互夹具来验证命令选择，但不修改既定骰子滚动／归位、庄园红线边框、雾效或布局。正式动作选择的视觉交互留 D3；D2 只读角色配置不依赖其完成。

### 7.3 给后续 LLM 留的接口

事实只由已提交事件映射，记录来源 head、runRef、encounter／room、可见者和撤回关系。D1 可产生铭约实际触发、提线成功、净化结果等已发生事实；不输出 RNG、隐藏队列、未开放内容或猜测分支。

GameFact v2 不自动意味着 AI 请求协议也必须升级为 2。现有本地反应接口在明确适配前可继续只消费支持的事实投影，不把 v2 raw record 强塞入 v1 请求，也不阻塞战斗。

模型不决定目标、成牌、升级、掉落或解锁；rp-style-lab 将来读取投影、编排上下文并返回表现建议。D1 不接真实模型、不建提示词管线，Abyssa 的全部规则验证在无网络环境也能通过。
