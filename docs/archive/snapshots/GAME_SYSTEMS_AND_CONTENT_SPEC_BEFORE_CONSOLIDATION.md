## 1. 项目形态与历史快照

### 1.1 一句话结论

**[已实现，2026-09-07更新]** 项目已有同档案的正式角色、地图出征、持久战斗、一次结算与回馆循环。新档入口尚无初章，现有庄园配平和剧作未达到完整交付标准。

> 工程闭环已建立；从开场认识作品、学会操作，到进入庄园的体验链尚未建立。

### 1.2 核心体验支柱（2026-09-03历史）

结合当前 UI、战斗规则和设计参考，项目的核心体验可归纳为四条：

1. **角色即骰子。** 设计目标是让每名可出征角色的战斗性格由六个战面表达；点数、命数、花色和品相提供第二层构筑。当前共享骰装仍有六名角色为空，尚未达到这一目标。
2. **分诊而非堆数值。** 玩家看到敌方意图后，用攻击、格挡、治疗和偷取处理具体问题。
3. **胜负之外的贪心。** 日常敌人不是“能不能赢”的问题，张力来自打得是否漂亮、要不要继续深入、能带回多少收益。
4. **战斗为日常提供素材。** 伤情、救场、失误、大牌、贪心层数和战利品应该反哺洋馆对话、角色记事与经营选择。

关键断点：

- **[已实现]** 枢纽“出征”目前直接进入 battle.html，绕过地图。
- **[已实现]** 地图没有来自标题页或枢纽的正式入口，也没有统一返回导航；当前只能直接访问 map.html，刷新会重建本页编队状态。
- **[已实现]** 地图会写出击令并跳往 Battle，但 Battle 不读取、校验、消费或清理该出击令。
- **[已实现]** Battle 总是生成固定五人，不使用地图选择的成员或节点。
- **[已实现]** 商店、洋馆、骰局、Battle 各自维护局部余额和库存；刷新或换页不会形成统一经营资产。
- **[已实现]** 战斗终局没有正式“提交结算并返回洋馆”的事务。
- **[占位]** 枢纽顶栏的第 12 天、昏相位、12800 公款、1450 小队资金和 8 晶石是静态样本；洋馆则从第 1 天昼开始。

## 2. 建议确立的完整闭环

### 2.1 大循环

**[拟议]** 建议将主循环定为：

~~~mermaid
flowchart TD
  HOME[洋馆：收产、治伤、修缮、事件] --> SHOP[商店：鉴定、出售、购买]
  SHOP --> LOADOUT[仓库：角色骰装、挂坠、装备、道具]
  LOADOUT --> MAP[地图：选节点、选四人、亲征或托管]
  MAP --> BATTLE[战斗：意图、掷骰、分诊、牌型、深入]
  BATTLE --> SETTLE[结算：资金、素材、遗物、晶石、伤情、耐久、事实]
  SETTLE --> HOME
  HOME --> DICE[码头骰局：有限额的可选资金波动]
  DICE --> HOME
~~~

这条循环的每一步应回答一个明确问题：

| 阶段 | 玩家问题 | 输入 | 输出 |
| --- | --- | --- | --- |
| 洋馆 | 今天先照顾谁、修哪里、收什么？ | 时间、公款、设施、伤员 | 产出、恢复、事件、设施变化 |
| 商店 | 这趟战利品卖掉还是留作构筑？ | 小队资金、晶石、未知物、库存 | 消耗品、装备、鉴定结果、资金 |
| 仓库 | 这次想稳过、赚牌型，还是赌高收益？ | 角色、骰面、挂坠、道具、装备 | 远征 loadout 快照 |
| 地图 | 去哪里、带谁、自己打还是托管？ | 节点、缺勤、编队、时间 | 一次性出击令 |
| 战斗 | 保战面还是追点数？现在撤还是继续？ | 骰池、意图、敌群、loadout | 层收益、伤情、消耗、战斗事实 |
| 结算 | 这一趟真正改变了什么？ | Battle completion | 一次幂等的战役事务 |
| 码头骰局 | 是否用有限风险换一点现金和角色互动？ | 当日限额、小队资金 | 小额盈亏、骰局记事 |

### 2.2 战斗内小循环

**[已实现]** 当前 Battle 已经具备以下核心循环：

~~~mermaid
flowchart LR
  INTENT[公开敌方意图] --> ROLL[初掷]
  ROLL --> KEEP[装载保留]
  KEEP --> REROLL[重掷未装载骰]
  REROLL --> ACT[攻击／格挡／治疗／偷取]
  ACT --> HAND[牌型与品相结算]
  HAND --> ENEMY[敌人逐只行动]
  ENEMY --> CHECK{层是否结束}
  CHECK -->|否| INTENT
  CHECK -->|清层| GREED{离场或深入}
  GREED -->|深入| INTENT
  GREED -->|离场| RESULT[远征结果]
~~~

### 2.3 时间节奏

**[已实现]** 洋馆已有晨、昼、昏、夜四相位，夜后进入次日晨。

**[拟议]** 为闭环接线时，建议采用下列时间成本：

| 行动 | 建议时间成本 | 理由 |
| --- | ---: | --- |
| 浏览档案、仓库配装、普通买卖 | 0 相位 | 避免菜单操作惩罚 |
| 鉴定一批物品 | 0 相位 | 先保持商店流畅；如需限制，用费用而非时间 |
| 亲征一次 | 1 相位 | 让伤情、生产和驻在换班产生节奏 |
| 托管出击一次 | 1 相位后结算 | 不是免费复制收益；凯尔留守且收益较低 |
| 开始一段修缮 | 不立刻跳相位；施工需 1 相位 | 与当前洋馆实现一致 |
| 码头骰局 | 0 相位，但每日限定净投入或局数 | 防止通过无时间成本无限刷钱 |
| 周常大战 | 固定日期触发，不占普通远征次数 | 作为周节奏高潮 |

**[待决策]** “每天允许几次亲征／托管”尚无当前代码规则。设计参考建议亲征每日 1～2 次；首个闭环版本可先允许每相位最多一次出击，由实际节奏测试决定是否收紧。

## 3. 全局战役状态

### 3.1 为什么需要唯一 CampaignState

**[已实现]** 当前各 App 只共享 UI、内容和过场协议，不共享业务状态。
**[拟议]** 闭环需要一份跨页面唯一事实源，负责“现在是第几天、钱和物在哪里、谁受伤、设施几级、哪份结算已经入账”。

建议边界：

- CampaignState 管跨场景、跨局、需要存档的事实。
- BattleState 管一趟战斗内部的确定性状态。
- Shop、Mansion、Map 只通过 Campaign command 读写，不各自复制余额。
- UI 的面板开关、动画阶段、计时器和视觉随机永远不进入 CampaignState。

### 3.2 建议数据轮廓

**[拟议]** 下列轮廓用于确定责任边界，不是要求立即照抄字段名：

~~~ts
type CampaignState = {
  schemaVersion: number
  revision: number

  clock: {
    day: number
    phase: "dawn" | "day" | "dusk" | "night"

  }

  inventory: {
    capacity: number
    stacks: StackEntry[]

  }

  characters: Record<CharacterId, {
    bondLevel: number
    bondProgress: number
    pactStage: number
    availability: null | {
      reason: "injured" | "story-locked"
      availableAtDay: number | null
    }
    diceLoadoutId: string | null

  }>

  mansion: {
    levels: Record<RoomId, number>
    damagedRoomIds: string[]
    repairProgress: Record<RoomId, number>

  }

  sortie: {
~~~

### 3.3 写入规则

**[拟议]**

1. 每个业务动作必须是明确 command，例如购买、收产、开始修缮、创建出击令、提交远征结算。
2. command 成功后 revision 加一；失败不写入任何字段。
3. 跨页面传递的是稳定 ID 和快照版本，不传 React 对象。
4. 远征开战时冻结骰装、装备、特质和遭遇规则快照，内容热更新不能改变正在进行的战斗。
5. 结算使用 settlementId 去重；刷新、返回、重复点击不得二次发奖。
6. inventory、钱包、伤情、耐久和事实必须在同一结算事务内一起提交。
7. 有效出击令只消费一次；消费后进入 activeExpedition，结算成功后清理。
8. 本地首版可以使用带版本迁移的浏览器存档；是否引入后端不属于当前闭环的前置条件。

### 4.2 货币单位

**[已实现]** 当前显示并不统一：

- Battle 使用 G，侧栏又出现 AUREI 文案；
- 商店把数字称作里拉；
- 洋馆按钮称金币；
- 码头骰局使用 G；
- 世界观设定规定 1 金里拉 = 100 银里拉 = 10,000 铜里拉，且 10,000 铜里拉等于 10,000 G。

**[待决策]** 必须确认 UI 中 45、250、2998、12800 等数值究竟是：

1. 最小单位铜里拉／G；
2. 未区分面额的通用“里拉”；
3. 为原型临时写入、之后整体重标。

**[拟议] 推荐**：底层统一存整数最小单位 currencyMinor，界面按场景格式化为 G、铜／银／金里拉；公款和小队资金只是账户不同，不是两种货币。

### 4.3 经济设定中的交易与汇兑

以下来自世界观经济设定，当前 Shop 与 Battle 尚未实现对应汇兑机制：

- 凡界采用“源导贵金属本位”：金属的魔法传导率、净化能力和稳定性本身就是价值基础。
- 赤铜承担日常工资和基层魔导消费；白银能兼容秩序与混沌，是跨阵营核心硬通货；黄金用于王庭级结界与裂隙封印。
- 第三纪元的旧教廷十字币、魔将骨筹和军阀徽记混有阵营源力；第四纪元《里拉度量衡》要求重熔为中性纯金属。
- 官方造币机构对旧币净化和重熔收取 2.5% 火耗费。
- 缇比以龙胃与龙炎把实际重熔损耗压到约 0.5%，向小队收取 2% 一口价汇兑费，并吞食旧币残存魔力。
- 维稳公款来自人类摄政府、商贸同盟和深渊贡赋，受双方审计；小队资金来自遗迹、战利品、旧币与博弈，属于小队自主资产。
- 普通金属货币用于横向配装、耗材和维修；远古晶石用于法则级重铸、暗伤解除与深层成长。

**[拟议]** 若把旧币做成正式战利品，应先作为待汇兑素材进入库存，再由玩家选择官方 2.5% 火耗或缇比 2% 手续费。现有 Battle 的 G 不能在未定币值前自动宣称为已经重熔的里拉。

### 4.4 Battle 层倍率冲突

**[已实现]** 击杀赏金当前先乘一次层倍率，清层入袋时所有散金又乘一次层倍率，因此玩家攻击击杀的主要收益近似含“层倍率平方”。

**[待决策]** 三种可选方案：

| 方案 | 击杀时 | 清层时 | 特点 |
| --- | --- | --- | --- |
| A，推荐 | 最大 HP × 10 | 牌型因子 × 层倍率 | 深度只放大一次，最容易与商店物价配平 |
| B | 最大 HP × 10 × 层倍率 | 只乘牌型因子 | 账本直观，但偷取等散金是否吃深度需另定 |
| C | 保留现状 | 保留现状 | 深层爆炸式增长，必须重做价格与失败损失 |

在该项定稿前，本文后续的“目标经济”只描述流向，不承诺最终绝对数值。

## 5. 地图、委托与编队

### 5.1 地图交互状态

### 5.3 编队规则

**[已实现]**

- 有 4 个玩家可选队员席。
- 亲征会额外加入凯尔作为第五席；托管不加入凯尔。
- 至少选择 1 名队员才可出发。
- 队伍最多 4 名可选成员，不能重复。
- 名单中的角色可以先加入预览；真正出发时才统一校验。
- 出发会拒绝未知节点、未知成员、任何 absence 标记和没有骰装的成员。当前内容只有蕾诺尔的 injury 缺勤，模型同时支持 mood 缺勤。
- 预览聚合攻击、格挡、治疗、其他、空面、醒／眠、四色花色与阵营构成。
- 预览刻意不显示难度星级、胜率或期望值，让玩家自己读取阵容形状。

当前提示逻辑：

- 纯勇者、纯天王和混编会得到不同文字。
- 空面加沉眠面占比不低于 34% 时提示“易手忙脚乱”。
- 该占比不高于 15% 时提示“有效面充足”。
- 逻辑上，同一主色骰达到至少 3 枚时，会优先提示某花色“同花可期”。
- 当前三套非空骰装的主色分别为圣辉、渊影、彼岸，名单又禁止重复角色，因此正式内容暂时无法触发这条提示；只有合成测试阵容能走到该分支。
- 这些提示只按静态骰装估计编队形状，不读取本轮朝上的面；Battle 目前也没有花色规则。

### 5.4 当前实际可出发成员

**[已实现]** 地图名单由九人档案与共享骰装拼成：

- 尤斯缇丝：有完整骰装，可出发。
- 艾比希斯：有完整骰装，可出发。
- 蕾诺尔：有完整骰装，但静态状态签为“轻伤休养 2 天”，会被拒绝。
- 艾洛拉、柯萝萝、诺玛、玛丽埃塔、阿尔薇特、薇薇安：共享骰装为空，会被拒绝。
- 凯尔：不在九人档案中，共享骰装也为空；亲征仍会让 UI 骰数加一，但构成统计中没有他的六面内容。

因此，当前地图虽然有四个席位，真正能通过出发校验的可选成员只有尤斯缇丝和艾比希斯。

### 5.5 出击令

**[已实现]** 地图在出发时向 sessionStorage 写入：

~~~ts
{
  version: 1,
  nodeId,
  memberIds,
  command,   // personal 或 delegate
  diceCount,
  issuedAt
}
~~~

键名为：

~~~text

~~~

**[已实现]** 这份出击令目前只有写入端和页面跳转，形成以下单向交接断点：

- Battle 不读取或验证。
- Battle 不检查订单时效。
- Battle 不区分亲征和托管。
- Battle 不按 memberIds 动态建队。
- Battle 不按 nodeId 选择敌群、背景、掉落或遭遇规则。
- Battle 不在成功开战或结算后清理订单。

**[拟议]** 正式出击令应再带稳定 orderId、campaignRevision、resolvedLoadoutId 或 loadout 快照哈希；Battle 验证后一次性消费，并创建 expeditionId。

| 战面 | 这一面在战斗中做什么、强度多少？ | Battle 已实现攻击／格挡／治疗／偷取／万能／空面 |

### 7.2 花色：身份、编队与同花

原文只记录了四色名称和“Battle 尚未接入”，不足以构成可执行规格。本节把当前数据、当前 UI、长期参考和建议实现规则分开写清。

#### 7.2.1 Canonical 词表与不变量

**[已有底座]** [共享骰面契约](../../../src/shared/domain/dice/face.ts)把花色定义为每个 `DieFace` 的必填字段，正式枚举只有四个。角色档案页采用语义色加几何形状双编码：

| Canonical ID | 中文名 | 世界观出身 | 共享形状 | 档案语义色 |
| --- | --- | --- | --- | --- |
| `holy` | 圣辉 | 天穹、诸神、圣力与教会 | 菱形 `diamond` | 金 `#d8bd7d` |
| `earth` | 尘世 | 大地、凡人与市集 | 方形 `square` | 绿 `#7fb193` |
| `abyss` | 渊影 | 深渊、魔力与混沌 | 三角 `triangle` | 绯 `#bf6070` |
| `beyond` | 彼岸 | 生死之外、亡灵与契约 | 圆形 `circle` | 紫 `#9d87cd` |

必须保持的语义边界：

- 花色属于**当前朝上的具体骰面**，不是只属于整枚骰；`primarySuit` 和 `secondarySuit` 只是六面分布的摘要。
- 标准角色骰的目标约束是主色 4 面、副色 2 面，主副色不同；当前内容测试已对非空骰装强制该约束。
- 花色表达出身和队伍关系，不表达稀有度、品相、阵营、伤害属性或克制关系；四色不分高低。
- 花色与战面、点数、醒眠和品相正交。同一面是圣辉还是渊影，不会直接改变攻击、格挡、治疗或偷取强度。
- 花色是不可成长、不可重铸的身份轴。角色成长可改变命数醒眠或品相，装备可改写战面，但普通效果不应把圣辉改成渊影。
- 颜色不能单独承担信息。所有正式界面至少同时给出形状；检视和辅助文本还应给出中文名。

档案语义色只在骰装组件中统一。地图的骰面主题色来自阵营，Battle 的骰面主题色来自角色，两者都不能当作花色判定依据；规则只能读取枚举字段。

#### 7.2.2 当前已有花色内容

**[已实现]**（档案与地图静态内容）目前只有三套非空骰装：

| 角色 | 主色 | 副色 | 六面分布 | Battle 是否读取 |
| --- | --- | --- | --- | --- |
| 蕾诺尔 | 彼岸 | 尘世 | 4／2 | 否；不在固定 Battle 队伍 |
| 艾比希斯 | 渊影 | 彼岸 | 4／2 | 否；不在固定 Battle 队伍 |
| 尤斯缇丝 | 圣辉 | 尘世 | 4／2 | 否；Battle 使用另一套骰面 |
| 其余六名档案角色 | — | — | 空骰装 | 否 |
| 凯尔 | — | — | 共享档案中没有骰装 | 否 |

**[已实现]**（仅表现）固定 Battle 队伍另有一份硬编码的整骰花色标签：凯尔和尤斯缇丝为圣辉，艾洛拉和诺玛为尘世，柯萝萝为渊影。`ExpeditionDie3D` 据此让一颗骰子的六面共用菱形、方形或三角角标；固定队伍没有彼岸标签。

这份表现数据有三个限制：

1. 它没有进入 `FaceDef`、`DieState`、`HandEvaluation`、事件或存档。
2. 它只能表达“一整颗骰一种形状”，不能表达尤斯缇丝真实档案中的圣辉 4／尘世 2。
3. 角色颜色是独立的 `themeColor`；同为圣辉的凯尔和尤斯缇丝也使用不同主题色。因此不能写成“Battle 按花色给整骰着色”。

#### 7.2.3 地图如何预览花色

**[已实现]** 地图编队页已经能读取共享骰装并计算：

- 四色各自在全队骰装中占多少个定义面；这里会统计沉眠面和空面，因为它展示的是静态构筑，不是一次掷骰结果。
- 有多少枚角色骰以某色为主色；显式 `primarySuit` 优先，缺失时才按六面众数推断。
- 优势花色先比较主色骰数量，再比较该色总面数；仍并列时按圣辉、尘世、渊影、彼岸的固定顺序取先者。
- 优势花色达到至少 3 枚主色骰时，赌法摘要优先显示“某色 N 骰同色，同花可期”（N 为实际主色骰数），覆盖空面／沉眠风险提示。

这只是编队层的倾向性提示，不是同花概率和战斗判定。当前三套完整骰装的主色互不相同，角色又不能重复入队，所以正式内容实际上无法触发“同花可期”；现有测试通过合成三枚同主色骰验证了该逻辑。

**[未实现]** 出击令虽保存版本、节点、成员 ID、亲征／托管模式、骰数和签发时间，却不保存逐面花色或解析后的骰装；Battle 也不读取地图的花色构成。

#### 7.2.4 花色在玩法中的职责

**[拟议]** [战斗设计参考日志](../battle/DESIGN_REFERENCE_LOG.md)已经给出应保留的方向，但尚未进入当前规则：

- 远征牌型在点数牌型之外增加同花和同花顺。
- 同花要求至少 4 个自然同色的有效朝上面。
- 花色不参与攻击、防御、治疗、命中、敌人弱点或属性克制；它只服务于成牌收益和编队策略。
- 每面花色由角色出身决定，万能点只能替代点数，不能任意改成另一花色。
- 花色把“带谁出征”连接到收益层：伤员缺勤不仅减少一种战面，也可能切断某套同花阵容。

因此，四种花色不应各自附带“圣辉加治疗”“渊影加攻击”之类的常驻效果。角色差异来自六面动作、私约和装备；花色只决定哪些人更容易共同组成同花。

#### 7.2.5 推荐的正式判定契约

以下是把长期方向补成可实现规则的**[拟议]** 方案，不是当前 Battle 行为。

结束玩家回合时，系统与点数牌型共用一份有效骰集合。某骰只有同时满足下列条件才提供花色：

1. 本轮已有朝上面；
2. 未被封锁；
3. 骰主未力竭；
4. 该面的 `fate` 为 `awake`；
5. 花色来自开战时冻结的 `ResolvedDieFace.suit`。

`asleep` 只表示该面的命数刻痕不进入点数／花色牌型，不表示这一面不能被掷出或不能执行其攻击、格挡、治疗等战面。是否装载、是否已用于行动、战面是否为空都不影响已醒面的成牌；每名角色每轮最多贡献当前朝上的一个面。`wildPip` 可在点数识别阶段替代 1～6，但它的花色仍是该面原生花色，不能作为花色万能牌。

建议加入两种候选牌型：

| 牌型 | 推荐条件 | 推荐基础加成 | 贡献面 |
| --- | --- | ---: | --- |
| 同花 | 至少 4 个有效面具有同一自然花色 | +0.6 | 枚举同色四面组合，取品相最优的一组 |
| 同花顺 | 5 个有效面同一自然花色，且点数可组成 1–5 或 2–6 | +2.4 | 构成连续点数的五面 |

这两个数值是首轮平衡基线：同花位于当前小顺 `+0.5` 与葫芦 `+0.8` 之间；五骰同花顺高于快艇 `+2.0`。正式数值仍需模拟和试玩确认。

同花候选与当前点数候选使用同一套选择规则：

~~~text
收集有效朝上面
  → 枚举点数牌型候选
  → 枚举四色同花候选
  → 枚举五骰同花顺候选
  → 先取基础加成最高者
  → 基础加成相同，取贡献面品相修正更高者
  → 仍相同，按固定候选排序键决胜
  → 只结算一个最大牌型，不与较低牌型叠加
~~~

固定候选排序键依次为：基础加成降序、品相修正降序、牌型固定优先级（同花顺→快艇→大顺→四条→葫芦→同花→小顺→三条→两对→一对→散牌）、已解析点数元组降序、花色顺序圣辉／尘世／渊影／彼岸、贡献者在 `BattleStartInput.party.resolvedDice` 冻结数组中的槽位升序、面号升序。非花色牌型跳过花色键。不得使用当前 React 渲染顺序、对象遍历顺序或本地化名称决胜。

品相仍只计算最终贡献面：金铭每面 `+0.1`，素铭 `0`，锈铭 `−0.1`，结果最低为 `0`。五枚同色但未成顺时会生成一个四贡献面的同花候选；只有该候选最终胜出时，才从五面中选择品相最优、稳定排序最前的四面。若同一组骰同时构成快艇、四条或葫芦等基础加成更高的点数牌型，仍结算更高牌型，不会强制降为同花。

同花的单轮实际加成与其他牌型一样写入本层累计 `H`，清层时进入“散金 × (1 + H) × 层倍率”，入袋后归零。它不直接制造金币，也不改变击杀赏金。

按地图编队规则，亲征为最多四名成员再加凯尔，合计最多五枚骰，可以形成同花和同花顺；托管不带凯尔，只有所选的最多四枚成员骰，满四人时才可能形成同花，无法形成本方案中的五骰同花顺。Battle 当前尚未读取这两种订单。这与凯尔作为亲征第五骰、提高大牌上限的定位一致。

#### 7.2.6 私约、羁绊与经营消费

花色牌型接通后，会成为多个系统的事件源：

| 消费者 | 当前内容 | 正式接线要求 |
| --- | --- | --- |
| 尤斯缇丝私约“王权领域” | 档案写“同花成型时，全队本回合格挡值 +1” | 监听一次 `hand-evaluated`；必须先定义“全队格挡 +1”如何投影到当前按敌方意图保存的格挡模型 |
| 成名牌型 | 长期参考指定尤斯缇丝认领同花 | 羁绊升级只提高该牌型收益，不修改掷面概率或花色 |
| 薇薇安“账单” | 长期参考有“出同花五折”阶段 | 只在薇薇安参战且该条款已解锁时消费同花事实 |
| 战斗高光 | 长期参考包含“首次同花顺” | completion 输出结构化 highlight／fact，结算幂等写入记事与餐桌话题 |
| 伤情与轮换 | 当前只有静态缺勤和拟议伤情 | 缺勤自然改变可用主色组合，不另加隐藏惩罚 |
| 商店与挂坠 | 当前没有改花色商品 | 允许奖励某牌型或修复醒眠／品相，不出售永久“洗花色”效果 |

同一个牌型事件只能触发每条私约一次；撤回到结束回合之前时，牌型加成、私约效果和事实必须作为同一事务一起撤销。

#### 7.2.7 UI、事件与存档要求

**[拟议]** 正式接线应做到：

- 档案继续逐面显示中文花色、语义色和形状，并显示主 4／副 2 总览。
- 地图继续显示静态花色构成，但把“同花可期”明确写成构筑倾向，不显示伪精确概率。
- Battle 改为从每个解析面读取形状；不能再让整颗骰六面共用 `PARTY_VISUALS.suit`。尤斯缇丝掷到尘世副色面时应显示方形，而不是菱形。
- 当前牌型条同时显示牌名和花色，例如“圣辉同花 +0.6”；贡献面同时点亮点数和花色角标。
- 不能只靠红、绿、金、紫区分；屏幕阅读文本应包含“圣辉／尘世／渊影／彼岸”。
- `BattleStartInput` 的每个 resolved face 必须带非空 suit；旧存档若无法从冻结的内容版本补全，应拒绝继续并给出迁移说明，不能把 `null` 当第五种花色。
- `HandEvaluation`／`hand-evaluated` 保留当前已有的 `contributors`，并增加 `kind`、`suit` 和最终贡献面号；这些字段参与 Battle 存档和重放。
- completion 只输出需要跨局保存的首次、高额或私约相关花色高光，不必把每回合普通同花写进 Campaign。

建议的最小事件载荷：

~~~ts
type SuitHandMetadata = {
  kind: "flush" | "straight-flush"
  suit: "holy" | "earth" | "abyss" | "beyond"
  contributorIds: string[]
  contributorFaceNumbers: Array<1 | 2 | 3 | 4 | 5 | 6>
  baseBonus: number
  qualityModifier: number
  adjustedBonus: number
}
~~~

外部内容、开战契约、事件与存档统一使用 `faceNumber: 1..6`；当前 Battle 内部 `DieState.faceIndex` 的 `0..5` 只保留为 legacy 数组下标。入口／迁移适配器负责唯一一次 `faceNumber = faceIndex + 1` 转换，领域事件不得同时暴露两种基数。

#### 7.2.8 花色验收案例

实现花色后至少验证：

1. 四枚已醒、未封锁、未力竭的圣辉面构成同花。
2. 三枚圣辉加一枚尘世不构成同花。
3. 已行动、空战面或未装载的骰，只要命数有效仍可贡献花色。
4. 沉眠、封锁和力竭骰均不贡献花色。
5. 凯尔万能点可以补同花顺的点数，但不能改变自己的自然花色。
6. 沉眠面仍可按其战面掷出并行动，只是不贡献点数和花色。
7. 五枚同色但未成同花顺时会生成四贡献面的同花候选；同花最终胜出时才选五个中的四个品相最优者。
8. 五枚同色且五枚同点时，快艇 `+2.0` 仍压过同花 `+0.6`；四条和葫芦同理按基础加成比较。
9. 五枚同色且点数为 1–5／2–6 时升级为同花顺。
10. 同时满足同花与较低点数牌型时只结算较高基础加成，不叠加。
11. 尤斯缇丝的尘世副色面在档案、地图、Battle 和存档中保持同一个 `earth`。
12. 相同 seed、骰装快照和命令序列在保存恢复后得到同一花色牌型、贡献者和收益。
13. 五枚同色、同品相且只有四面参与同花时，按开战快照槽位稳定选择相同四人。
14. 外部面号 1–6 与 legacy 内部下标 0–5 往返转换没有 off-by-one。
15. 撤回结束回合同时撤回花色倍率、私约反应与高光事实。

**[待决策]** 同花 `+0.6` 和同花顺 `+2.4` 是本文推荐值；尤斯缇丝“全队格挡 +1”的精确投影仍需拍板。如果首个 MVP 决定暂缓花色牌型，就必须同步隐藏地图“同花可期”和所有同花私约效果，避免 UI 继续承诺不存在的收益。本文更推荐首个可信闭环至少接入四面同花，把五骰同花顺与成名牌型成长放到下一阶段。

### 7.3 命数与品相冲突

共享档案模型：

- 醒面进入牌型；
- 沉眠面不进入点数／花色牌型，但共享契约没有禁止它被掷出或执行战面；
- 没有锈铭、素铭、金铭、无铭四档字段。

Battle 模型：

- none、rust、plain、gild 四档；
- rust 为成牌 −0.1，gild 为成牌 +0.1；
- 当前 none 修正为 0，但仍然进入牌型；
- 没有醒／眠字段。

**[待决策] 推荐拆分**：

~~~text
fate: asleep | awake
quality: plain | rust | gild
~~~

判定顺序：

1. asleep 直接不进入牌型识别；
2. awake 才读取点数和花色；
3. 成为最终牌型贡献者后，再读取 quality 修正；
4. 伤势产生的临时锈蚀不能覆盖永久骰装定义，二者分开保存。

这样“能不能成牌”和“成牌值不值钱”不会继续混成一个枚举。

### 7.4 挂坠槽

**[已有底座]** 完整骰装页定义 3 个可见挂坠位；六名空骰装角色直接显示“未编入远征”，不渲染挂坠位。挂坠分为：

- 战面改写：改变动作或强度；
- 命数修正：改变醒眠、品相或特定成牌奖励。

**[拟议]** 延续设计参考的护栏：

- 每人最多 3 件挂坠；
- 战面改写最多 2 件；
- 命数修正最多 2 件；
- 点数底盘固定为 1–6，不允许装备直接改点数分布；
- 战前装配、战中静态；
- 所有改写在开战时解析成 resolved dice 快照。

| 2 | 治疗 | 1 | 已醒 | 尘世 | 回复 1 心 |

## 8. 裂隙远征：当前可玩规则

### 8.1 定位与初始条件

**[已实现]** Battle 是一个在给定初始状态、seed 和命令序列后可确定重放、事件驱动、可序列化的小规模回合制系统。当前玩家实际进入的是固定内容：

- 地点：混沌领域；
- 队伍：凯尔、尤斯缇丝、艾洛拉、柯萝萝、诺玛；
- 每人最大生命 3，开局满血、0 盾、0 新增锈蚀；
- 每人一枚专属六面骰；
- 最多 5 层；
- 每回合 1 次初掷和 2 次重掷；
- 无等级、经验、法力、行动点、前后排或属性克制；
- UI Controller 总是传入空道具、空装备、空特质 loadout。

正常 UI 首次挂载仍会通过 `Math.random` 生成一次初始 seed；确定性是指该 seed 一旦确定后，规则随机、存档恢复和命令重放可复现，并非每次点击“再来一局”都得到同一局。

核心决策有三层：

1. 战面是否足以处理已公开的威胁；
2. 要保留行动结果，还是重掷追逐点数牌型；
3. 清层后带宝离场，还是带着伤势和包裹继续深入。

### 8.2 状态机

**[已实现]**

~~~text
创建远征
  → 进入层级、生成敌群、公开第一轮意图
  → awaiting-roll
      → 初掷
  → player-turn
      → 装载／卸载
      → 重掷
      → 攻击／格挡／治疗／偷取
      → 结束回合
  → enemy-turn
      → 计算并累计本轮牌型
      → 检查残局反拖延
      → 冻结本轮敌方行动队列
      → 敌人逐只执行意图
      → 狂暴敌人自伤
      → 判定
          ├─ 敌人仍存活：下一回合
          ├─ 清层且未到第 5 层：greed
          ├─ 清完第 5 层：finished
          └─ 全员力竭：finished

greed
  ├─ 再深一层：新层
  └─ 带宝离场：finished
~~~

补充：

- 每层第一轮在掷骰前就公开敌方意图。
- 玩家可以在还有可用骰时主动结束回合。
- 战斗中途不能任意撤离，只能在清层后的 greed 阶段离场。
- 最后一只敌人被玩家击杀时，其意图立即取消；UI 完成退场演出后自动结算本轮牌型和层收益。
- 第 5 层清完自动完成远征。
- 终局“再来一局”会创建全新的本地远征，地图选择、局外伤势和奖励不会保留。

### 8.3 初掷、装载和重掷

#### 初掷

**[已实现]**

- 只掷未封锁且未力竭角色的骰子。
- 初掷不消耗重掷次数。
- 完成后进入 player-turn。

#### 装载

**[已实现]** 点击骰子切换装载／卸载：

- 装载骰不会参加后续重掷；
- 只有装载骰可以执行其当前战面；
- 空面也可装载，以保留其点数；
- 已行动、封锁或力竭骰不能切换；
- 每次装载或卸载都会建立一个可撤回 checkpoint。

#### 重掷

**[已实现]**

- 每回合最多 2 次。
- 每次同时重掷所有未装载、未封锁、未力竭、未消耗的骰子。
- 已装载结果保持不变。
- 第二次重掷后，本次参与重掷的骰子自动装载。
- 没有合法骰时不能重掷。
- 重掷会清空此前的撤回栈。

### 8.4 玩家行动

**[已实现]** 每枚骰每回合最多行动一次。行动后标记为 spent，但点数仍参与本轮牌型。

| 行动 | 合法战面 | 合法目标 | 效果 |
| --- | --- | --- | --- |
| 攻击 | attack、wild | 任一存活敌人 | 造成等于强度的伤害 |
| 格挡 | guard、wild | 一条公开攻击意图 | 为该敌人的该次攻击增加抵消量 |
| 治疗 | heal | 未力竭、未满血友方；可治疗自己 | 回复强度点生命，上限 3 |
| 顺手牵羊 | coin | 任一存活敌人 | 当前层散金增加 5 × 强度 |
| 空面 | blank | 无 | 不能行动，但其点数照常成牌 |

规则细节：

- 攻击造成致死伤害时，敌人 HP 立即归零、意图取消，并发放击杀赏金。
- 格挡不是全队公共护盾，只抵消被指定敌人的那一条攻击。
- 多枚格挡骰可以叠在同一意图上。
- 角色卡盾值是本轮保护该角色的汇总展示；实际结算仍按每个敌人的 blocked 独立计算。
- 直接点击攻击意图可精确格挡该敌人。
- 用格挡骰点击队友时，UI 会在所有瞄准该队友的攻击中，自动选择剩余伤害最高的一条。
- 治疗不能复活本层已经力竭的人。
- 凯尔的 wild 当前只能作为攻击或格挡，不能代替治疗或偷取。
- 成功行动及其资源、事实、状态或未来 reaction 属于同一撤回单位。

### 8.6 生命、力竭与远征内锈蚀

#### 力竭

**[已实现]** 角色 HP 归零后：

- 标记力竭；
- 清空盾值和待封锁状态；
- 当前骰卸载；
- 本层剩余时间不能行动；
- 不再参与牌型；
- 新增 1 级远征内锈蚀，直到所有可锈面耗尽；
- 若继续深入，下一层以 1／3 HP 归队。

没有力竭但残血的角色进入下一层时不会回血。

#### 锈蚀顺序

**[已实现]** 锈蚀不改点数、动作或强度，只把有效品相变为 rust。普通面先锈，金铭最后锈。

| 角色 | 每次力竭新增锈面的顺序 |
| --- | --- |
| 凯尔 | 1 → 2 → 3 → 4 → 5 → 6 |
| 尤斯缇丝 | 1 → 2 → 3 → 5 → 6 → 4 |
| 艾洛拉 | 1 → 2 → 3 → 4 → 6 → 5 |
| 柯萝萝 | 1 → 2 → 4 → 5 → 6 → 3 |
| 诺玛 | 1 → 3 → 4 → 5 → 6；第 2 面原本就是锈铭 |

新增锈蚀当前只存在于本次 BattleState；“再来一局”后重置。

**[拟议]** 闭环中应区分：

- baseQuality：角色成长与装备决定的永久品相；
- expeditionRust：本趟受伤产生的临时覆盖；
- injuryDays：离场后进入 Campaign 的缺勤；
- 不建议一次普通力竭永久破坏已培养骰面。

### 8.8 五类敌人和意图

**[已实现]** 所有意图在玩家掷骰前公开。

| 类型 | 当前意图 | 精确行为 |
| --- | --- | --- |
| brute 蛮兽 | 攻击 | 随机锁定一名未力竭角色，造成 attack 点伤害 |
| charger 蓄力兽 | 蓄力／重击 | 未蓄力时整轮蓄力；下一轮随机锁定并重击；执行后清空蓄力 |
| anomaly 异象 | 封锁 | 随机指定一名未力竭角色，使其下一回合骰子不可掷、不可行动、不可成牌 |
| trap 陷阱 | 倒计时 | 陷阱自己执行该意图时倒计时 −1；归零时自毁并损失散金 |
| summoner 召唤者 | 召唤 | 存活敌人少于 5 时生成一只 2 HP、攻 1 新生畸变物 |

#### 攻击结算

~~~text
实际伤害 = max(0, 意图伤害 − 该意图累计格挡)
~~~

- 完全减到 0 时显示 BLOCK。
- 多名敌人可以瞄准同一角色。
- 目标在该轮意图公开时固定。
- 若目标先被前一个敌人击倒，后续瞄准同一目标的攻击 MISS，不重新选人。
- 敌方队列在玩家结束回合后，按当时存活且有意图的数组顺序冻结。
- 玩家阶段击杀会立即清除意图，因此该敌人在结束回合时不会进入冻结队列。

#### 封锁

- 意图执行时才把 sealedNext 写入目标；
- 目标若先力竭，封锁落空；
- 下一回合创建骰子时应用；
- 被封骰该回合没有点数，之后自动恢复。

#### 陷阱爆炸

~~~text
名义损失 = max(10, round(当前层散金 × 20%))
实际散金最低为 0
~~~

- 陷阱自毁，无赏金；
- 只影响本层散金，不碰已入袋包裹；
- 追加“未及时摧毁陷阱”的事实；
- 日志写名义损失；余额不足时实际扣除可能更少。

#### 召唤

- 存活敌人少于 5 才成功；
- 每次生成一只新生畸变物；
- 召唤物不插入已经冻结的本轮队列；
- 下一回合才获得并执行攻击意图。

### 8.9 残局反拖延

**[已实现]** 用于阻止留下弱敌无限偷钱或刷牌型。

必须同时满足：

~~~text
数量已溃散
且剩余总 HP 较低
且公开攻击几乎无威胁
且（当前已有收尾伤害，或连续僵持达到 2 轮）
~~~

精确判据：

- 数量已溃散：存活数不高于 max(1, floor(本层开场敌人数／3))，或只剩 1 只；
- 剩余总 HP 不高于 max(3, 玩家当前潜在攻击伤害)；
- 当前攻击威胁 ×4 不高于队伍当前总 HP；
- 可收尾：当前未封、未倒下、未消耗骰面的攻击／万能强度足以清空总 HP；
- 僵持：连续 2 次结束回合时敌方总 HP 未下降。

结果：

- anomaly、trap、summoner 立即逃跑；
- 每一只逃跑者按顺序拿走当时剩余散金的 round(50%)；
- 逃跑无赏金；
- brute 与 charger 先进入狂暴预警；
- 经过两个完整玩家回合后永久狂暴，攻击 +3；
- 狂暴敌人在每个敌方阶段结束后自伤 1；
- 狂暴自毁无赏金；狂暴不可净化，当前也没有玩家解除手段。底层显式 remove-status 原语仍能移除状态。

- 尚未装载；
- 已经用于行动；
- 战面为空；
- 本轮没有选它行动。

| 8 | 一对 | 两枚同点 | +0.1 |
| 9 | 散牌 | 无以上组合 | 0 |

#### 凯尔万能点

**[已实现]**

- 静谧之楔是凯尔实际的 6 点面；
- 识别牌型时穷举它作为 1–6 的所有可能；
- 先选基础加成最高的牌型；
- 基础加成相同时，选品相修正更高的贡献组合。

#### 品相

| Battle 品相 | 每个最终贡献面 |
| --- | ---: |
| gild 金铭 | +0.1 |
| plain 素铭 | 0 |
| rust 锈铭 | −0.1 |
| none 无铭 | 当前 0，且仍可参与识别 |

~~~text
若为散牌：
  单轮实际加成 = 0

否则：
  单轮实际加成 =
    max(0, round2(牌型基础加成 + 最终贡献面的品相修正总和))
~~~

若同一点数有多枚候选，而牌型只需要其中一部分，当前算法优先选品相修正更高的骰面。

#### 层内累计

~~~text
本层累计牌型加成 H =
  round2(旧 H + 本轮实际加成)
~~~

H 可跨本层多个回合累计；清层入袋后归零，不带到下一层。

#### 当前不存在的牌型

**[未实现]** 当前引擎没有同花、同花顺、角色成名牌型加成，也没有任何私约牌型触发。地图的“同花可期”只是静态构筑提示，而且以现有正式骰装还无法触发。目标判定、倍率、事件、UI 与验收契约见第 7.2 节。

### 8.11 散金、赏金与入袋

#### 散金来源

玩家攻击击杀赏金：

~~~text
赏金 = round(敌人最大 HP × 10 × 当前层倍率)
~~~

| 层 | 当前常见赏金 |
| ---: | --- |
| 1 | 2 HP = 20G；3 HP = 30G |
| 2 | 2 HP = 26G；3 HP = 39G |
| 3 | 2 HP = 34G；3 HP = 51G |
| 4 | 2 HP = 44G；3 HP = 66G；4 HP = 88G |
| 5 | 3 HP = 90G；4 HP = 120G；6 HP = 180G |

只有玩家攻击造成的击杀给赏金。陷阱自爆、逃跑、狂暴自毁不给赏金。

诺玛偷取：

~~~text
获得散金 = 5 × coin 面强度
~~~

#### 单层入袋

~~~text
牌型因子 = round2(1 + H)
层因子 = [1.0, 1.3, 1.7, 2.2, 3.0] 中的当前值

本层入袋 =
  round(当前层散金 × 牌型因子 × 层因子)

新包裹 =
  旧包裹 + 本层入袋
~~~

- 最后一轮牌型照常计入；
- 清层后散金和 H 归零；
- 已入袋包裹不再吃后续层倍率；
- 普通敌人、陷阱和逃跑只影响本层散金；
- 全灭才会损失包裹。

**[待决策]** 当前玩家击杀收益在赏金和入袋阶段各乘一次层因子，必须在正式经济平衡前处理，见 4.4 节。

### 8.12 深入、离场、全灭与晶石

#### 清层与深入

**[已实现]**

- 清层后先完成本层入袋；
- 未到第 5 层时展示离场／深入；
- 面板显示力竭人数、残血人数、锈面总数与下一层倍率；
- 深入后，力竭者以 1 HP 归队；
- 其他残血不恢复；
- 远征内锈蚀保留；
- 生成新层敌群与第一轮意图。

#### 正常离场

**[已实现]**

- Battle 终局结果记录各层包裹之和；当前不会跨页增加经营钱包；
- 终局不再追加一个全局倍率；
- 最深层达到 3 后进行一次晶石判定；
- Battle 终局结果每趟最多记录 1 枚；当前不会跨页增加经营晶石。

| 最深层 | 晶石概率 |
| ---: | ---: |
| 1–2 | 0% |
| 3 | 25% |
| 4 | 50% |
| 5 | 75% |

#### 全员力竭

**[已实现]**

- 当前层散金全部丢失；
- 当前层牌型累计归零；
- 已入袋包裹损失 round(50%)；
- 保留包裹扣除损失后的余额；奇数时损失向上取整，例如包裹 101G 会损失 51G、保留 50G；
- 不判定晶石；
- 立即结束远征。

因此当前实现不是“全灭整趟清零”。

### 8.13 战斗事实与日志

**[已实现]** 日志保存层数、回合、语气和文本。UI 倒序显示最近 40 条，完整数组仍在 BattleState 中。

当前可生成的事实包括：

- 诺玛偷藏不明小物；
- 艾洛拉使用昂贵治疗材料；
- 某角色被具体敌人击倒；
- 陷阱炸飞战利品；
- 特殊敌人在残局逃跑；
- 敌人显露狂暴预兆；
- 敌人进入狂暴；
- 狂暴敌人自我崩坏；
- 掷出四条、大顺、快艇等罕见牌型；
- 两回合内零伤清层；
- 全员带伤撤离；
- 撤离时散落半个包裹；
- 从指定深度带回晶石。

相同事实文案会去重。终局弹窗可显示事实，但当前 BattleCompletionOutput 没有把 facts 作为正式跨场景字段提交。

### 8.14 撤回

**[已实现]** 当前玩家行动阶段可撤回：

- 装载／卸载；
- 攻击；
- 格挡；
- 治疗；
- 偷取。

**[已有底座]** 同一个 checkpoint 也能整体撤回行动引起的资源、状态、reaction、道具次数与耐久变化；后三类目前只由底座和测试夹具验证，因为正式 UI 没有可用道具或装备。

checkpoint 包含 HP、敌人、意图、资源、骰子、锈蚀、状态、遭遇规则、loadout、日志、事实、三条 RNG cursor 和事件序号。

限制：

- 仅 player-turn 可撤回；
- 没有 redo；
- 初掷、重掷、结束回合、新回合、终局会清空撤回栈；
- 最后一只敌人退场演出期间 UI 禁止撤回。

### 8.15 随机与确定性

**[已实现]** 正式规则使用 Mulberry32 的三条独立流：

| RNG 流 | 当前用途 |
| --- | --- |
| combat | 骰面、第二层分支、敌方目标、层生成 |
| loot | 离场晶石 |
| flavor | 诺玛 35% 隐藏事实 |

保证：

- 每条流保存 seed 和 cursor；
- 一类随机消费不会扰乱其他流；
- 失败命令不消费随机；
- 撤回恢复 cursor；
- 相同初始状态、seed 和命令序列得到同一 state 与 event trace；
- 视觉旋转圈数和动画时长不进入规则存档。

**[未实现]** 当前 Battle UI 没有“保存／读取／继续远征”入口，因此这些是引擎能力，不是完整玩家存档。

## 9. 道具、装备、挂坠、词条与状态

### 9.1 名词必须分开

为了避免 UI、人物设定和规则实例互相冒充，建议统一使用下表：

| 名词 | 生命周期 | 例子 | 当前状态 |
| --- | --- | --- | --- |
| 道具 Item | 有次数，可主动或被动消耗 | 治疗药水、屏障符文 | **[已有底座]**，无正式可用目录 |
| 装备 Equipment | 归属角色和槽位，有耐久 | 驱魔匕首、灵缚圆盾 | **[已有底座]**，无正式接入 |
| 挂坠 Charm | 档案骰装中的独立展示数据；正式接线时可映射为一类装备 | 缚灵书页、旧勋章 | **[已实现]**（只展示）；当前不是 EquipmentInstance |
| 装备词条 Affix | 由 definition 驱动的手工规则 | 对特定标签增伤 | **[已有底座]**，仅测试示例 |
| 角色私约 Trait | 档案当前保存私约文本；正式接线时可映射为唯一 TraitInstance | 王权领域、阿卡夏之锁 | **[已实现]**（只展示）；当前不是 TraitInstance |
| 状态 Status | 有目标、层数和持续边界的战斗条件 | 狂暴预警、狂暴 | **[已有底座]**，仅狂暴正式使用 |
| 遭遇规则 Encounter Rule | 一趟或一层的环境／节点规则 | 水位、钟声、天气 | **[已有底座]**，无正式内容 |
| 战斗事实 Fact | 已经发生、供局外叙事消费的记录 | 某人被击倒、零伤清层 | **[已实现]**（文字日志）；未结构化回写 |

档案页的“人物特性”是人物说明，不应自动当作 Battle Trait；角色卡的静态饰品图标也不应自动当作 EquipmentInstance。

### 9.2 道具底座

**[已有底座]** Battle 已支持：

- 可序列化 ItemInstance；
- instanceId、definitionId、来源、可选所有者（可为 null）、标签和 JSON data；
- 当前次数与最大次数；
- 开战 loadout 快照；
- consume-item 原子效果；
- item-consumed 事件；
- 离场时按 instanceId 计算真实消耗差量；
- 次数为 0 时不再编译被动效果；
- 道具效果与次数消耗一起撤回。

**[未实现]** 仍缺：

- 正式道具内容 registry；
- 玩家背包到 BattleStartInput 的接线；
- 通用 use-item command；
- 战中道具栏和目标选择；
- 正式主动道具；
- 会实际扣次数的正式 reaction；
- 离场后回写共享库存。

Controller 中存在 item targeting mode，但它只是 UI 预留，不代表道具已可用。

### 9.3 装备与耐久底座

**[已有底座]** EquipmentInstance 已有：

- 所有者；
- 槽位；
- 当前／最大耐久；
- definitionId 与 JSON data；
- consume-equipment-durability；
- 装备破损事件；
- 0 耐久时在下一次 effect runtime 编译中停止提供效果；同一 resolver 因果链使用开始时已经编译的 runtime；
- 离场输出 durabilitySpent、durabilityRemaining 和 broken；
- modifier／reaction 编译入口。

**[未实现]** 当前没有：

- 正式装备目录；
- 仓库配装；
- 商店购买生成装备实例；
- 正式槽位限制；
- 哪些事件磨损耐久；
- 破损在当下还是战后失效的产品规则；
- 工坊或保养工具实际维修；
- 任何正式改骰面能力。

### 9.4 手工词条底座

**[已有底座]** 当前刻意没有随机前后缀系统，也没有独立 AffixInstance。手工词条通过“装备或 TraitInstance + definitionId + JSON data + modifier／reaction”表达。

数值 modifier 支持：

- add；
- multiply；
- reduce；
- prevent；
- pierce；
- redirect。

当前窗口只有伤害前和治疗前。稳定排序为：

~~~text
priority
→ sourceId
→ instanceId
~~~

reaction 可监听已经发生的事件并追加原子效果；同一个 binding 对同一 event 至多触发一次。单次解析最多 256 个事件、触发深度最多 8，避免无限链。

**[未实现]** 正式 reaction registry 当前为空。以下只是自动化测试夹具，不是玩家可取得内容：

| 测试夹具 | 已验证的能力 |
| --- | --- |
| 目标标签特攻 | 对匹配标签目标伤害 ×2 |
| 命中施毒 | 命中后施加最多 3 层、持续 2 回合的毒 |
| 击杀赏金 | 击杀后额外获得 7G |
| 范围伤害吸血 | 每次实际命中后回复所有者 1 HP |

### 9.5 状态底座

**[已有底座]** StatusInstance 支持：

- 稳定实例与 definition ID；
- source 与 target；
- 层数和上限；
- 标签和 JSON data；
- 应用、修改、移除、净化；
- 敌人被击败、逃跑或移除时，清除以该敌人为目标的状态；角色力竭当前不会自动清除其通用状态；
- 按 definition 或 tag 净化；
- unremovable；
- immune:definitionId。

刷新策略：

| 策略 | 含义 |
| --- | --- |
| replace | 用新实例整体替换 |
| refresh | 保留层数，只刷新持续时间 |
| stack | 增加层数到上限，并刷新时间 |
| extend | 不改层数，延长时间 |

持续范围：

- effect；
- action；
- round；
- next-round；
- layer；
- expedition。

这些 duration scope 与推进辅助函数目前只是底座；正常 Battle 生命周期尚未统一调用通用 `advanceStatusDurations`。只有狂暴预警通过专用回合流程正式递减。新增其他持续状态前必须先把每种边界接入 canonical transition。

**[已实现]** 当前真正工作的正式状态只有：

- status.frenzy-warning；
- status.frenzy-active。

艾洛拉的昂贵治疗是 action.expensive-heal，不是状态。封骰目前使用 PartyMemberState.sealedNext 专用字段，也不是通用 Status。

**[待决策]** 新增中毒、流血、护佑、虚弱前必须先决定：

- 在 action、round、layer 或 expedition 哪个 canonical 边界递减；
- 状态击杀是否给赏金和触发私约；
- 封骰是否迁入通用状态；
- 哪些状态跨层；
- 离场时哪些转化成局外伤情。

### 9.6 当前正式 definition

**[已实现]** 正式内容 registry 只有三项：

| definitionId | 用途 |
| --- | --- |
| action.expensive-heal | 艾洛拉越限奇迹扣散金并写日志／事实 |
| status.frenzy-warning | 反拖延狂暴预警 |
| status.frenzy-active | 永久狂暴身份 |

正式 Battle modifier 数组和 reaction registry 当前都为空。

### 9.9 私约实现护栏

**[拟议]**

- 每名角色最多一条正式私约；
- 触发条件手工策划，不做无限随机词条；
- 私约阶段由 CampaignState 保存；
- 开战时把当前阶段编译成 TraitInstance 快照；
- 每条每回合最多触发一次，除非条款明确说明；
- 私约的派生结果默认不能再次触发另一条私约；
- 条件不随阶段改变，阶段只改变后果的可控程度；
- 私约不得修改标准 1–6 点数底盘；
- 牌型、意图、状态等词表必须先统一，私约再接入。

### 9.10 装备与赏金的已知风险

**[待决策]** 当前攻击在 modifier 生效前，用原始骰面强度预判是否致死并规划赏金与日志。正式增伤、减伤、穿透或重定向上线后，可能出现：

- 预判致死但实际未死，仍规划了赏金；

装备上线前，赏金和致死日志应改为根据实际 damage-applied／unit-defeated 事实生成。

### 11.3 推进相位结算

**[已实现]** 每次正式推进：

1. 剩余 1 相位的施工完成；
2. 对应设施修缮进度 +1，最多 3；
3. 完工时再次确保房间不在损坏集合中；通常它已在修缮开工时被移除；
4. 所有五处生产重新标为可收取；
5. 在可修缮且未施工的房间池中制造新损坏；
6. 通常新增 1 处，首个随机数低于 0.35 时尝试新增 2 处；
7. 总损坏数始终不超过 3；
8. 角色移动到新相位的演示驻在位置。

### 11.4 修缮与升级

**[已实现]** 每个可升级设施采用循环：

~~~text
支付基础价并开工
→ 等 1 相位
→ 修缮进度 +1
→ 重复至 3／3
→ 再支付 基础价 ×2
→ 设施等级 +1
→ 修缮进度清零
→ 下一等级重新做三步
~~~

规则：

- 每一步都扣一次完整基础价，不是三步合计一份基础价；
- 施工占 1 相位；
- 修缮开工时就从 damaged 集合移除；
- 三步全部完成后才出现升级按钮；
- 升级费为基础价 ×2；
- 最高 Lv.4；
- 公共设施扣维稳公款，武备库和工坊扣小队资金。

**[已实现]**（但语义异常）

- 没有受损的可升级设施也能直接“修缮”；
- 设施正在损坏、施工或等级提高都不影响当前功能与产量；
- Lv.1 与 Lv.4 的生产数相同；
- 初始损坏的厨房仍可收热食；
- 随机损坏池不排除 Lv.4 设施；满级设施一旦被标损坏，startRepair 会因已满级拒绝，形成无法修复的永久损坏标记；
- 随机损坏也不排除修缮进度已经 3／3 的待升级设施；这类设施不能再开修缮，而升级又不清 damaged，同样可能留下无法消除的标记；
- 这使升级目前主要是 UI 状态演示，尚未构成经营选择。

## 12. 码头“明暗骰”局

### 12.1 当前定位

**[已实现]** 这是与裂隙远征不同的一套五骰信息博弈。核心规则完全本地可玩；外部 Runtime 只是可选对手反应和战报增强。

当前双方的开桌本金：

- 玩家 bankroll：500G；
- 缇比 bankroll：500G；
- `createInitialGame` 会立即创建首局并缴底注；首局缇比坐庄，玩家扣 20G、缇比扣 10G，因此首屏实际显示 480G／490G，底池 30G；
- 每方 5 枚标准六面骰；
- 庄家逐局轮换；
- 码头 bankroll 与小队资金完全隔离；
- 刷新页面重新开始。

### 12.2 每局流程

**[已实现]**

~~~text
起蛊：双方暗掷五骰，缴底注
→ 初押：第一轮下注
→ 明蛊：双方选择公开锁定的骰子
→ 暗转：所有未公开骰强制重掷
→ 暗蛊：私下保留一部分未公开骰
→ 定蛊：其余暗骰可做最后一次整体重掷
→ 终押：第二轮下注
→ 揭蛊：展示双方全部骰子 5 秒
→ 定局：比较牌型、明蛊优先和底池
~~~

### 12.3 底注、庄家与行动顺序

**[已实现]**

- 庄家底注 10；
- 非庄家底注 20；
- 初始底池通常为 30；
- 第一轮下注由非庄家先；
- 第二轮由明蛊较少的一方先；
- 若明蛊数相同，仍由非庄家先；
- 下一局庄家交换。

### 12.4 下注动作

**[已实现]**

| 动作 | 条件 | 效果 |
| --- | --- | --- |
| 过牌 | 当前无需跟注 | 不投入；连续两次过牌结束该下注街 |
| 跟注 | 面前有差额且余额足够 | 补齐当前下注，结束该街 |
| 小注／小加注 | 本街仍允许加注且余额足够 | 投入待跟额外加 roundTo5(底池 ×0.5) |
| 大注／大加注 | 同上 | 投入待跟额外加 roundTo5(底池 ×1.0) |
| 弃牌 | 轮到自己 | 对方赢得底池；仍揭示双方骰子 |

roundTo5 会四舍五入到 5 的倍数，且最低为 5。

每条下注街允许一次“对初始下注的再加注”；再加注后，对方只能跟注或弃牌。余额不足的动作会禁用。

### 12.5 明蛊、强制重掷与暗蛊

#### 明蛊

**[已实现]**

- 可公开锁定 0–5 枚；
- 确认后不可撤回；
- 公开位置和点数对双方可见；
- 所有未公开骰必须强制重掷。

#### 暗蛊

**[已实现]**

- 强制重掷后，可私下锁定未公开骰；
- 对手知道暗锁的位置／数量，但看不到点数；
- 玩家通过暗锁决定哪些结果留下。

#### 定蛊

**[已实现]**

- 明蛊为 1–4 枚时，可以把所有“未公开且未暗锁”骰再掷一次，或直接停手；
- 玩家不是直接选最后重掷子集，而是通过暗锁留下想保留的骰，余下全部重掷；
- 明蛊为 0 或 5 时，最后重掷额度为 0；
- 缇比使用本地策略选择明锁、暗锁和最后重掷。

### 12.6 牌型与比较

**[已实现]** 牌型顺序与 Battle 当前点数牌型一致：

~~~text
散牌
< 一对
< 两对
< 三条
< 小顺
< 葫芦
< 四条
< 大顺
< 快艇
~~~

定义：

- 小顺：五骰中包含任意 4 个连续点，额外骰作为踢脚；
- 大顺：恰好包含 1,2,3,4,5 或 2,3,4,5,6；
- 同一牌型先比较主体点数，再比较剩余踢脚；
- 完全同牌时比较明蛊数量；
- 明蛊较多者获得 Lumen Priority 并赢得底池；
- 明蛊数也相同则平分底池；
- 平分时玩家得到 floor(底池／2)，余数给缇比。

### 12.7 摊牌和弃牌

**[已实现]**

- 正常终押结束后，双方全部骰子揭示 5 秒；
- 任一方弃牌也会展示双方全部骰子 5 秒；
- 胜者获得整个底池；
- 真平局按上述方式分池；
- 结果面板显示双方牌型、bankroll、底池和是否由明蛊优先决胜。

### 12.8 对手与战报 Runtime

**[已实现]**

- 无 Runtime 时使用本地 AI，核心牌局完全可玩；
- Runtime 可用时，可为缇比生成实时下注动作、情绪和一句台词；
- 实时对手决策请求失败时会回退到本地 AI；局后长战报生成失败则进入 failed 状态并保持报告为空，当前没有本地长战报替代；
- 局后可选择约 800、1200 或 1800 字战报；
- 战报管线按大纲、三路润色、审阅定稿、状态记忆提案运行；
- 记忆提案不会自动写入游戏状态。

## 14. 正式闭环的逐步结算规格

本章描述如何把当前页面岛接成一条不会丢数据、不会重复发奖的正式流程。除特别注明外均为 **[拟议]**；它不改变第 8 章记录的当前 Battle 行为。

### 14.1 出征前准备

一次正式远征从 CampaignState 开始，而不是从直接打开 battle.html 开始。

建议顺序：

1. 玩家在洋馆查看当前日期、相位、设施、伤员和可领取产出。
2. 在商店与仓库完成买卖、鉴定、维修和配装。
3. 地图读取同一份角色可用性、骰装和库存，而不是静态档案快照。
4. 玩家选择一个节点、1～4 名可选队员以及亲征或托管。
5. 地图对整个命令做一次校验；失败时不扣物、不推进时间、不写半份订单。
6. 成功后冻结本次远征需要的角色骰、装备、道具、私约与节点规则快照。
7. Campaign 创建一次性出击令；亲征进入 Battle，托管进入独立结算器。

出发校验至少包括：

| 校验 | 失败原因 | 失败后的要求 |
| --- | --- | --- |
| 节点存在且可用 | 节点已过期、被剧情锁定或版本未知 | 保留玩家当前编队，显示具体原因 |
| 成员数量 1～4 | 空队或超员 | 不创建订单 |
| 成员 ID 唯一且存在 | 重复或未知成员 | 不尝试自动修正 |
| 成员可出勤 | 仍在养伤、剧情缺勤或已参加另一任务 | 指出具体角色 |
| 每名成员有可解析骰装 | 当前共享数据为空或 definition 缺失 | 指向需要补齐的骰装 |
| 实例归属正确 | 装备或道具不存在、重复装备、已被占用 | 不扣次数与耐久 |
| 亲征时凯尔可用 | 凯尔被剧情锁定或正在其他任务 | 禁止亲征，可允许改为托管 |
| Campaign revision 可接受 | 准备期间存档已被别的事务更新 | 刷新预览后重新确认 |
| 当相位尚可出击 | 已达次数限制或正处于强制事件 | 不推进相位 |

**[拟议]** 正式库存应在创建订单时标记相关实例为 `reservedByExpeditionId`。这样玩家不能在另一个页面出售已经带出门的装备。道具次数和装备耐久仍在远征结算时按实际差量扣除，不应在出发时预扣后再猜测退款。

### 14.2 创建与一次性消费出击令

地图当前写入的 `abyssa:sortie-order:v1` 只能当原型交接。正式订单需要稳定身份和生命周期：

~~~text
draft → issued → consumed → settled
                  └→ cancelled（仅开战前）
~~~

建议语义：

- `draft` 只属于地图 UI，不写入正式存档。
- `issued` 表示 Campaign 已验证并冻结快照；此时物品被预留。
- `consumed` 表示 Battle 已用该订单创建唯一 expedition；同一 orderId 不能再创建第二局。
- `settled` 表示唯一 settlement 已成功入账并释放预留。
- 只有 `issued` 且尚未创建 expedition 的订单可取消。
- 已 `consumed` 的订单不能靠返回按钮取消；只能恢复该远征或完成正式结算。
- 直接刷新 Battle 应读取 activeExpedition 存档，不应重新消费订单。
- 直接访问 battle.html 时只允许进入明确标记的“开发预览”，其结果永远不能写入 Campaign。

消费订单必须原子完成以下动作：

1. 确认 orderId 仍为 `issued`；
2. 再次验证 Campaign revision 与所有预留实例；
3. 创建 expeditionId 和确定性 RNG seed；
4. 保存不可变 `ExpeditionStartInput`；
5. 把订单改为 `consumed` 并写入 activeExpeditionId；
6. 成功后才导航至战斗画面。

任一步失败都不得留下“订单已消费但没有远征”的孤儿状态。

### 14.3 亲征与托管分支

#### 亲征

**[拟议]** 亲征沿用当前手动 Battle：

- 地图所选四人进入动态队伍；凯尔作为领队加入第五枚骰。
- 实际骰数等于所有有效参战者的骰数，不再由 UI 单独写一个可篡改的 diceCount。
- 节点快照决定地点、背景、遭遇表、层数、奖励表和 encounter rules。
- Battle 只修改自己的 canonical state；战中不能直接改钱包或洋馆。
- 玩家清层后决定离场或深入；选择结果进入 Battle completion。

#### 托管

**[已实现]** 地图可以选择 `delegate`；**[未实现]** 仓库没有托管解析器，Battle 也不会根据该选择生成自动结算。

正式落地前必须决定：

- 托管是否仍逐层解析，还是使用队伍评分快速结算；
- 自动深入到几层、由谁决定风险偏好；
- 没有凯尔时允许几名队员和几枚骰；
- 收益折扣、晶石资格、伤情和道具消耗如何计算；
- 结果何时返回，是立刻完成还是等待一个相位；
- 托管期间成员是否从其他活动中锁定。

**[拟议] 首个闭环建议**：在上述规则定稿前，把托管按钮显示为“尚未开放”，不要伪装成已经完成的任务。若要做最小版本，则让它复用同一套 Battle 规则的无表现层模拟器和固定风险策略，输出完全相同的 completion contract；不要另写一套无法复现的随机百分比。

### 14.4 Battle completion 的生成时机

**[已实现]** 当前 Battle 有三种实际终局：玩家在清层后的 greed 阶段离场、清完第五层、全员力竭。

**[拟议]** 只有进入 `finished` 且所有规则事件已经解析完毕，才可以从 BattleState 生成 completion。以下都不能生成正式奖励：

- 玩家刚击杀最后一个敌人但清层事件尚未完成；
- 敌方动画仍在播放但规则状态未完成；
- 玩家关闭页面或强制中止；
- 开发预览局；
- 载入失败或版本不兼容的存档；
- UI 自己拼出的金币、晶石或伤员参数。

completion 必须由规则层根据最终 canonical state 导出，并至少冻结：

- 结果类型与最深层；
- 最终可带回金币和晶石；
- 素材与物品掉落；
- 每个角色的倒地次数和相关战斗事实；
- 道具实际消耗差量；
- 装备实际磨损与破损；
- 本局新增锈蚀；
- 结构化高光与完整性哈希；
- rulesVersion、contentVersion 与完成时间。

### 14.5 幂等远征结算

一次正式结算不是“给钱包加钱”这一条操作，而是一笔不可拆分的 Campaign 事务。

推荐校验顺序：

1. completion schema、rulesVersion 与 contentVersion 可识别；
2. expeditionId 与 Campaign.activeExpeditionId 一致；
3. orderId 确实由该远征消费；
4. settlementId 尚未出现在 appliedSettlementIds；
5. completion 的 start snapshot hash 与 Campaign 保存的快照一致；
6. 所有 item／equipment instanceId 都来自本次预留；
7. 消耗量和磨损量不为负，也不超过开战快照；
8. 奖励来源和数量可由 completion 的正式结果解释；
9. 库存空间或溢出暂存规则能够容纳全部战利品。

事务成功时一起完成：

~~~text
小队资金增加最终带回额
+ 远古晶石与素材入库
+ 装备／物品掉落实例化
- 道具次数与装备耐久差量
+ 伤情与角色可用性
+ 事实、记事候选与高光
+ 房间／委托可能监听的完成事件
+ appliedSettlementIds 记录
+ 出击令 settled、activeExpedition 清空
+ 释放全部预留
~~~

若任一字段无法应用，整笔事务失败并保留 active expedition，玩家可以修复或重试；不能只加金币却漏扣道具。

重复提交同一 settlementId 时应返回第一次的 SettlementReceipt，Campaign revision、钱包、库存和事实均不再变化。不能只靠按钮 disabled 防重，因为刷新、双击和崩溃恢复都会绕过表现层。

#### 库存满时

**[拟议]** 远征结算不能因为 48 格仓库已满而吞掉战利品或卡死存档。建议把无法入库的实例放入 `settlementOverflow`：

- 溢出区属于本次 receipt，不计入普通仓库容量；
- 玩家必须在结算画面选择丢弃、出售或腾出空间后领取；
- 金币、晶石和可叠加素材照常入账；
- 重进结算页面仍能恢复未处理内容；
- 同一个 settlement 不能借反复领取复制实例。

### 14.6 时间与经营推进顺序

**[拟议]** 亲征成功结算后消耗 1 个相位。推荐严格按以下顺序处理：

1. 固化远征 completion；
2. 应用远征结算并生成 receipt；
3. 记录当前相位发生的战斗事实；
4. 将时钟推进到下一相位；夜后进入次日晨；
5. 结算到期的修缮、升级和生产；
6. 在跨日时刷新每日限额和委托；
7. 根据绝对恢复日期重新计算角色可用性；
8. 生成下一相位的洋馆事件候选；
9. 存档成功后再揭示洋馆画面。

伤员不建议用“每推进一次就减 1 天”的可变计数。更稳妥的是保存 `availableAtDay`：若角色在第 4 天获得 2 天伤情，则第 6 天晨起恢复。这样当晚出征不会因为跨到次日而立刻白送一天治疗。

**[待决策]** 当前洋馆的施工按相位推进，但角色伤情文案按天显示；二者必须保留不同单位。

### 14.7 伤情与锈蚀的首版建议公式

**2026-09-06 状态更正：以下普通力竭产生 1–3 天强制伤情及配套缺勤规则已被后续柔化定稿替代，仅保留历史记录，不适用于正式 DEMO。** 当前依据为[设计状态第 5 节](DESIGN_DECISIONS_AND_CURRENT_STATUS_BEFORE_CONSOLIDATION.md#5-已定稿的地牢与常备包框架)与[DEMO 实施规格](../design/DEMO_CHARACTERS_AND_OLD_MANOR_SPEC_V0_1.md)：普通挫折不生成强制住院或永久损伤，新增退化停留在本趟远征；永久身份锈和凯尔成长锈另行处理。

当前 Battle 的 HP、力竭和新增锈蚀都只存在于一趟远征中。要接入经营，需要给玩家可读且不会滚雪球失控的后果。

**[历史提案·已被替代] MVP 伤情公式**：

~~~text
若该角色本趟未力竭：伤情天数 = 0

若至少力竭一次：
基础 = 1
重复力竭 = 力竭次数 >= 2 ? 1 : 0
深层加重 = 最后一次力竭发生在第 4～5 层 ? 1 : 0
全灭加重 = 远征结果为 wipe ? 1 : 0

伤情天数 = min(3, 基础 + 重复力竭 + 深层加重 + 全灭加重)
~~~

配套语义：

- 只剩 1 HP 但从未力竭的角色，回洋馆后自动恢复，不产生缺勤；残血已经通过继续深入时的风险体现。
- 力竭角色进入记事事实，并在 `availableAtDay` 前不能加入地图编队。
- 医务设施可以降低新伤情 1 天或提前恢复，但最低仍应有一次可见的受伤反馈。
- 全灭仍按当前 Battle 规则损失包裹的约一半，不应再额外清空全部经营资产。
- 伤情公式只读取结构化 down records，不根据演出文案猜测。

**[历史提案·部分被替代] MVP 锈蚀口径**：新增锈蚀只作为本趟远征内的恶化，结算页展示但回馆后清除，这部分继续成立；原“跨局惩罚由伤情承担”已撤销，不据此新增永久退化或强制缺勤。

### 14.8 崩溃、返回与版本异常

| 情况 | 正式行为 |
| --- | --- |
| 战中刷新 | 读取 active expedition 的 Battle save，恢复相同 RNG cursor 与事件队列 |
| 战中关闭页面 | 不结算；成员和实例继续被该 expedition 预留 |
| 玩家返回地图 | 提示继续远征，不能创建第二份订单 |
| completion 已生成但尚未入账 | 重开结算页并重试同一 settlementId |
| 结算已入账但揭示动画中崩溃 | 读取 receipt，直接回洋馆；不重复发奖 |
| rules/content 版本不兼容 | 禁止用新规则悄悄重算；提供迁移或显式终止补偿策略 |
| Battle save 损坏 | 保留 Campaign 备份和订单；进入恢复界面，不把损坏当全灭 |
| sessionStorage 被清除 | 正式订单仍在 Campaign 存档中；短期交接缓存不是事实源 |

## 15. 统一远征输入与输出契约

### 15.1 设计原则

**[拟议]** 正式契约遵守以下边界：

- 输入是已验证、已冻结的事实快照，不是对可变 Campaign 对象的引用。
- Battle 可以从输入完整重建开局，不需要读取 Shop、Map 或 Mansion 的内部状态。
- 输出只描述这趟远征发生了什么，不直接执行局外记账。
- 所有金额和数量使用整数；所有 ID 稳定且唯一。
- 内容 definition 与玩家持有 instance 分开。
- 时间戳用于审计，不参与战斗 RNG。
- seed 与三条 RNG cursor 属于规则状态；动画随机不进入契约。
- 输入、存档和输出分别版本化，不能只维护一个模糊的 `version`。

### 15.2 ExpeditionStartInput 示例

~~~ts
type ExpeditionStartInputV1 = {
  schemaVersion: 1
  expeditionId: string
  sortieOrderId: string
  commandMode: "personal" | "delegate"

  campaignRef: {
    campaignId: string
    sourceRevision: number
    day: number
    phase: "dawn" | "day" | "dusk" | "night"
  }

  node: {
    nodeId: string
    locationDefinitionId: string
    encounterTableId: string
    rewardTableId: string
    snapshotVersion: number
  }

  party: {
    leaderId: string | null
    memberIds: string[]
    resolvedDice: ResolvedCharacterDie[]
    traits: TraitInstance[]
  }

  loadout: {
    items: ItemInstance[]
    equipment: EquipmentInstance[]
  }

  encounterRules: EncounterRuleInstance[]
  rngSeeds: {
    combat: number
    loot: number
    flavor: number
  }

  versions: {
    rules: number
    content: number
  }
  snapshotHash: string
}
~~~

`ResolvedCharacterDie` 必须保存最终六面，而不是只存一个会随内容更新变化的 loadoutId。每面至少包含：

~~~ts
type ResolvedDieFace = {
  faceNumber: 1 | 2 | 3 | 4 | 5 | 6
  pip: 1 | 2 | 3 | 4 | 5 | 6
  wildPip?: true
  action: "attack" | "guard" | "heal" | "coin" | "blank" | "art" | "wild"
  power: number
  suit: "holy" | "earth" | "abyss" | "beyond"
  fate: "awake" | "asleep"
  quality: "plain" | "rust" | "gild"
  effectDefinitionIds: string[]
  modificationSources: string[]
}
~~~

**[待决策]** 当前 Battle 的 legacy `none` 仍能成牌，而档案沉眠语义相反。推荐 canonical 迁移时把旧 `none` 显式映射为 `fate: "asleep"`，并给它一个独立的基础 quality；不要让 `none` 继续同时表示命数和品相。`art` 虽保留在档案动作枚举中，但当前 Battle 没有对应命令或效果语义，正式骰面含 `art` 时必须在开战编译阶段拒绝或先定义其行为。

### 15.3 BattleCompletionOutput 示例

~~~ts
type BattleCompletionOutputV1 = {
  schemaVersion: 1

  }

    characterId: string

  }>

  consumedItems: Array<{
    instanceId: string

  }>

    instanceId: string

~~~

当前 `BattleCompletionOutput` 已能表达道具消耗和装备磨损的一部分差量，但还没有成为跨 App 的正式事务，也没有完整输出事实、素材、伤情与实例掉落。

### 15.4 SettlementReceipt 示例

~~~ts
type SettlementReceiptV1 = {
  settlementId: string
  expeditionId: string
  appliedCampaignRevision: number
  walletDelta: {
    partyCurrencyMinor: number
    ancientCrystals: number
  }
  inventoryAddedInstanceIds: string[]
  overflowInstanceIds: string[]
  injuredCharacterIds: string[]
  acceptedFactIds: string[]
  nextClock: { day: number; phase: "dawn" | "day" | "dusk" | "night" }
  appliedAt: string
}
~~~

receipt 是“已经入账”的证明；completion 是“Battle 请求入账”的事实。两者不能混用。

### 15.5 必须保持的领域不变量

1. 同一 orderId 最多创建一个 expeditionId。
2. 同一 expeditionId 最多产生一个有效 settlementId。
3. 同一 settlementId 最多改变 Campaign 一次。
4. 钱包、堆叠数量、次数和耐久不能为负。
5. 同一个不可堆叠 instanceId 不能同时位于仓库、装备槽、商店、溢出区和远征预留中。
6. Battle 输出的消耗实例必须是开战输入的子集。
7. 输出的剩余次数／耐久必须与开战快照和 spent 差量一致。
8. `memberIds` 唯一；所有骰子的 owner 都必须在正式队伍中；`resolvedDice` 的数组顺序属于冻结快照，重放时不可重排。
9. 沉眠或封锁骰是否参与牌型只能由一套共享算法决定。
10. 事实 factId、奖励 grantId 和掉落实例 ID 在重放时稳定。
11. 失败 command 不推进 Campaign revision，也不消耗 RNG。
12. 表现层计时、皮肤、面板开关和视觉随机不影响 completionHash。
13. 每个 resolved face 恰有一个非空 canonical 花色；花色在远征中不可被表现层或普通装备改写。
14. 花色牌型的最终贡献者只能由冻结输入和规则排序决定，不能依赖数组外的 UI 状态或对象遍历顺序。

| P1 | 道具 | 有 instance／charges／effect 底座，无正式目录和 use-item | 首批 definition、命令、目标与 UI | 商店消耗品不能进入战斗 |

| P1 | 词条／私约 | modifier／reaction 可用，正式 registry 近空 | 手工 definition、触发上限与升级规则 | 角色成长不会影响玩法 |
| P1 | 状态生命周期 | 通用状态结构存在，边界未接入正常回合 | action／round／layer 的推进点 | 中毒等内容会永久或过早消失 |
| P1 | 实际击杀奖励 | 加成与重定向上线后，预判可能不同于实际事件 | 按 damage-applied／unit-defeated 结算 | 增伤装备会造成错误赏金与日志 |
| P1 | 素材 | 地图仅相对星级，洋馆有五种产出，Battle 无掉落表 | 统一 definition、堆叠和用途 | “战斗—生产—维修”缺一边 |
| P1 | 库存容量 | 洋馆显示 48 格，商店和 Battle 不共享容量 | 堆叠、实例占格、溢出结算规则 | 满仓时掉落会丢失或卡死 |
| P1 | 伤情 | 当前锈蚀只在一趟远征存在 | 可用性、恢复日期、医务设施 | 战斗失败不影响经营 |
| P1 | 战斗事实 | UI 有事实文本，completion 未完整输出 | 结构化白名单与 journal 接线 | 餐桌、羁绊、记事无法验证来源 |
| P1 | 商店库存 | 完整交易只改本页余额和列表 | Campaign 交易事务与 instance 化 | 买到的东西无法配装 |
| P1 | 洋馆生产 | 设施产出只在本页库存 | 写入共享 stacks 并规定收取时机 | 经营资源不能用于战斗 |
| P1 | 托管 | 有按钮和订单枚举，无规则 | 正式模拟、风险策略与结算时点 | 托管是空承诺 |
| P2 | 骰局经济 | 双方开桌本金各 500G、首局立即扣底注，战报只在内存 | 每日限额与小队钱包接线 | 可选玩法不属于经营循环 |
| P2 | 羁绊 | 档案为静态值与样稿 | 事实驱动成长、每日上限和解锁表 | 关系内容无法由玩法推进 |
| P2 | 周常大战 | 只有长期设计方向 | 触发日、议会规则和奖励 | 不影响首个日常闭环 |
| P2 | 设置 | 只作用于本页预览 | 全局偏好存储和各 App 读取 | 设置页不改变实际游戏 |
| P2 | 返回与辅助功能 | 场景多为单向、设置未共享 | 统一返回、键盘、降动效与音量策略 | 完整产品体验不稳定 |
| P2 | 离线资源 | 若干图片、Google Fonts 和可选 Runtime 在外部 | 本地化资产或明确联网需求 | 完全离线发行不完整 |
| P2 | 跨页 E2E | 当前主要是模块级 Vitest | Playwright/Cypress 或同等浏览器流程 | 关键断点只能靠人工发现 |

### 16.1 首次评审必须拍板的十项

为避免代码先于规则，建议第一次闭环评审只回答以下问题：

1. UI 数字统一按最小单位 G／铜里拉，还是整体重标价格？
2. Battle 深度倍率采用 A、B 还是 C？
3. 沉眠面是否仍能掷出和执行战面，并只从点数／花色牌型中排除？
4. 花色是否按“至少 4 个自然同色有效面”在 MVP 接入；同花和同花顺采用什么倍率？
5. 凯尔亲征是否永远作为额外第五人？
6. 普通远征最多仍固定五层，还是由节点各自定义？
7. 锈蚀是否只在本趟存在？
8. 托管首版关闭，还是与亲征同时实现？
9. 一次亲征固定消耗一个相位吗？
10. 仓库满时使用溢出区、自动出售还是禁止出发？

本文给出的推荐答案依次为：最小单位、倍率 A、沉眠面仍可掷出和执行战面但不贡献点数与花色、MVP 接入四面自然同花并暂取 `+0.6`（五骰同花顺暂取 `+2.4`、可在下一阶段开放）、凯尔额外第五人、节点可配置且当前裂隙为五层、锈蚀局内、托管暂时关闭、一相位、使用溢出区。

## 17. MVP 接通顺序与验收标准

### 17.1 阶段 0：冻结规则口径

交付物：

- 拍板第 16.1 节十项决策；
- 统一角色 ID、节点 ID、货币单位、骰面／花色枚举和 outcome 枚举；
- 冻结同花的有效面、贡献面、优先级、品相与倍率口径；
- 把出击令、resolved dice、completion 和 settlement 移到 shared domain；
- 给 Campaign、Battle save、start input、completion 各自建立版本号。

验收：Map 和 Battle 不再各声明一份近似但不同的类型；同一六面定义能同时驱动档案、编队预览和战斗。

### 17.2 阶段 1：建立可保存的 Campaign

交付物：

- 新游戏初始化和继续游戏；
- 版本化本地存档、迁移和备份；
- 单一 clock、钱包、库存、角色可用性和设施状态；
- command → validate → apply → receipt 的写入管线；
- 标题页“继续”仅在存在有效存档时可用。

验收：在洋馆、商店、地图之间来回并刷新，日期、余额和库存始终一致；损坏主存档时可以识别并尝试备份恢复。

### 17.3 阶段 2：地图到动态 Battle

交付物：

- 枢纽出征先进入地图；
- 九人可用性与 canonical 骰装接入；
- 出击令创建、库存预留、一次性消费；
- Battle 按 node、party、resolved dice 和 loadout 建局；
- Battle 逐面读取花色并完成四面同花判定、贡献者高亮和存档恢复；
- 开发预览与正式远征明确隔离。

验收：地图选哪几个人，战场就只出现对应骰子；档案中的主副色逐面进入 Battle，四个自然同色有效面能稳定形成同花；同一个 orderId 无法通过刷新创建第二局；伤员、空骰装和重复成员均在开战前被拒绝。

### 17.4 阶段 3：Battle 到幂等结算

交付物：

- 从 finished BattleState 导出完整 completion；
- settlement 事务与 receipt；
- 金币、晶石、消耗、耐久、伤情和事实同时回写；
- 结算溢出区；
- 相位推进与返回洋馆；
- active expedition 恢复。

验收：

1. 同一个 settlement 连续提交两次，第二次所有资源 delta 均为 0。
2. 在结算应用后、返回动画前刷新，最终资产只增加一次。
3. 在敌方回合中刷新，继续后的状态、下一次 RNG 结果和未刷新流程一致。
4. 全灭按当前规则保留约半数已入袋包裹，不被 UI 错写成全清。
5. 任一道具扣减失败时，金币和事实也不应部分入账。

### 17.5 阶段 4：接通经营用途

交付物：

- 商店买卖、出售和鉴定使用 Campaign transaction；
- 洋馆修缮、升级、生产与收取使用统一钱包和 stacks；
- 医务设施读取并改变伤情；
- 工坊维修真实装备耐久；
- 事实进入记事候选和相位事件。

验收：战斗取得的素材可用于一次设施或维修，商店买到的道具可在下一趟 Battle 消耗，受伤角色在地图中不可选且到恢复日自动可选。

### 17.6 阶段 5：首批构筑内容

建议只做能证明完整纵切的最小内容：

- 1 个治疗道具、1 个定向格挡道具、1 个解封道具；
- 2～3 件会实际改战面的装备；
- 2 条正式角色私约；
- 2 种正式状态；
- 3 个地图节点各自的一小套 encounter rule 与奖励表；
- 1 条从结构化 Battle fact 生成的洋馆事件。

验收：每项内容都能从取得／购买开始，经过配装、战斗触发、消耗或磨损，最终回到仓库／维修／记事；只在测试夹具里成功不算完成。

### 17.7 跨页浏览器验收场景

2026-09-07补充：下列是早期经营闭环目标，不是当前新玩家入口。新的首条验收路径应为 **新档→CG→洋馆介绍→基础教程／简单副本→回馆→自由枢纽／庄园**，并覆盖各阶段恢复与旧档继续；具体以[初章计划](../../plans/DEMO_PROLOGUE_AND_ONBOARDING_PLAN.md)和[D6](../plans/DEMO_CHARACTERS_AND_OLD_MANOR_IMPLEMENTATION_PLAN.md#9-d6综合验证配平与交付)为准。

至少建立以下正式 E2E：

~~~text
新游戏
→ 洋馆领取一份产出
→ 商店购买道具
→ 仓库给角色配装
→ 地图选四人并亲征
→ Battle 使用道具、至少清一层并离场
→ 结算应用
→ 返回洋馆
→ 刷新
→ 再次检查钱包、道具次数、伤情、时间与事实
~~~

还要覆盖：

- 空队、伤员和空骰装不能出发；
- 订单消费后浏览器后退不能再开一局；
- 战中刷新与敌方回合中途恢复；
- 仓库满时进入 overflow；
- 重复 settlement；
- 至少一次四面同花，以及花色牌型在战中刷新后的确定性恢复；
- 旧 Campaign schema 迁移；
- 不兼容 Battle rules/content version 的可解释错误；
- 各正式链接在发行产物中都存在。

### 17.8 MVP 完成定义

当且仅当以下条件同时成立，才可称“出征—战斗—经营闭环已实现”：

- 玩家不借助开发入口就能从标题页走完整流程并回到洋馆；
- 选择的节点、成员与配装真实改变 Battle 输入；
- 档案、地图和 Battle 共用逐面花色，同花不再只是预览文案；
- Battle 的结果、消耗和伤情真实改变同一份 Campaign；
- 刷新、返回、重复点击和崩溃恢复不会复制或吞掉资产；
- 至少一种战利品在经营层有用途，至少一种经营取得物能在战斗中产生效果；
- 时间推进会改变至少一项设施、伤情或事件状态；
- 全流程有自动化浏览器验收，而非只在每个页面单独演示。

## 18. 构建、发行与质量现状

> S0 实施追记（2026-09-05）：本节保留编写时的审计快照。入口与产物已迁移到统一登记、`dist/ui|game|lab|tools`，novel／rp／studio 的源码相对素材路径已修复，远程骰局默认关闭。新的验证结果见 [S0 实施记录](../plans/S0_ENGINEERING_BASELINE_PLAN.md#11-实施记录)；本节历史失败记录不覆盖新基线，也不代表存档／结算闭环已完成。

### 18.1 当前验证基线

**[已实现]** 仓库使用 TypeScript、Vitest/jsdom 与模块边界脚本；Battle 另有规则、存档、迁移、不变量、Controller 和表现事件测试。

本次文档核对的实际结果：

- `npm run typecheck` 通过；
- `npm run boundaries:check` 通过；
- 测试清单共 80 个文件、695 项；
- 两次完整 `npm test` 都因 `ExpeditionBattleScreen.test.tsx` 的 5 秒演出用例超时而出现同文件后续连锁失败，分别通过 673／695 和 671／695；
- 单独重跑该 Battle 文件时 42／42 通过，但耗时约 64 秒；
- 把全局 testTimeout 放宽到 10 秒后仍只通过 682／695：除 Battle 的计时／`act()` 连锁外，组件目录的 20 秒自定义 timeout 和枢纽打字机等待也在全量负载下失败。
- 随后以单 worker 只跑 Catalog 与 Menu 时 9／9 通过；三处失败目前都只在全量并行负载中复现。

此前存在 80 文件、695 项全部通过的基线记录，但本次不能把它继续表述成无条件绿灯。现象整体指向全量并行负载下的时间敏感、未等待完成的演出与失败后的清理连锁；Markdown 修改本身不触及运行时代码。正式发布应修正或隔离这些计时测试后，在目标 commit 重跑并记录稳定结果。

### 18.2 多入口发行断点

**[已实现]** 仓库有 18 个 Vite 入口，但没有聚合 `build:all`。根 `npm run build` 只构建组件库。

容易被根开发服务器掩盖的缺页：

| 构建 | 当前包含 | 页面会继续前往 | 风险 |
| --- | --- | --- | --- |
| title-dist | title、menu | mansion、shop、battle、character-status | 除 menu 外的目标未全部打入，正式点击可能 404 |
| menu-dist | menu、character-status | mansion、shop、battle | 三个主要目标未打入 |
| map-dist | map | battle | Battle 未打入 |
| mansion-dist | mansion、shop、dice、battle | 四条洋馆内路径 | 当前相对最完整，但仍不含标题、枢纽、地图和档案 |
| battle-dist | battle | 未来结算／洋馆 | 当前没有正式返回闭环 |
| novel-dist／rp-dist | novel 或 rp | 本页演出 | 生产代码仍以 `../src/...` 引用背景、纸娃娃及漫符，但独立构建未复制源码资产；预览会出现资源 404 |

**[拟议]** 正式游戏应有一个明确发行目标：要么建立包含所有玩家页面的统一多页 Vite 配置，要么迁移到单一应用壳。无论哪种方案，都要自动扫描页面内相对链接并验证目标文件存在。

### 18.3 外部依赖与离线性

**[已实现]** 地图图片已全部本地化：底图在 `src/assets/map/terrain/`，三个节点图在 `src/assets/map/landmarks/`，委托背景在 `src/assets/map/quest-backgrounds/`；这部分已移除外部图床依赖，文件映射见[地图素材说明](../../../src/assets/map/README.md)。

当前仍有以下远程依赖：

- 骰局和商店的缇比立绘仍有远程来源；
- loading、mansion、menu、shop、title 的 HTML 通过 Google Fonts 加载字体；
- novel 与 rp 的生产资源路径仍回指 `../src`；这不是远程依赖，但会破坏当前独立 dist 的背景、纸娃娃与漫符展示；
- 骰局开发服务器把同源 `/api` 代理到本机 8787；静态构建默认请求同源 `/api/v1`，也可由 `VITE_DICE_RUNTIME_API_BASE_URL` 覆盖。

核心骰局在 Runtime 不可用时有本地 fallback，但远程图片和字体仍会影响完全离线展示。

**[拟议]** 正式离线发行应把字体和必要图片纳入版本化资产，给可选 Runtime 设置超时和清晰降级状态，并在断网 E2E 中验证主循环仍可完成。

### 18.4 测试缺口

- **[已实现]** 有大量模块与组件测试。
- **[未实现]** 没有正式跨 HTML 页面 E2E。
- **[未实现]** 没有验证独立 dist 中所有目标链接存在的发行测试。
- **[未实现]** 没有 Campaign schema、结算幂等和跨 App 恢复测试，因为 Campaign 尚不存在。
- **[已实现但不稳定]** `ExpeditionBattleScreen.test.tsx` 单独通过，全量并行时会越过 timeout，并在未完成的 `act()`／清理后造成同文件连锁空 DOM 失败；Catalog 的大渲染测试和 Menu 的打字机等待也会受全量负载影响。应消除真实墙钟依赖、完整 await 演出任务，或为调度建立更稳定的假时钟边界。
- **[拟议]** 每次更改 Battle schema、rulesVersion 或 contentVersion 都必须提供迁移／拒绝策略测试。
- **[拟议]** 经济平衡应另建模拟测试，统计各层平均收益、全灭损失、牌型贡献和商店购买力，不能只凭单局手感。

## 19. 世界观与内容定位摘要

本章概括 `st/setting` 中的叙事基线，帮助玩法实现理解“为什么要出征和经营”。它是内容设定，不代表其中每项已经做成可交互系统。

### 19.1 宇宙法则

- 大天平不是人格神，而是维持秩序与混沌总量平衡的中立机制。
- 秩序／玛那代表结构、稳定、边界和可预测；过量会导致静止、情感剥夺与结晶化。
- 混沌／瘴气代表变化、适应、分化和溶解；过量会导致肉体畸变与理智崩坏。
- 两者都不是善恶阵营。凡界恰恰由两极冲突后的混合残余孕育。
- 天穹神域、混沌深渊与下层凡界构成三层宇宙；诸神正在极端秩序中结晶，深渊则通过位面裂隙倒灌。
- 勇者和魔王都是大天平选出的法则代理人，本质上是互补调律器，而非天生必须互相杀死的善恶宿敌。

### 19.2 四个纪元

| 时期 | 核心变化 |
| --- | --- |
| 纪元前 | 创世大撕裂分离两极；原初神战残骸沉积为凡界 |
| 第一纪元 | 凡世生命与万灵协约出现；最早的勇者／魔王代理人降生 |
| 第二纪元 | 人类收编勇者制度；魔族建立深渊王庭与四天王摄政；周期性限战和阵营货币固化 |
| 第三纪元 | 双方极端化并爆发总体战争；勇者斩杀魔王后源力失控，旧制度破产 |
| 第四纪元 | 伪典圣战揭露政治豪赌；凯尔安抚艾比希斯；人类新王权与深渊四席在共同毁灭威慑下共治 |

### 19.3 伪典圣战与当前共同体

- 改革派把三大主战势力继承人尤斯缇丝、艾洛拉、柯萝萝编入勇者小队，既是远征者也是政治人质。
- 诺玛原本受雇担任监视与失控时的肃清暗子；凯尔则是各方眼中可消耗的平民老兵。
- 小队在断粮和背叛中交换真相，放弃原阵营最高指令，结成“所有人都活下去”的共犯同盟。
- 四天王沿途测试凯尔的法则适格性，同时与人类主战派发生真正的致命冲突。
- 王座前的刺杀法阵唤醒艾比希斯并引发灭世级暴走；凯尔没有拔剑，而以稳定秩序波长和拥抱将其安抚。
- 事件后，人类摄政府、商贸同盟与深渊四席维持脆弱共治；小队拒绝返回王都，最终共同留在守望者之崖。

### 19.4 守望者之崖为什么需要经营

守望者之崖表面是海崖洋馆和隐居小镇，实质是收容灭世级法则容器的政治与防御中枢：

- 外围由人类重兵控制陆海通路；内部由四天王结界保护。
- 极品食材、日常起居、结界耗材与禁军开销形成高昂且受审计的维稳成本。
- 魔王气息会吸引畸变魔物、归渊密教和其他破约者靠近。
- 凯尔与小队频繁清理周边裂隙，既为提前消除威胁，也为取得可交易的遗物和经营资金。
- 所以“战斗赚钱—修好洋馆—维持日常—让所有人安全回来”不是两套无关玩法，而是同一主题的内外两面。

### 19.5 玩法应保护的叙事基调

1. 秩序与混沌都不是简单善恶，敌人应更多来自失衡、畸变和政治破约。
2. 艾比希斯是需要被保护且拥有独立人格的法则容器，不是可消耗的基地 Buff。
3. 凯尔的核心价值是稳定、照料与承担，而非无条件输出最高。
4. 勇者小队与四席的共同生活来自真实创伤和政治决裂，日常喜剧应沉淀关系，而不是抹去后果。
5. 战斗事实回到餐桌、房间和记事，才能表现“门外肃清、门内生活”的对照。
6. 公款与小队资金的分离有世界观意义：前者受跨阵营审计，后者承载小队自主权。
7. 私约成长应让角色更能掌控自身代价，不把创伤简单升级成更大数值。
