## 1. P0 · Bug修复（已完成，以下保留修复前诊断）

### 1.1 副本（庄园）防御操作失效 —— 交互未统一

**现象**：队友被怪物攻击时，拿起持盾牌骰面的角色后点击被攻击的队友（或敌人卡体），无任何反应、无提示。

**根因**：裂隙版与庄园版是两套点击绑定，庄园版漏接了 guard 路径。规则层正常（`src/game-core/battle/rules/v2/combat.ts:205-215` 的 guard 选项生成、`:294-306` 的 `guard-applied` 结算均无问题），纯属 UI 绑定缺口：

| 防御触发路径 | 裂隙版（原状） | 庄园版（修复前） |
| --- | --- | --- |
| 点被攻击的队友卡 → 自动格挡威胁最大的敌人 | ✅ `battle-view-model.ts:58-73` | ❌ `ManorBattleBinding.tsx:58-70` 的 `onMember` 只处理 heal 和拿起/放下 |
| 点敌人卡体 | ✅ `battle-view-model.ts:87` | ❌ `ManorBattleBinding.tsx:71-77` 的 `onEnemy` 只处理 attack/bind |
| 点敌方意图气泡 | ✅ | ✅ `ManorBattleBinding.tsx:78-81` `onIntent` |

**修复要求（统一交互原则）**：

1. 庄园版 `onMember` 补 guard 路径：手持 guard/guard-all/protect 面时点被攻击队友 → 从 `options` 中找出该队友对应的 `guard` 选项（多个敌人攻击同一队友时选剩余威胁最大者，比照裂隙版 `battle-view-model.ts:59-72` 的排序逻辑）；有 `guard-all` 选项时按现有 `onIntent` 优先级处理。
2. 庄园版 `onEnemy` 补 guard 路径：手持 guard 面点有攻击意图的敌人卡体 → `act("guard", enemyId)`。
3. **交互统一是验收标准**：两版战斗中，"拿骰 → 点队友 / 点敌人 / 点意图"三条路径的语义必须一致。建议把目标推导收敛为一个共享的 view-model 函数（庄园版基于 `options` 列表、裂隙版基于骰面推导，可各自实现但语义对齐），并在 `ExpeditionBattleScreen.test.tsx` 已有的 4 个防御用例基础上，为庄园绑定补对应用例。

**附带修复（同批处理）**：

- `ExpeditionBattleScreen.tsx:100` 的 `handleIntentClick` 缺 `isPresentationBusy()` 检查（同文件其他 handler 均有），演出中点击会被静默吞掉——补齐。
- `handleDieToggle`（`ExpeditionBattleScreen.tsx:81`）卸下手持骰后不再清空 `heldActor`，可能出现"手持已失效骰去点目标"的状态错乱——确认 `controller.finish()` 兜底是否充分，不充分则恢复清空。

### 1.2 出征编队页骰子展示退化为纯文字

**现象**：出征编辑页面的骰面从图形组件退化为无样式文字段落。

**根因**（未提交改动引入）：

- `src/apps/map/sortie/live-roster.ts:26-34`：`liveParty()` 给每个成员设 `faces: []`（空数组），并把骰面拼成纯文字 `legacySummary`（"攻击 2（锈） / 防御 1 / …"）。
- `src/apps/map/sortie/SortieRosterPanel.tsx:319`：`legacySummary` 存在即渲染 `<p>` 纯文本，图形组件 `FaceStrip`（内部为 `src/shared/ui/dice-face/ExpeditionFlatDieFrame.tsx` SVG 骰面）被短路；`:374` 的战面/命数/私约 `<dl>` 同样被文字段落替换。
- `MapPage.tsx` 已把花名册来源切到 `liveParty(archive view)`，运行时必然走文字分支。

**修复要求**：

1. `liveParty()` 产出真实 `DieFace[]`（archive view 中已有骰面数据，参照同文件 `presentDice` 的返回结构），删除 `legacySummary` 及其短路分支。
2. `SortieRosterPanel.tsx` 恢复 `FaceStrip` 与 `<dl>` 构成表渲染。
3. 验收：编队页六面骰以 `ExpeditionFlatDieFrame` 图形呈现，含锈/镀质量标记；真实档案数据（非静态 `sortie-roster.ts`）驱动。

目标：

1. 道具从右侧栏与弹窗流中移出，归入行动坞（`ExpeditionDicePanel.tsx:153-190` 的 `ActionDock`）体系。

### 2.3 右侧角色反应区（A3）

右侧栏保留340设计px列宽，上部仪表座与下部角色反应共用外框：

1. 层数／回合以图标＋数字嵌在仪表座上沿，不再占用独立刻板。**只有庄园皮肤有红线**，其余四套皮肤使用各自普通框边。
2. 现有六人立绘按角色裁切，头部／帽饰可越过内框上沿；收紧与刻板间的空档，保留身体渐隐。
3. 底部复用 `RpgDialogue`，高度随文字撑开；姓名、状态和对白不得越框，长句逐条验证。
4. 触发逻辑：每次打出骰子（`action-resolved` 等已提交演出事件，接入点在 `presentation/committed-events.ts` / `controller/presentation-events.ts` 的事件回放流）时，切换到出手角色——旧立绘**淡出**、新立绘**淡入**，反应框同步显示该角色对本次行动的反应文案（例：打出摆烂/空白骰的角色吐槽）。
5. 反应文案来自**本地反应表**：按"角色 × 触发类型（打出骰面类型/空白面/格挡成功/治疗/事件判定成功失败等）"建表，以已提交回执／事件ID的稳定哈希选择句子，避免重渲染刷句；实现上可参照 `game-client/CampaignPanel.tsx:26-37` `createReactions` 的本地反应模式，但作为战斗表现层的独立模块，不复用洋馆归来报告的语义。
6. 事件解谜过程（§3）同样驱动此区域——这是互动感的关键，事件态不得让反应区静默。
7. 反应属于表现层，**不进入规则状态与存档**；演出跳过/快进时反应直接切换到最终态。

接入时按已提交事件ID去重；页面重渲染、失败请求、读档恢复不能再次随机刷文案。当前刷新／撤销回到同行待机句，不恢复上一条未持久化反应。不改变战斗RNG，空白／摆烂只有实际可用且已提交的动作才触发，不因查看骰面伪造一次行动。旧版、庄园与回忆共用展示组件，由各自适配层提供事实。

   - **事件**：事件文本**淡入**、界面布局同步切换（§3）；
   - **战斗**：背景连续推近、轻微弧形回收、再放大进入快速双闪，两闪间回暗时保持镜头末态，第二闪覆盖期间切到新战场，再柔和揭示敌人。效果仅限敌区，复用现有敌人登场演出，不增加前置弹窗。
3. 层结算推进沿用权威结果；按用户后续定稿，不把逐层入袋清单或计算公式重新放回展开账本。原事件／结算弹窗的进一步整理属于P1-D。

实施边界：P1先把**现有单人事件**内嵌，仍展示现有规则与原选项，结果从已提交投影读取；多人解谜、事件专用骰及角色卡折叠按P2交付。推进保持先提交后演出，失败不播抵达、连点不重发；只摇背景图层，不移动雾气画布、敌人命中区或顶栏。低动效与刷新恢复直接显示已提交节点，不重演命令。

## 3. P2 · 需改 core 契约：事件系统内嵌化与骰子解谜

独立审计与详细提案见[多人骰子事件：规则与存档契约 v0.1](../../plans/MULTI_ACTOR_DICE_EVENT_RULES_AND_SAVE_CONTRACT.md)。它补齐费用、开骰、放弃、RNG、证据、恢复和版本边界；候选玩法与数值尚非用户定稿。P2-A的可操作原型及契约代码仍待完成。

### 3.1 原则

事件层逻辑已统一在 game-core（`DemoEventDef`，`src/game-core/contracts/demo.ts:103`；结算 `src/game-core/session/demo-items-events.ts:22-34`；校验 `src/game-core/battle/rules/v2/journey-validation.ts:61-76`）。**呈现层不得再造弹窗事件**；本次扩展契约以支撑内嵌解谜交互，规则仍全部在 core，UI 只读投影 + 提交命令。

### 3.2 契约扩展（`DemoEventDef` 演进）

现状字段：`{ id; name; text; kind: "register"|"relic"|"seats"; cost; reward }`，选项硬编码为 read/attempt/skip，无图片、无人数上限、无结构化判定。

扩展方向（新内容版本发布，旧档旧事件按原规则运行，比照 D3 §3.3 存档策略）：

1. **选项结构化**：`options: DemoEventOptionDef[]`，每个选项含 `id`、`label`、**前置判断**（可声明式表达：需要散金 ≥ cost、需要某角色在队、需要前序事件完成等，复用 Catalog 引用校验体系）、以及结算方式（`free`（纯文本/直接结算）或 `dice-puzzle`（进入骰子解谜））。现有 read/attempt/skip 平移为首批选项实例。
2. **骰子解谜结构**：选项为 `dice-puzzle` 时声明：
   - `maxActors`：**最多允许被选中的参与人数**（UI 必须标注）；
   - **硬判断（hard）**：特定骰面种类命中即判定成功的白名单（现 relic 事件"治疗、昂贵治疗、庇护、守护全体、万能可强保全"即原型，`ManorBattleBinding.tsx:182` 文案背后的规则正式化）；
   - **软判断（soft）**：不满足硬判断时按点数/命数阈值判定（现"清醒且至少四点或万能命数可弱保全"即原型），可声明部分成功/失败档位与对应奖惩。
3. **配图占位**：`illustration?: string`（素材引用 ID）。**本次仅进契约与占位渲染框，不接真实资产**；Catalog 校验允许为空。
4. **命令扩展**：现有`choose-event`接收`choiceId + actorId`，attempt提交时独立掷事件骰。新协议支持`actorIds[]`及事件专用骰身份（受`maxActors`约束）；core校验唯一参与者、在队／存活、骰的归属与本事件状态，UI只读合法性投影。旧命令／旧档继续原规则。
5. **事件骰生命周期先收口**：建议采用“选解谜选项 → core生成并持久化事件骰 → 玩家在已投影结果中选人 → 确认结算”，让匹配有可见依据。需要明确选项进入是否可取消、重复进入是否重掷、费用在哪一步扣除、未选骰如何处理，以及刷新／重试如何还原同一结果。骰面、RNG推进、费用与判定由事务提交；不借用战斗loaded／spent，不在React中随机。本方案属P2勘探起点，原计划未定稿的这些边界不能默认为已实现。

### 3.3 事件态呈现（内嵌布局切换）

1. 事件触发时**不弹窗**：战场区淡出，事件文本区淡入（事件涉及较大文本量，文本区占据原敌人区位置，带滚动）；配图占位框在文本侧。
2. **角色卡折叠**：下方角色卡从 160×216 大卡（`expedition-party.css:45-63`）**自动折叠为条状**（横条：头像缩略 + 名字 + HP + 当前骰面缩略图），腾出纵向空间给事件文本；**仅事件态自动折叠**，战斗态恢复大卡，不提供手动折叠。折叠/展开带过渡动画。
3. **解谜交互**：玩家点击条状角色卡上的骰面进行选中/取消（复用"拿起骰"的既有心智），选中数受 `maxActors` 约束并在 UI 标注（如"最多 2 人参与"）；确认后提交命令，core 按硬判断 → 软判断顺序结算并发事件回执。
4. **全程角色反应**（互动感关键）：选中角色、硬判断命中、软判断勉强通过、判定失败等节点均驱动 §2.3 反应区的立绘切换与吐槽文案。
5. 事件结算后（现"已完成整理"弹窗内容）以界面内叙述条呈现，玩家点击"继续前进"回到 §2.5 节奏流。

### 3.4 选项 + 解谜的组合形态（推荐方案，实施前向用户过一次原型）

事件呈现为：**文本 + 选项列表**（选项可用性由前置判断决定，不可用选项置灰并显示原因）；选项分两类——纯文本选项直接结算（如"阅读迎宾簿"、"绕行"），解谜选项进入 §3.3 的骰子匹配环节。即"选项承载叙事分支与前置判断，骰子解谜承载资源投入与随机性"。若实施中发现某事件需要"先掷后选"的反向顺序，回写本节。
