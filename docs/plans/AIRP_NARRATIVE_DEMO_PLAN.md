# AIRP 叙事闭环 DEMO 实施计划 v0.6

更新：2026-09-12。本文保留AIRP的领域设计与阶段范围，当前优先级统一见[Abyssa推进计划](ABYSSA_DEMO_NEXT_STEPS.md)。AIRP-1～3已实现；显式内容10与0.2.1药箱两场曾通过真实模型和记忆闭环验收。第一批已修复0.3.0的版本接纳与最终formatter映射，当前源码应用包、玩家链和恢复通过隔离复验，见[09-12报告](../audits/2026-09-12-airp-package-compatibility.md)。真实安装仍未升级，文学质量与资料接线不因此算完成。

依据：用户提供的《ABYSSA · AIRP 叙事闭环核心设计文档 v0.1》及后续讨论。现有能力与源码依据见[勘探报告](../audits/2026-09-09-airp-narrative-exploration.md)，现行可玩范围见[机制总览](../GAME_SYSTEMS_AND_CONTENT_SPEC.md)。

本计划将AIRP作为“初章引导→初章副本→庄园副本”三段骨架后的叙事闭环交付，不改写O阶段完成状态。[AIRP-1](AIRP_1_CONTRACTS_AND_FIRST_ERRAND.md)定义契约，[AIRP-2](AIRP_2_IMPLEMENTATION.md)接通内容8单条手写链，[AIRP-3](AIRP_3_IMPLEMENTATION.md)以内容9扩展四型与时局；这些已实现版本尚未接入rp。

v0.6依据最新决定撤销纯静态／发布后脱离rp的约束，取代v0.2至v0.5的制作期生成、内容发布器与静态消费路线；[旧发布器方案](../archive/plans/AIRP_4_CONTENT_PUBLISHER_PLAN.md)仅留历史。不恢复单次Manual调用方案，不再抽取浏览器版内核。保留三类模型、分任务预设、固定Workflow、原生状态／记忆语义及旧档保护；通用机制归rp，AIRP配置领域规则，Abyssa通过接口使用。后续实施进度统一见[AIRP-4记录](AIRP_4_IMPLEMENTATION.md)。

## 1. 交付目标与范围

玩家能接受一项与人物有关的委托，通过真实巡守完成，回馆得到与行动一致的回应；也能遇到一次没有参与、后来由他人处理的事件，并在后续对话中感知余波。

同时分开验收两项结果：

- **确定性叙事闭环**：手写内容可独立完成筛选、触发、接受、执行、失效、收尾、记忆、冷却和恢复。
- **应用接口 AI 闭环**：至少一条同样的委托由Abyssa请求rp的AIRP应用，完成大纲生成、文本展开／润色、受控状态整理、场景接纳与阅读，并在后续任务中引用已确认记忆；制作调试和实际运行使用同一后端执行链。

前一项不能代替真实模型验收；后一项新增受限任务的在线生成，不扩展为任意自由聊天、自主Agent或无限世界模拟。先本机联调，对外服务另验访问隔离与费用边界。

| 范围 | 首个可验证样本 | 完整 DEMO 目标 | 本轮排除 |
| --- | --- | --- | --- |
| 三轴 | 一条委托的时局、角色记忆、时空快照 | 四型事件共用可重复投影 | 向量库、完整世界模拟 |
| 卡池 | 3条出击链的简短稿；先落通其中1条 | 共20–30张：出击6–8、牵线4、家务4、小景6；基础组合20–22张 | 首轮堆满30–50张、实时无限构思 |
| 生命周期 | 一次接受、一次完成、一次重复提交 | 四型、两类失效各2–3例、备用库、64日主题账本 | 备用库模型改写、语义相似度模型 |
| 巡守 | 1个现有路线底板＋1个预制任务目标 | 2个经过配平的底板、4–6个预制特化定义 | 模型任意新增敌人、数值或路线 |
| 完整出击委托 | 1条从洋馆到巡守再回馆 | 3条可完整演示的出击链 | 全部卡均有独占美术和专属长篇演出 |
| 生成 | 既有作者骨架与手写稿 | 至少1条应用接口大纲→写作链、情境对照、实际接纳及后续记忆引用 | 任意自由生成、主线／羁绊阶段／回忆改写、自动主角代言 |
| 运行 | 保留现有前端与本地玩法存档 | Abyssa通过应用接口使用rp；单用户本机先行，公开运行单独验收安全配置 | 全量存档上云、共享世界、现实时间离线推进、必须桌面打包 |

首条工作稿已在AIRP-1登记为艾洛拉的“旧药箱的搭扣”，仅记忆反馈、无额外数值奖励；其余委托与特化敌人清单在后续内容阶段登记。工作稿不是用户已确认的新正典，不预占剧情中未解锁的角色或地图。

## 2. 部署与所有权

定稿为 **rp通用应用后端＋AIRP应用定义＋Abyssa游戏客户端**。不再做内容包导出／导入或浏览器内核移植。开发调试与实际游玩固定相同Release、Contract、Workflow和状态规则，运行Session彼此隔离。

| 层 | 拥有的状态与职责 |
| --- | --- |
| rp通用后端 | 模型槽、上下文编译、Workflow、资源／版本、原生Thread／Branch／Floor／Checkpoint、State／Updater、审计与恢复 |
| AIRP应用 | 人物／世界资料、三轴语义、分任务预设、记忆政策、输出和领域校验；复用通用能力，不另建引擎 |
| Abyssa | 既有Campaign、玩法事实／奖励／事件调度、本地存档；应用调用、玩法快照、场景接纳、阅读与AVG表现 |
| 模型 | 执行受限任务和叙事更新提案，无玩家游戏写权限 |

通用机制缺口在rp对应模块补齐，AIRP只定义策略。每项字段只有一个writer；首轮不迁移整个Campaign，不让rp Updater与本地reducer同时维护任务终态、奖励或冷却。rp持有叙事State和连续性记忆；Abyssa保存必要引用／冻结正文，已有Fact记忆经有来源的投影提供给rp。

先本机联调，前端通过应用接口连接rp；不需要将两个仓库合并或整体桌面打包。现有[资源加载契约](../../src/shared/loading/README.md)仍适用于前端资产，但缓存不等于在线AIRP离线可用。后端故障时保留已完成玩法与阅读，新的生成明确等待／失败／降级。构建与CI不调用真实模型。

rp当前只监听loopback且没有用户认证协议。若公开运行，须先落实认证、TLS、任务／实例访问隔离和限流费用边界，不直接暴露管理API。此决定不授权公网部署或可信云存档。

所有期限使用游戏时钟：`phaseIndex = (day - 1) * 4 + phaseOrdinal`，晨／昼／昏／夜依次为0–3。服务在线不意味着现实时间自动推进世界。

## 3. 概念与最小数据契约

### 3.1 术语

事件阶层使用 `canon | bond | echo | ripple`；涟漪型别另用 `sortie | liaison | household | vignette`。避免把原稿 `tier: sortie` 与“事件四阶”混为同一枚举。

初征、再战、回响战、巡守是叙事准入与表现分类。再战从未首通与已有失败／撤离事实派生，不另造战斗引擎；巡守基于已开放的维护玩法扩展，不能绕过庄园首通。

### 3.2 拟新增对象

以下为完整DEMO概念总览，不能将表格直接当作可导入schema。AIRP-1定义首条sortie契约，AIRP-2实现严格存档reader／事务，AIRP-3以独立契约2实现多卡四型、备用与失效。AIRP-4应用请求、叙事State及场景接纳边界以应用接口计划为准，新增字段必须通过正式契约演进。

| 对象 | 最少需要表达的内容 |
| --- | --- |
| `RippleDefinition` | 稳定ID／版本、阶层／型别、规范主题标签、触发前置、演员槽、目标模板、提供期、失效政策、奖励表、对白骨架与降级稿 |
| 应用请求与候选 | 固定任务／情境、rp原生运行身份、结果／修订、情绪与骨架绑定；候选不包含可执行奖励或任意状态patch |
| `RippleInstance` | 实例ID、定义／版本、状态、创建／提供／首次曝光／接受时点、确定演员、期限、目标绑定、选择、完成证据、终态／领取身份 |
| `PatrolBinding` | 委托实例、本趟 run、底板／注入定义与版本、目标实体或事件槽、证据要求、进入时冻结值 |
| 运行时冻结场景 | 游戏首次显示前接纳已校验结果，保存不可变正文、骨架、精确来源、正文hash与阅读关联；不只存远程URL |
| `SceneReading` | 场景身份、持久节点、已选分支和已完成状态；分页与动画缓存不授予奖励 |
| `MemoryEntry` | 持有者、来源Fact／事件、时点、主题、涉及人物、可见性、确定性摘要；文学细节另标作用域 |
| `CooldownEntry` | 规范主题键、来源终态、起止相位；不按角色或展示标题封禁 |
| rp运行与叙事记录 | 原生资源／Branch／Checkpoint／Result及应用记忆；调试与实际运行隔离，客户端不重建第二份权威库 |
| `NarrativeCampaignState` | 事件索引、任务占用、调度消费身份、记忆／冷却、生成内容引用和当前阅读；与已有剧情互斥规则 |

定义与实例分开，候选与已接纳内容分开。所有机械字段来自游戏规则；LLM的合法JSON仍须来源、语义与格式校验，不能自行成为玩法效果。

### 3.3 模块接线建议

- `game-core`：保留事件、目标、时间、冷却及纯玩法规则，不做网络请求。
- `game-application`：玩法投影、请求身份、结果接纳、阅读／选择和事实确认；模型等待放在本地事务之外。
- `game-infrastructure`／`game-runtime`：实现并装配rp应用API客户端；复用真实DTO，处理网络与精确结果查询，不编排多个模型调用。
- rp通用模块：复用资源／执行／状态／审计；确有通用缺口再补，不内置Abyssa字段。
- rp的AIRP应用：人物／骨架／预设、固定Workflow、State Schema、记忆策略与领域校验，沿原生扩展入口接入。
- `content`／`game-client`／apps：保留作者定义、手写降级稿、洋馆与巡守入口；调用后在原AVG中展示。
- `shared`：复用AVG校验、编译与演员表现，不反向读取存档或卡池。
- `llm/`：保留O1-W和预设提取／离线试验，不建设AIRP后端、发布器或第二套Workflow。

精确原生接口、SDK限制及跨端恢复见[接入计划§2](AIRP_4_APPLICATION_INTEGRATION_PLAN.md#2-原生接口与执行路径)与[状态权威](AIRP_4_APPLICATION_INTEGRATION_PLAN.md#3-状态权威与跨端接纳)。不跨仓库直接导入内部服务，不在React render或构建中调用模型。

## 4. 生命周期、调度与失效

### 4.1 事件状态与生成请求分开

```text
应用请求：冻结输入 → rp Workflow → 查询终态／校验 → 本地接纳 → 阅读／事实确认

事件实例：待命 → 已呈现 → 已接受 → 目标完成待交付 → 已解决
            │       │
            │       └─ 提供期结束／拒绝 → 留有历史的结束状态
            ├─ 从未曝光＋惰性过期 → 备用模板引用
            └─ 有后果过期 → 错过终态＋一次余波
```

家务与小景可以按定义从已呈现直接解决，不制造无意义的出征目标。小景也需合法阅读完成，动画结束本身不是状态证据。牵线委托通过真实目标角色对话的提交完成，不能靠打开任意聊天窗口完成。

首次呈现须将已校验剧本的冻结引用与曝光状态提交后再展示。生成失败不推进游戏时间或授予效果；迟到结果不能替换已展示的场景。跨端接纳与确认规则见应用接口计划。

### 4.2 首版推荐规则

1. 在普通远征归来、游戏相位变化、正典阶段完成等安全边界检查；按提交／相位保存消费身份，保证重复检查没有额外效果。
2. 新档须完成初章或具有合法旧档豁免后才开放自由涟漪；出击委托还要求对应巡守已开放。正典、成长与回忆的必需收尾优先。
3. 首条切片先限定一个活动出击委托。待命数、每日补充数和四型比例在模拟后配置，不将任意默认值伪称配平结果。
4. 提供期从事件可提供的持久时点计算。首版建议已接受委托不继续使用提供期限；如将来增加履约期限，单独定义，不能让已取得证据的任务在回馆对白中失效。
5. 从未被玩家看到的惰性候选可移入备用库；备用库存定义／素材引用和使用历史，不复用已结束的实例身份。重新提供时重新检查三轴与配额。
6. 已看见但未接受的惰性事件过期，保留已见历史，不再声称它从未发生。有后果事件保存唯一余波，允许后来一句引子回应，不硬扣好感或锁正典。
7. 冷却以规范主题键和结构化标签判定；64游戏日为原设计工作目标，即256相位。保留终态事实，过期只解除筛选禁用，不删除去重历史。
8. AIRP-1已登记：已解决、有后果错过、拒绝及已见过期均冷却256相位；从未曝光的惰性备用最早下一游戏日重查资格，不复活旧实例。
9. 有合法候选才补充；卡池耗尽允许空窗，不自动缩短64日或通过换标题绕过主题排斥。

### 4.3 关系与人物日程

首版以事件记忆和既有已解锁关系信息构建 Bond。微量好感数值、阶段阈值、设施状态变化是待补规则，不直接改动现有 Lv.1–3 成长。需要小奖励时先用已有可授予资产并单独配平，规则未定义则不发。

将实际需要的洋馆人物可达规则从展示排布中整理为共享内容与纯查询；起步只覆盖首批事件涉及的角色和房间。校验外出、活动远征、剧情占用与正确相位，确保牵线目标可达。固定背景装饰不冒充可生产或可修缮设施。

## 5. 三轴快照、人物资料与应用任务

### 5.1 组装职责

Abyssa生成有来源的合法玩法投影，rp从精确Branch／Checkpoint与版本资源组装本轮任务，冻结实际输入后执行Workflow。作者测试情境必须标明，不冒称玩家实际经历；客户端输入不成为后端State的替代品。

| 输入块 | 首版必需内容 |
| --- | --- |
| 固定政策 | 模型权限、主角控制边界、演员／情绪／资产白名单、格式与预算 |
| 静态资料 | 精简世界前提、人物动机／语言／关系基线、场所规则与少量范例，均有版本 |
| Agenda | 当前阶段、委托状态、承诺、相关结果、余波和主题排斥 |
| Bond | 已发生关系节点、选择与按知情／人物／主题筛选的有效记忆 |
| Locus | 游戏日期相位、地点、实际可达演员、已实现设施 |
| 任务与舞台 | 固定任务、骨架／目标结果、已选分支、最近已读片段及对白槽 |
| 来源 | rp Release／Contract／Branch／Checkpoint、玩法身份／head、实际输入与筛选策略；Child按需带父锚点 |

世界观、人设和用户定稿保留出处，不把情绪映射的一行direction当作完整人格，不常驻全人物与完整战报。

### 5.2 可见性与预算

记忆必须符合来源、分支、接纳／已读资格、故事时间和角色知情；不混入未来剧情、未选分支、撤回事实或内部RNG。首版共同对白采用在场者共同知情切片，私人记忆另行授权；规划者知道不等于演员知道。

逐块／逐条及总预算有上限；必需内容缺失或超限明确失败，可选内容稳定省略并留证据。rp的字段View不是逐条记忆检索；筛选在送模前完成，不能把全量秘密交给文本模型自筛。

### 5.3 模型与输出

采用大推理纯文字大纲→文本模型纯正文→小推理格式化／报错修复的原生Workflow，实际阅读后再由独立小推理Updater整理授权记忆提案；三个模型槽、四个任务预设，不强制三个不同型号。格式化及Updater的JSON边界错误均附上一轮原文与程序错误有限修复，不重跑创作。类酒馆预设提取有效模块／顺序／宏依赖与插槽，保留文本质量与正常虚构冲突；不照搬全套脚本，文学预设不套在后处理任务上。

最终展示结构仅要求前置可见创作记录、正文与14情绪，必要时验证说话者；这些字段由小模型封装，文本模型不输出JSON，不索取隐藏推理。选项、跳转、奖励和资产仍由作者／程序控制，不要求模型输出完整AVG。创作记录不混入玩家正文或记忆正文，不执行模型HTML／JS／CSS。详见[接入计划§4](AIRP_4_APPLICATION_INTEGRATION_PLAN.md#4-模型预设与上下文)。

保留[主角行为契约](../design/NON_LLM_PLAYER_AGENCY_CONTRACT.md)与已有作者定稿特例。新的14情绪、场景长度与在线来源须做契约演进，不放宽旧版校验。人工验收应用版本与样本文风，不设置每次在线生成都必须人工审批的发布器。

### 5.4 变量与记忆

rp原生State／权限／Updater／Checkpoint作为底座，补基础记忆契约、受控抽取、召回和来源失效；通用机制归rp，AIRP定义语义与策略。原文／修订、有效记忆、派生上下文分别处理，不另建数据库。

- 任务终态、奖励、关系阶段等硬变量由规则程序写；文本和摘要不能授予效果。
- 事实、人物认知、创作计划分开；大纲／可见创作记录不是已发生经历，候选不等于玩家已读。
- 条目有稳定ID、来源、故事时点、主题、知情、作用域及有效性；同源处理幂等。
- 采用改稿的分支内失效／替代相关条目并复核依赖资料，走新Floor，不追改其他分支和已读文本。
- 开发与实际运行Session隔离；已有Abyssa Fact记忆只投影到rp，不让Updater与本地reducer双写。
- 必需更新失败明确阻断后续依赖，不静默丢关键记忆，不建向量库、无限压缩或自主循环。

详细契约与证据见[接入计划§5](AIRP_4_APPLICATION_INTEGRATION_PLAN.md#5-变量与记忆)。药箱样本已具备已读摘要；多人物／多事件、长期容量和玩家改稿恢复仍未完成，不把总设计视作现有完整能力。

## 6. 巡守注入与委托证据

第一条出击链先选择现有维护路线中可表达的目标；题材由内容稿决定。最小实现可在已有房间完成后产生任务证据，不必一开始新增敌人机制。后续再逐步补足两个底板与预制特化池。

| 层 | 固定内容 | 允许的变化 |
| --- | --- | --- |
| 底板 | 合法路线、房间、敌群、退出与结算规则 | 从已发布的底板定义选择 |
| 注入 | 预制特化敌人／目标物／事件槽、任务证据与奖励映射 | 从白名单定义绑定一项，出征时冻结 |
| 表现 | 入场、目标说明、归来骨架与本地资产 | 手写变体或模型对白槽 |

LLM 不改写 Catalog，不把字符串敌人名转成新规则。新定义进入新内容版本；旧包与既有存档继续使用原引用和摘要。

证据必须同时限定：委托已接受、合法本地档案／epoch、匹配的本趟 run、目标实例／房间、有效而未撤回的动作、对应终局或带回政策。接受之前的击杀、历史回忆、其他任务、模拟以及作废操作不计入。

“击败目标”和“把证据带回来”由目标模板区分。撤离、团灭、继续下一趟、部分完成与重新绑定的规则必须明文定义；第一条建议使用成功归来可证明的简单目标。目标完成进入待交付，回馆提交一次领取与记忆，重复请求只读同一回执。

每条巡守模板需评估压力、资源与退出体验；给敌人换皮和增加对白不算完成战斗配平。AIRP 不自动解决既有庄园低压问题。

## 7. 存档、事务、版本与容量

### 7.1 需要一起落地的内容

事件出现、接受、选择、目标证据、终态、奖励、余波、记忆与冷却都需要合法命令和可验证来源。一个结算的终态、资产与沉淀在同一事务完成；重复提交、刷新或重播对白不能重发。

调度消费标记与本轮事件选择也需原子提交。若用随机抽池，独立保存叙事RNG来源／游标；不消耗战斗RNG，不在页面重挂载时重新抽取。

网络执行与玩家本地事务分开。请求先持久化、事务外调用，结果凭固定身份与当前head校验接纳；阅读／选择成功后幂等确认给rp。多窗口沿用CAS，迟到候选无领域效果。本地与rp不是同一个事务，不假装可以同时回滚；恢复与分叉规则见[接入计划§3](AIRP_4_APPLICATION_INTEGRATION_PLAN.md#3-状态权威与跨端接纳)。

### 7.2 导入、复制与旧档

- AIRP-2核对注册表后修订版本方案：新增内容8与独立AIRP契约1，沿用未变的记录／战斗协议4；内容8要求严格重放的narrative，旧内容禁止AIRP字段／命令，不接受任意可选JSON。理由见[AIRP-2版本决定](AIRP_2_IMPLEMENTATION.md)。
- 旧档不强制补做教程或已完成主线，不清空资产；从明确的合法状态提供显式升级或保持旧版，不能静默热改活动远征。
- AIRP-2原身份恢复保持完整引用；复制新身份仅允许安全边界，来源档案作为只读origin保留，不搬运活动委托证据。未来支持更广泛复制时再定义完整重映射；外部调用身份不得跨新旧档复用。
- 已接纳生成文本与必要身份进入玩家备份；只有外部URL或runId不足以恢复。恢复在线续写还须核对rp检查点；复制新身份不能共用可写Session或请求命名空间，不直接以旧备份覆盖后端较新分支。
- 二周目哪些记忆可以继承、哪些任务／冷却重置需单独列规则，不继承活动委托或凭旧领奖证据重复发奖。
- 验证失败时保留原档并报告，不通过补空字段或只改版本号掩盖缺失历史。

### 7.3 容量策略

现行记录存在8 MiB及集合上限，事实历史又会持续增长。AIRP-1的30张卡合成满额样本4,063,932 bytes；AIRP区域4 MiB硬上限。AIRP-2首条完整交付样本连同来源首通档422,652 bytes，叙事11,171 bytes；长期多卡／多祖先仍需复测。详见[容量方案](AIRP_1_CONTRACTS_AND_FIRST_ERRAND.md#8-容量测算与故障边界)与[实测](AIRP_2_IMPLEMENTATION.md)。

初版可优先采用有界的本地内容映射，避免将全部原始Prompt与失败输出塞入主存档；若需要独立内容store，场景引用与内容写入必须有原子性／完整性检查，导出需打包对应内容。无论采用哪种方式，已经可回看的文本、领取去重与关键事实不得因容量压力静默删除。

## 8. rp应用接入与开发验收

rp既用于制作调试，也服务Abyssa实际运行；AIRP是同一套应用资源、Workflow和状态定义，不是两套引擎。先用原生Session／Interaction／Timeline／Result接口接一条场景，不增加通用导出Port、内容发布器或任意业务HTTP路由。

准备与运行分别验收：应用资源／模型槽／预设固定成版本；Abyssa在合法场景提交冻结输入；rp执行固定纯文字大纲→纯正文→小模型格式化／报错修复，实际阅读后另运行授权Updater；客户端查询精确终态后校验接纳、阅读和确认实际事实。修复不重跑大纲／正文，开发fixture与玩家实例隔离，记忆来源和权限可追溯。2026-09-10分工与验收见[0.2.0报告](../audits/2026-09-10-airp-three-stage-acceptance.md)。

失败／取消／中断不伪造成功，不在后台无限修复；网络不明重放同一请求。已有手写稿可明确降级但不计入真实模型通过。首个切片先本机完成，公开运行再验身份隔离、限流和费用；普通构建不调用模型，旧内容8／9不被新稿覆盖。

详细接口、状态边界、记忆、4A至4D与验收只维护在[应用接口接入计划](AIRP_4_APPLICATION_INTEGRATION_PLAN.md)。

## 10. 验收矩阵

| 类别 | 必须看到的结果 |
| --- | --- |
| 正常全链 | 合法接受、真实战斗／探索证据、一次归来交付；角色回应符合事实 |
| 调度与失效 | 重复读取／刷新／多窗口不多补卡；正典优先、双轨失效、一次余波与64日冷却 |
| 目标隔离 | 旧击杀、回忆、其他run、未接受任务、撤回与伪造目标不能完成委托 |
| 事务与恢复 | 失败不损坏原档，重复领奖无收益；战中／待交付／收尾刷新可恢复 |
| 版本与容量 | 内容8／9及旧档保持兼容；新内容、备份复制、正文容量分别有实测 |
| 同一应用链 | rp调试与Abyssa使用相同Release／Contract／Workflow；实例隔离，原生执行与State可查询 |
| 真实模型 | 至少一条大纲→写作→授权状态整理链及两个情境对照，不能由手写降级代替 |
| 上下文与记忆 | 来源／时间／知情正确，计划不变事实；同源幂等，连续引用与改稿失效通过 |
| 接纳与确认 | 精确结果、分支、请求与本地状态一致；过期稿无效，已读场景不热替换，确认中断可恢复 |
| 故障边界 | 后端超时／中断、Updater失败、CAS冲突可见；本地与rp不假装原子提交 |
| 运行安全 | 本机先行；对外运行须认证／实例隔离／预算，前端无Provider密钥和管理权限 |

64日冷却另做可重复长时序模拟，不要求40分钟演示自然跨过64日。情境对照必须有明确来源，不能只展示随机文本差别。

按实际package命令分层验证rp应用／执行、Abyssa接口／事务／旧档和真实浏览器；构建与CI不调用真实模型。当前历史测试见各AIRP实施记录，不能当作新接线或文风通过。
