# 出征 GM 特殊鉴定物：最小接入计划

日期：2026-09-25。状态：已实施，验收记录见 [特殊鉴定物接入](../audits/2026-09-25-gm-special-appraisal.md)。原角色卡及既有 SHOP 台词未改写。

播放位置按用户补充明确为 **商店现有小对话框**：使用 `ShopCounter → ShopSurface → MerchantWindow`，不交给 AVG 播放器。

## 结论与首版范围

可以在现有链路上实现：程序在出征准备时预先确定奇物及品质、价位；现有副本 GM 在同一次规划响应中写完物品身份、介绍和缇比台词；校验并保存后才允许出发。战斗实际取得、带回、鉴定与出售继续由程序执行。

推荐首版采用“已有经济模板 + 每件实例独立文案”。现有掉落定义继续负责价格和真实交易，GM 为本次实例创作新身份。无需先实现通用动态道具库、新背包或第二套交易规则。

- 覆盖普通远征现有的奇物奖励位；目前相关路线各有两个机会位，提前抽样后通常需要生成一件或两件。
- 品质使用现有铜、银两档及已配置价位。先把品质映射移到程序可引用的规则处，UI 只读结果。不是让 GM 自选品质，也不是只在商店临时换边框。
- 若要金、紫、神话五档一起投入掉落，需要另加固定经济模板、概率和版本化内容；不将这些未定数值混入本次最小接入。
- 不增加普通掉落数量，不覆盖教程结界钉等作者物品，不把必须交付的委托物改成可售商品。

## 接入前勘探（历史）

下表记录实施前的缺口；现已完成，不作为当前未完成清单。最终行为与验证见[接入记录](../audits/2026-09-25-gm-special-appraisal.md)。

| 环节 | 当前实现 | 接入缺口 |
| --- | --- | --- |
| 出征规划 | `airp-expedition-gm` 已有完整输入冻结、校验、采纳、出发门禁与重试 | 同一响应增加鉴定物文案扩展 |
| 奇物掉落 | `loot-tables.ts` 按独立 loot seed 和房间地址确定结果，不消耗战斗随机流 | 出发前用相同算法只读预演，并冻结实例映射 |
| 品质与价格 | 品质目前写在 presentation；船灯环铜色，另外三种普通奇物银色；价格在 Catalog | 程序明确产出品质，校验与基础经济模板一致 |
| 委托物品 | `itemDefinitions` 已专用于可执行委托奖励，v1 要求数量等于委托数 | 鉴定文案不能直接塞进去挤占名额或触发委托校验 |
| 商店 | 已有外观、真名、介绍、选中提示、鉴定逐句播放、成交台词与记录 | 当前主要按 `definitionId` 读静态文案，缺少实例级覆盖 |
| 缇比材料 | 完整卡在 `st/setting/char/3-tibby.txt` | `director-documents.ts` 未收录她，当前出征材料不会自动提供完整卡 |
| 副本收获 UI | 未鉴定物隐藏真名与品质，按定义聚合 | 使用实例级未鉴定名称与外观；不同生成物不能合成一行 |

现有普通奇物的经济范围为鉴定费 300 G、未鉴定收购 2 G；已鉴定价有 600/800/1000/1200 G。首版沿用对应基础定义的数值，不新增价格随机数。程序抽中基础模板时同时确定品质与价位，GM 再围绕其价值创作身份。

## 数据与执行顺序

1. 玩家确认出征，程序确定 `runId`、路线、队伍与 seed，先用现有引擎在复制的游戏状态上只读验证出发资格。
2. 从这个副本状态取得实际 `run.rng.loot.seed`，按现有路线顺序预演奇物抽取。不能误把出征 seed 当成派生后的 loot seed；预演不写完成事实或库存。
3. 将会命中的奇物位、稳定实例 ID、基础定义、品质及报价保存到本次准备输入。GM 只收到必要的物品规格和场景依据，不收到随机种子。
4. 同一次出征 GM 调用写完所有槽位对应的文案，随后进行结构和引用校验，冻结到已采纳计划。
5. 出发门禁确认本趟应生成的每件物品都有完整文案，且与本次出征身份一致。此时完成的是设计，不是取得。
6. 战斗胜利／房间完成后，原掉落程序才产生对应实例。按原有逐层保管、撤离和团灭规则决定最终带回哪些物品。
7. 商店按真实拥有的 `runId + instanceId` 查找对应冻结文案。鉴定成功后揭示真名和品质；出售成功后播放成交台词。此处不再请求模型。

目前路线为顺序推进；预演必须测试所有可执行前缀与实战结果一致。以后若允许跳过不同奇物房间，需重新检查无重复抽取的依赖，不能直接假设整条路线预演仍等于分支结果。

## 建议的最小字段

已采用新准备输入标记 `appraisalPlanVersion: 1`，仅在启用时要求新字段。以下为设计摘要；完整现行字段以[合同](../../src/game-core/contracts/expedition-appraisal.ts)为准。

程序冻结输入：

```ts
appraisalSlots: Array<{
  key: string;
  instanceId: string;
  grantId: string;
  baseDefinitionId: string;
  roomDefinitionId: string;
  rarity: "bronze" | "silver";
  appraisalFee: number;
  salePrice: number;
  scrapPrice: number;
}>;
```

GM 响应追加独立数组，与委托 `itemDefinitions` 并列：

```ts
appraisalItems: Array<{
  slotKey: string;
  unknownName: string;
  appearance: string;
  name: string;
  description: string;
  selectUnknown: { text: string; emotion: string };
  selectKnown: { text: string; emotion: string };
  appraisal: Array<{ text: string; emotion: string }>;
  sold: { text: string; emotion: string };
}>;
```

- 程序掌握数量、地点、掉落条件、品质、报价、实例 ID；GM 只回填槽位引用和文案，不能改数值。
- 每个槽位恰好一条输出，无槽位时输出空数组。首版容量单独按当前最多两个奇物位设置，不占委托四件定义预算或叙事节点预算。
- 复用整个计划的哈希、原始响应和保存流程；不要为文案另建独立数据库或再发一次模型请求。
- 建议鉴定为 1–4 句可逐句播放的中文；其他提示各一句。表情从缇比现有支持值中选取，不增加立绘或动作系统。
- 收好物品、未鉴定出售、未鉴定废料报价可以使用新的通用中文提示，避免为辅助状态多生成一整组台词。不能回退到某个固定物品的专属台词。
- 图标复用现有 `resolveItemIcon` 关键词权重匹配器：未鉴定只用公开的未知名称，鉴定后用真名及程序品质；未命中使用匹配器自带的杂物袋兜底。商店、掉落通知、收获／结算及日志保持一致。GM 不返回图片 URL，也不读取隐藏文案提前选图。

独立数组比扩展通用道具定义更小：当前委托校验要求每个定义挂到叙事节点，鉴定文案本身不需要新增节点；程序房间奖励位已经足够证明来源。若 GM 正好安排了相关探索节点，可承接实际发现，但跳过对白不影响物品取得。

## 缇比与创作约束

- 仅在新启用的出征鉴定规划中附带缇比完整角色卡，按既有文档机制冻结原文及哈希；不扩大每日 GM 常驻材料。
- 她是未来商店台词的写作参考，不加入副本队伍或节点演员能力。全局文档选择后仍须保留这份明确要求的参考卡，并校验缺失。
- 只为鉴定物字段开放 GM 写台词的权限。其他副本节点仍遵守现有“规划不写正文／演出”的分工。
- 台词全部中文。鉴定台词通过眼前物件的材质、痕迹、用途和价值体现她的判断及态度，不把角色标签列成每件物品都必须重复的口癖清单。
- 她可以辨认物件来历，不能预知玩家尚未完成的战斗、取物过程或未来分支。预写文案是待触发内容，不自动成为已读经历或公共记忆。
- 具体报价由界面显示。首版提示词要求台词不报具体金额、不使用变量占位符，避免另加模板替换机制。

## SHOP 与副本界面对接

| 实际操作 | 使用的内容 |
| --- | --- |
| 副本拾取、未鉴定列表 | `unknownName + appearance`；品质仍显示未知 |
| 选中未鉴定物，鉴定页 | `selectUnknown`，不提前讲真名与完整用途 |
| 选中未鉴定物，出售页 | 通用废料收购提示，使用真实 2 G 报价 |
| 鉴定交易成功 | 揭示名称、介绍、品质，并播放 `appraisal[]` |
| 选中已鉴定物 | `selectKnown`；不能继续借用鉴定最后一句或“收好”代替选中提示 |
| 已鉴定出售成功 | `sold` |
| 未鉴定直接出售成功 | 通用未知物成交提示，不能播放泄露真名或正常售价的 `sold` |
| 鉴定回看、出售历史 | 保留该实例原来的冻结文案，不读取最近一趟的同类型文案 |

关键细节：

- 生成物在 UI 中逐件列出；查询和交易入口同时约束其批量出售，防止旧堆叠逻辑一次消费其他不同身份的物品。
- `repeatAppraisal` 当前按基础定义识别“又一件”。生成物必须退出这套判定，不能因为共享经济模板就跳过自己的鉴定台词。
- 战斗收获视图当前也按 `definitionId` 聚合；生成实例需要独立展示 key，数量、背包归属与损失算法仍按真实掉落处理。
- 只给玩家和副本正文提供已取得物品的公开字段。GM 规划、共享计划与后续正文投影需检查隐藏字段边界；持有预写鉴定稿不代表角色已知。
- 商店鉴定后才揭示内容，但第一次播放鉴定稿需要随成功回执取得对应文案，不能继续使用交易前的过期视图造成空白。
- 旧物品沿用原静态展示与首访适配。现有初访中文台词、结界钉分支和立绘发言高亮规则保持原实现。

## 持久化和恢复

- 文案按已开始计划、runId、instanceId 精确匹配；归队后、再次出征后和出售后仍可解析旧物品及记录。只读“当前计划”是不够的。
- 新准备输入显式启用新协议；旧冻结计划和正在进行的旧远征不自动补物或改稿。旧存档后续新出征可启用，原有库存继续静态展示。
- 更新出征依据或重试可以重新生成尚未采纳的文案，但同一 runId/seed 的品质、报价和实例映射不能重抽。
- 保存失败重试保存已有响应；接口失败按现有 GM 恢复流程处理。缺稿不静默进入副本，正常接入不增加额外模型阶段。
- 真实掉落、鉴定、卖出依旧使用现有幂等交易和事实重放。文案层不得再发一次道具或金钱。
- 旧协议的解析／提示词版本需继续被读取。首版不修改已有 Catalog 内容或经济曲线；若后续新增品质经济模板，再按内容版本发布。

## 实施顺序与落点

1. **程序规格与规划协议**：建立经济模板→品质的权威映射及只读奇物预演；扩展 `airp-expedition-plan` 合同、解析、计划校验和 output schema。确认每个实例都能由既有掉落重新验证。
2. **单次 GM 接入**：在 `airp-game/host.ts`、`projection.ts`、`airp-expedition-gm/d5-source.ts` 和 `context.ts` 接入新准备版本及缇比参考卡；更新新版本提示，保持原有重试和采纳流程。
3. **实例展示与商店触发**：提供统一的实例文案解析器，由 `versioned-views.ts`、`ShopPage.tsx` 和副本 loot view 使用；调整 `ShopCounter.tsx` 的选中、重复鉴定和未知出售提示，并处理生成物批量出售约束。
4. **保存、公开投影与完整验收**：检查计划共享、历史解析、出发门禁、恢复和旧计划；完成从出征准备到售出的闭环后再启用。

这四步是一批最小闭环，不能只交付 GM 输出字段而遗漏真实物品与界面。

## 验收重点

1. 同一出征反复预演／重试，品质、实例、价格一致，战斗与普通素材随机结果不变；每个可执行路线前缀都与真实掉落吻合。
2. 同一次 GM 请求包含完整缇比卡，并产生全部对应文案；没有额外鉴定模型调用。缺稿、额外槽位、伪造品质或越权数值不能通过。
3. 带委托同时出征：委托物与特殊奇物都按各自真实条件取得，互不覆盖；未战胜、未到达的奖励不能提前入库。
4. 拾取、撤离、团灭严格沿用普通奇物规则，不误用委托物“团灭全丢”的规则。计划存在不代表物品拥有。
5. 未鉴定不露真名／品质；鉴定、选中、正常出售、未知出售各触发正确台词；失败或重复点击不提前播成交，也不重复扣钱。
6. 两趟生成物共享同一基础经济定义时，名字、描述、鉴定稿与记录独立，不能错误堆叠或触发“又一件”的固定稿。
7. 刷新、导出导入、售后历史和继续新远征仍读取原稿；初访剧情、旧库存、已开始旧远征和非 GM 模式保持兼容。

程序集成、存档恢复、商店交互及构建验证已实施；测试中的 GM 响应明确使用模拟数据，未将其当作真实模型文风验收。
