## 1. 方向与职责

**rp-style-lab是通用应用后端，也是制作调试平台；AIRP是其上的应用定义；Abyssa是调用该应用的游戏客户端。** 制作与实际运行使用同一套Release、Interaction Contract、Workflow、状态规则和输出契约，不再通过“导出文稿→另一个叙事引擎”对齐。

| 层 | 拥有的职责 | 不承担 |
| --- | --- | --- |
| rp通用能力 | Application／资源／Release、模型槽、上下文编译、固定Workflow、State／Updater、分支／检查点、幂等、恢复与审计 | Abyssa角色、委托、战斗奖励、AVG专用规则 |
| AIRP应用定义与领域模块 | 三轴语义、人物资料、任务预设、大纲→写作→格式化流程、叙事State Schema、记忆策略、输出约束 | 第二套模型调度、状态库、分支系统或审计框架 |
| Abyssa游戏应用与客户端 | 现有玩法规则与事实、调用时机、玩法输入投影、请求绑定、场景接纳／阅读、AVG表现与本地存档 | 复制rp的运行内核、直接调用Provider、另建正式叙事数据库 |

通用就是通用：若实施中缺少可复用的条目筛选、预算或输入证据能力，应按通用契约补在rp对应模块；AIRP只配置其语义和策略。不把通用功能藏进AIRP专用服务，也不为尚未需要的能力另起平台。已有功能先复用，领域校验通过应用扩展接入。

“同一套运行”指同一后端执行链与版本定义，不是制作和玩家共用同一个Session。调试实例与实际运行实例隔离；同一冻结输入的确定性规则一致，不要求模型每次生成逐字相同。

取消当前主线中的内容发布器、导出Port、公开内容包、游戏导入器和浏览器版rp内核。普通前端构建仍可使用现有Vite与静态资产，但启用AIRP生成需要连接rp；不再以“关闭后端仍有完整AIRP能力”为验收条件。不要求把两个仓库打成一个桌面程序。

## 2. 原生接口与执行路径

### 2.1 首条调用路径

1. 在rp配置AIRP应用与精确Release、三类逻辑模型槽、固定Workflow和状态Schema；调试与Abyssa使用同一版本定义。
2. Abyssa为一个明确的游戏运行身份绑定独立Session，保存Release、Thread、Branch及检查点引用。开发试跑用其他Session，不按每个角色创建聊天库。
3. 在合法事件边界，由现有游戏应用层生成有来源的玩法快照，冻结任务、骨架、演员、内容版本和请求身份；持久化待处理请求后再调用接口。
4. rp接收Interaction，核验输入，从本分支State、授权记忆和版本化资源组装上下文，执行大纲→文本→小模型格式化Workflow。JSON及正文保真校验失败时，只重试格式化节点，并提供冻结正文、上一轮格式化原文和具体校验错误；本版最多两次尝试，耗尽后明确失败。
5. Abyssa根据响应定位精确Floor、终态检查点与结果，校验对应任务和本地状态，转换成原AVG可消费场景，经合法本地命令冻结后展示。
6. 实际阅读／选择和玩法结果仍由游戏规则提交。需要进入后续叙事记忆时，沿同一应用的Interaction接收这些已提交事实，不根据“生成了这段文字”推定玩家已经经历。

以上是固定任务流程，不是自主Agent循环；不在外层串联多个Manual Invocation重造调度。首条样本继续使用“旧药箱的搭扣”的一个归来场景，再验证下一场确实读到已确认记忆。

### 2.2 已有接口与调用约束

依据：[rp后端API](../../../rp-style-lab/docs/reference/backend-api.md)、[Interaction路由](../../../rp-style-lab/server/src/routes/conversation-threads.ts)。下列路径均位于`/api/v1`下；业务payload与Action现已由[在线契约](../../src/game-application/airp/contracts.ts)及rp AIRP应用固定，仍复用通用路由，没有AIRP专用HTTP接口。

| 目的 | 现有入口 | 接入要求 |
| --- | --- | --- |
| 创建运行实例 | `POST /sessions` | 指定`applicationReleaseId`；创建时冻结运行上下文与模型绑定 |
| 读取实例与分支 | `GET /sessions/:sessionId`、`GET /conversation-threads/:threadId/branches`、精确Branch的`context`入口 | 不靠界面的active分支或标题猜测来源；更新模型绑定须显式走原生Context操作 |
| 提交应用动作 | `POST /conversation-threads/:threadId/interactions` | 使用`submit-interaction-command-v2`，绑定Contract版本、`actionKey`、`branchId`、`expectedBranchHead`和`clientRequestId` |
| 核对提交与状态 | `GET /conversation-threads/:threadId/timeline` | 按返回的`floorId`查找并核对Checkpoint；分页至找到目标或耗尽，不取“最后一楼”代替 |
| 查询执行与正文 | `GET /runs/:runId/execution`、`GET /runs/:runId/result` | 从目标Floor的执行引用定位；成功拿到`outputText`不等于状态已提交或场景可以被接纳 |

首个Root Floor可使用空Branch head；后续使用直接上一terminal检查点的Floor ID、Checkpoint ID和hash。冲突后重读权威对象，不自行递增revision；网络结果不明时重放同一ID和相同内容，不另发新请求。

上述幂等重放适用于Interaction，不应误套给Session创建：当前`POST /sessions`没有原生幂等键。已实现的创建恢复只按精确存档／模式／Release标识查回唯一的未使用实例；玩家接线以Web Locks串行化同origin创建，并在取得锁后重读存档，双窗口丢失响应恢复已验证。这不是跨设备或后端强幂等；如需该保证，应补到rp通用Session能力中。多个匹配或已被使用的实例均明确阻断，不按标题／最新实例猜测。

基础Workflow走Managed Interaction主执行链。若选用V9可选Presentation，必须显式请求SSE；它是提交后的advisory结果，不能承载必须影响状态的步骤，也不能把Presentation失败当成机械检查点回滚。通用HTTP生命周期在优雅关闭时取消在途执行，等待handler的终态／清理工作结束后才关闭数据库；异常退出遗留的running执行在重启时收口为interrupted。两者都不保证自动续跑，客户端仍须检查精确终态，不能把取消当成回滚。

优先使用已有通用入口，不为每类AIRP任务新增HTTP路由。Package SDK仅提供Program、derived、Validator、终态Materializer等窄扩展，不允许直接查库、注册任意路由或调用Provider。缺口在4A核对后按原生机制补齐；Application Archive不是运行时协议，也不再是接入前置。

### 2.3 楼层、分支与资源

- Application／Release固定应用能力和资源；人物、骨架、提示词使用有版本的资源，不只留在浏览器缓存。Package-managed资源按原生安装／升级流程变更，不假设全部Artifact都可直接保存Draft。
- Floor是一项语义动作的提交单位，一楼可以包含大纲、写作与Updater，不按每次模型调用拆楼。
- Branch用于状态隔离和替代历史，不自动映射为AVG选项；游戏选项由作者／规则定义。
- 首轮优先Root Thread，无需求不建Child。确需子区时沿用原生父锚点和`isolated-initial`、`snapshot-copy`或`frozen-readonly-reference`模式；子区影响父状态必须经过可信接收与CAS，不能复制JSON覆盖。
- 原始Result与历史检查点不可被改稿覆盖。正式人工修订走合适的原生版本入口；不新增本地`approved`字段充当后端权威。

## 3. 状态权威与跨端接纳

### 3.1 每项数据只有一个写入权威

| 数据 | 首轮权威 | 另一端持有什么 |
| --- | --- | --- |
| Campaign、战斗／目标证据、资产、任务终态、冷却及既有Fact记忆 | 现有Abyssa合法命令／事务 | rp接收有来源的只读玩法投影，不重新结算奖励或运行第二份调度器 |
| AIRP应用资源、执行、分支叙事变量与连续性记忆 | rp资源与原生State／Checkpoint链 | Abyssa保存精确引用及必要的展示／恢复副本，不另设可编辑权威状态 |
| 生成候选与其状态 | rp目标Floor／Result及应用规则 | Abyssa持久保存待处理请求与结果接纳身份；未接纳文本不成为游戏事实 |
| 玩家实际看见的场景、阅读游标和选择 | Abyssa冻结场景及本地提交 | rp通过明确的事实接收动作获得阅读／选择证据，用于后续叙事 |

保留AIRP-1至3的玩法闭环，不把整个Campaign迁入rp，也不让Updater与`reduceAirpPoolCommit`双写同一字段。现有Fact记忆是玩法事实；rp记忆是有来源的叙事记录与连续性。两者使用引用与受控投影衔接，不各自推断对方状态。未来若迁移某项权威，须连同writer、验证和恢复一起切换，不能隐式双写。

生成时形成的计划或文学细节只能标为候选／场景连续性；后续任务仅在接纳条件满足后使用。已接纳场景也不等于已读完，更不等于完成委托。

### 3.2 最小一致性规则

本地存档与rp数据库不是一个原子事务。只在现有应用层增加必要请求／回执状态，不另建通用分布式任务平台：

- 发送前固定游戏运行身份／epoch、事件／场景、任务／内容版本、玩法head、rp分支与输入摘要，保存稳定请求ID。恢复时据此查询或重放同一请求。
- 结果接纳必须核对原请求、终态、来源和仍适用的本地状态。事件已变化、撤回、切档或分支不符时，结果留在rp审计中但不得推进游戏；UI取消不等于后端已回滚。
- 正文与场景引用在一个本地事务内冻结，接纳重试不能产生第二场或重复奖励。网络等待不得占用本地存档事务。
- 本地阅读／选择提交成功后再向rp确认；确认不明时保留待确认身份并幂等重试。在必需记忆确认前不开始依赖它的下一场；rp故障不回滚已完成的战斗。
- 冲突、模型失败、Updater失败和文本不合格分别可见。required步骤失败不能冒称全链成功；是否重新生成由明确重试决定，不做无界自动修复。
- 手写稿可作为显式降级路径，但也必须冻结自己的场景来源；降级后到达的模型稿不得替换已展示内容。降级不计作模型接线通过。

恢复备份中的本地head不能直接覆盖较新的rp分支。4A须定义精确检查点核对与恢复策略：能匹配则续接；分叉恢复沿原生Fork／新实例处理，否则明确阻断在线续写。复制新游戏身份不得共享原请求命名空间或可写Session；旧本地档继续可玩，不在本轮自动迁移。

## 4. 模型、预设与上下文

### 4.1 三类用途与最小输出

| 用途 | 输入与职责 | 产物 |
| --- | --- | --- |
| 大推理 | 作者骨架、受控情境、人物动机、相关记忆 | 纯文字大纲、因果与节拍，不要求 JSON |
| 文本 | 大纲、必要资料与视角边界、独立文本预设 | 纯文字文章／台词／旁白，不承担 JSON、情绪标签或变量 |
| 小推理：格式化 | 冻结正文＋大纲＋角色映射；修复时另附上一轮原文和程序错误 | 可见创作记录及 `lines[{speaker,emotion,text}]` JSON；不得改写正文 |
| 小推理：读后更新 | 可信已读结果、授权State View、更新政策 | 严格JSON状态／记忆提案，交原生校验提交；不是生成时写记忆 |

三类模型、四个独立任务预设：格式化与读后更新复用 `model.updater`，但不共用任务提示词。基础为三节点Workflow＋独立读后State Updater；不引入自主循环。格式化输入不重复携带全部玩法事实／记忆；文学预设仅用于文本节点。失败修复不能回退重跑大纲或文本，也不能凭生成成功写记忆。文风人工验收是应用版本与样本的质量门槛。

文本情绪固定使用现有14词：`neutral smile joy sad angry surprised serious closed wry flustered displeased confident confused panicked`。前置创作记录是显式可见检查，不索取模型隐藏推理，且不混入玩家正文。模型不生成完整AVG程序；场景／说话者绑定、选项、跳转、奖励、规则和资产由作者定义与代码控制。多人文本只增加必要的说话者可验证标识。

当前AIRP三情绪、短场景及`handwritten`来源限制仍是旧版事实。在线结果与14情绪适配必须走新契约／兼容测试，不能为新功能静默放宽旧档解析器。

### 4.2 类酒馆预设

以`/Users/liuhang/Downloads/Kemini_Dramatron_v3.0.json`为参考，提取有效提示模块、启用顺序、宏依赖、上下文插槽及必要历史处理；不执行全部脚本，不把整个JSON直接塞成system prompt，不建设完整酒馆兼容层。

- 基础预设：任务与事实边界、资料插槽、宏解析、权限、格式和预算。预设宏不是游戏变量。
- 文本特化：口吻、视角、节奏、自然对白、反机械复述与必要创作检查，不套给状态模型。
- 保留正常虚构冲突、反说教／过度净化及自然结尾；删除NSFW、绕过硬安全限制、防截断填充和无关显示脚本。混合条款按句处理，不把全部COT或反说教条款一起删掉。
- `llm/`既有O1-W七场／双语／本地审稿流程保留，AIRP独立配置；该目录不是新的运行后端或编排器。

### 4.3 送模组装

固定资源与权限→已提交玩法投影＋本分支授权State→Agenda／Bond／Locus与有效记忆切片→分任务预设／骨架→rp编译并冻结实际输入→Workflow。Abyssa负责玩法事实提取，rp负责权威叙事状态和最终任务输入，不能把客户端上传JSON当作后端State。

每次保留资源／Release／Contract版本、Branch／Checkpoint、玩法输入来源、筛选策略与条目ID、预算省略及实际输入证据。原始人设不是情绪映射中的一行方向提示；不常驻全人物、全战报和无限聊天历史。

首条药箱样本现已补齐版本化语义资源：三种接受安排逐字对应游戏选项，`phaseIndex`明确换算为游戏日与晨／昼／昏／夜，场所解析为公共休息室；实际撤离／完成结果与接受时的打算分开。大纲与文本共享这份上下文。Bond只引用已确认记忆与公开同伴基线，未提供的羁绊节点／关系阶段、设施和天气明确留空缺，不能让模型自行补齐；不据此声称已实现全部关系系统同步。资源漂移由[跨仓库语义校验](../../scripts/verify-airp-rp-context.mjs)核对，不在rp通用层写入Abyssa编码。

## 5. 变量与记忆

rp已有State Schema V2、稳定ID集合、写权限、Candidate Engine、Updater、Ledger与检查点，足以承载基础有界记忆；[状态文档](../../../rp-style-lab/docs/architecture/narrative-state-system.md)仍明确没有完整Memory系统。[View](../../../rp-style-lab/server/src/narrative-state/domain/view.ts)只做字段投影，不自动按条目知情人、主题、时间检索。

首版补齐四件事：记忆条目契约、受控抽取更新、送模前筛选、来源失效处理。通用存储／验证／筛选机制复用或补入rp；什么算AIRP事实、人物认知、文学连续性，以及何时接纳／失效，由应用策略定义。不另建Memory服务、向量库、无限压缩或知识图谱。

条目至少有稳定ID、类别、有界摘要、人物／主题、故事时点、知情范围与依据、精确来源和分支／场景作用域、有效性及替代关系。事实、人物认知、创作计划分开；人物可能误解或说谎，大纲与前置创作记录不能自动记为已发生。模型不能自授`approved`或凭正文改变奖励、任务和关系阶段。

抽取只提交授权字段的提案，程序核验来源和幂等身份，再走原生Proposal／Validation／Ledger／Checkpoint。沿用accepted-change／accepted-noop／rejected和有限Provider／格式重试语义，不把语义拒绝重试成成功。必需更新失败须阻止依赖该记忆的后续动作，不能扫描“最近成功一楼”绕过失败终态。

召回依次检查分支／继承、来源有效性、候选／接纳／已读资格、故事时间、知情与任务范围，再按人物／主题和稳定顺序选择。必需项缺失或超预算明确失败，可选项确定性省略并留证据；不让文本模型从全量私密集合自行保密。规划者获准知道的秘密不等于演员知道；首版共同对白使用在场者共同知情切片。

改稿只在采用新稿的分支内失效／替代相关记忆，并复核依赖摘要与后续产物；通过新Floor提交，不覆盖旧Result、旧Checkpoint、其他分支和玩家已读文本。同源重复处理不重复新增，摘要不得无限递归覆盖精确依据。开发候选与实际运行实例隔离，不把测试记忆当成玩家经历。

已参考Abyssa的[记忆语义](../../src/game-core/contracts/airp.ts)、[筛选组装](../../src/game-core/session/airp-context.ts)与测试案例，在rp AIRP应用中落实受控输入、共同知情筛选和已读摘要；精确原文使用通用`same-branch-terminal-output`可信来源，不跨仓库直接导入内部服务。原生精确检查点Fork及分支内记忆失效已通过后端测试：修改分支不改原检查点，工作台切换active分支不改变显式Branch请求的输入；这不等于玩家端已提供改稿或自动Fork界面。

## 6. 接入与部署边界

先用本机rp与Abyssa开发环境联调，应用接口是正常前后端调用。rp当前默认`127.0.0.1:8787/api/v1`且没有用户认证协议；开发代理／精确来源配置在接线时核对。不把该本地接口直接开放公网，也不在浏览器存Provider密钥。

公开试玩若需要远程访问，须先配置认证、TLS、任务与实例访问隔离、限流和模型费用边界；公开客户端不能获得完整管理API权限。当前Session／participant身份不等于安全的多用户隔离。公网部署不是本轮已执行或已授权的操作，也不是本地4A开工前置。

本地玩法输入的结构校验与hash只提供一致性，不证明客户端不可篡改；本方案不承诺服务器防作弊、可信资产或云存档。旧玩法和已冻结阅读的离线行为保留，新的在线AIRP任务在后端不可用时须明确等待／失败／降级。
