# 战斗动效管理与敌方舞台性能优化

日期：2026-09-18。状态：B1～B3 已实施，B4 检查与限制已记录，B5 换层载入衔接已修复；未做真实存档的前后 FPS／GPU 对照。

## 目标与边界

保留更新后的敌人美术、悬浮聚焦、生命珠、意图连线、死亡后补位，以及现有骰子、攻击、治疗和 AVG 节奏。减少无关测量、布局写入、过大 React 更新和被遮挡时的装饰绘制。不引入新动画库，不重做 UI，不处理暂缓的整备长帧。

规则与已提交事件不变：动画只消费视觉副本，命中帧不能重复提交伤害；撤销、连续击杀、场景切换和卸载均须保持可取消、可接续。

当前是共享基础加专用演出：UiModal 管普通窗口，SceneSequence 管场景，usePresentationQueue 管战斗事件队列；骰子、敌人补位、光带与 WebGL 雾仍由适合它们的执行方式播放。此次统一的是管理策略与更新边界，不将所有效果迁成 Motion。

## 已确认的源码问题（不等同于实测 FPS 归因）

- useEnemyStageLayout 捕获整个战场的 animationend，骰子和命中特效也触发全量敌区测量；字体、图片、ResizeObserver、resize 事件未合并。
- 每个敌人的图片尺寸写入与意图 offsetWidth 读取交错；补位每帧改 left，并重新查询连线路径。
- 敌人悬浮状态位于 ExpeditionBattleSurface，连带执行我方区域和画框渲染；敌区内联 ref 会反复注册教学锚点。
- 雾、队友光带和意图流线对前景忙碌、窗口遮挡、后台、手动减弱的处理不一致。
- 骰面已有 memo、局部绘制隔离，雾已有 640px 内部宽度上限，敌人血量珠最多 8 个。没有证据要求先降低这些美术细节。

## 实施批次

### B1：敌区测量与补位

1. 保留必要的首次／拓扑变更同步定位；外部图片、字体、尺寸与相关动画事件在同帧合并测量。
2. 仅接收会改变敌区或队友列几何的动画结束事件，不因斩线、闪光、骰子起跳等重测。
3. 批量读取文字和目标位置，再批量写入布局。缺口宽度如依赖新排版，集中进行第二批读取／写入，不按敌人数交错强制布局。
4. left 作为固定目标布局，补位只更新横向 translate；与原入场／受击属性分工，终态释放临时图层提示。连线端点与单位共享原 420ms 时钟。
5. 缓存动画期使用的元素／路径引用；不新增逐帧 React state，也不每帧查询 DOM。
6. 测试同帧合并、无关事件忽略、连续击杀／撤销接续、缩放、后台、减弱和卸载。

### B2：敌方预览的局部更新

1. 将敌方区域提取成独立组件，保留原 DOM 布局与样式，悬浮／键盘预览状态局限于该区域。
2. 稳定敌区与教学锚点的组合 ref；不因一次悬浮注销／注册舞台。
3. 预览只允许一个目标；触屏按下预览、抬起解除，键盘可恢复，攻击和补位时禁止预览。
4. 用渲染计数／锚点稳定性测试证明悬浮不会重新渲染我方区域、画框和骰盘。不能把 React render 减少直接称为 GPU 性能提升。

### B3：战斗装饰播放策略

1. 增加轻量 battle motion policy，消费现有 useUiMotion 和页面可见性，不增加常驻全局 RAF。
2. 窗口遮挡／场景锁定／后台／减弱时冻结装饰；前景攻击、治疗、掷骰、敌方行动、补位期间暂停流线，雾复用现有 8fps 降频。正常雾保持 24fps。
3. 保留已经生成的雾与光带形态，恢复不重新创建 WebGL 上下文；不修改权威战斗队列的时序。
4. 策略变化与卸载清理必须有测试。手动减弱在本批覆盖装饰与补位，不宣称整个战斗执行队列已统一该偏好。

### B4：验证与后续边界

- 运行敌区、补位、雾、光带、场景交接及正式／兼容战斗的相关测试，应用类型检查和正式游戏构建。
- 有可用浏览器入口时检查正常／密集阵容、悬浮、补位、手册遮挡与恢复，确认无跳位、连线脱节、重复入场。
- 性能证据分层报告：确定性测试证明不必要工作减少；浏览器采样才用于长帧／绘制收益。没有当前场景的同条件对照就不宣称 FPS 提升。
- 图片派生尺寸、滤镜／阴影简化和骰面材质调整留待实际 Paint／Raster 证据，不在本次顺带改动。

## 实施结果

### B1：测量与位移

`src/apps/battle/presentation/useEnemyStageLayout.ts` 保留原 420ms 曲线。外部几何通知合并为一个 RAF，animationend 只接收敌人入场与队友列入场。文字／目标列读取、布局写入、意图缺口读取、缺口写入分批进行。重复样式不再写入；尺寸缓存随 formationKey 重置。

补位使用固定 left 加临时 translate，结束释放 will-change。SVG 路径节点在提交时缓存，单位与连线共享同一时钟；逐帧不读取几何、不查询 DOM、不 setState。连续击杀和撤销从当前显示位置接续；减弱动态、新场景和隐藏页面会收敛到终态并清理时钟。

### B2：局部预览

新增 `ExpeditionEnemyStage.tsx`，迁移原敌方 DOM 与悬浮／焦点状态；未增加视觉包裹或修改美术。预览属性移到敌区 section，两个相关 CSS 选择器同步修改。键盘输入模式仍由主界面捕获，敌区组合 ref 使用 useCallback。

渲染计数测试确认鼠标进出时画框、我方成员读取、骰盘渲染次数不增加；真实 TutorialStore 的 revision 不变，正常父级渲染也不重注册敌区锚点。

### B3：装饰策略

新增 `useBattleMotionPolicy.ts`，复用 useUiMotion，集中读取可见性、遮挡和前景忙碌状态。EnemyMist、AnimatedPartyLink 与意图 CSS 流线消费同一策略；组件不再各自维护一套系统减弱判断。

雾暂停保留当前图像与 WebGL renderer，恢复不重编译；后台尺寸变化延迟处理。队友光带保留暂停形态与播放时间。战斗事件队列、骰子入场、命中、治疗、死亡时序与数据提交未改动。

## B5：旧庄园换层载入闪屏的定向修复

### 原因与复现

用户反馈进入下一层时会闪出一个界面，尚不能辨认是否为载入页。检查发现两件不同的事：遭遇中的双白闪是既有设计；`.battle-scene-preparation` 整屏暗色页则是素材准备与视觉切层没有衔接好。

修复前，目标房间开始显示后才准备其资源，固定时间的遭遇演出却不等资源，导致中途插入“正在准备战场／克雷格旧庄园 · 服务走廊”。新增 `ManorRoomLoading.test.tsx`，通过真实游戏命令推进到阅读完成节点，再延迟下一房间的 `prepareImages`：原代码在 680ms 步行、1200ms 遭遇和 240ms 白闪后稳定出现该整屏页，断言失败。此证据确认这条载入路径的问题，不等于已拍到用户当时那一闪。

### 实施边界与结果

- 房间指令持久化成功后即准备目标背景／敌人立绘，同时旧场景继续演出。控制器只维护可取消的视觉等待，Binding 负责资源就绪回报；不把下载逻辑塞进战斗规则。
- 步行和遭遇期间资源已就绪：保持原有时序，不增加载入页。资源仍未就绪：保留旧战场外框、我方卡片、骰盘和侧栏，仅在敌区保留统一载入遮幕。
- 遮幕复用 `LoadingPlaque` 和 `scene-loading-surface`，不新增动画依赖。短等待不出文字牌；超过 300ms 才显示。等待遮幕最少停留 180ms；刚出现提示牌时保留至少 180ms 阅读时间，避免提示闪现。
- 资源就绪后挂载新敌人，用原 280ms 揭幕时间淡去同一张暗幕，不再追加一次白闪。既有快速路径双白闪、敌人挂载入场、伤害／掷骰时序不改。
- 系统减弱动态时不走遭遇演出；快资源直接接续，等待超过 300ms 才启用局部遮幕。阅读时间不因减弱动态被压缩为一帧。
- 载入错误在原敌区提供“重新加载画面”，只重试资源，不重复提交 `advance-room`／`choose-exit`。刷新、隐藏页面或卸载均取消视觉等待；晚到资源不能重播过渡。
- 等待时暂停被遮挡的装饰，隐藏伸出敌区的旧意图连线。初次进场／刷新恢复时的资源失败回退仍保留，未全局删除加载保护。
