# AIRP 事件流与调度设计合同

更新：2026-09-25。本文保留已确认的事件、日度／副本调度、黑名单、结算和记忆方向；其中扩展能力不自动等于已实现。当前代码与缺口见[LLM与AIRP](../architecture/LLM_AND_AIRP.md)和[统一状态](../DESIGN_DECISIONS_AND_CURRENT_STATUS.md)。实施以[GM最小职责定稿](2026-09-24-airp-gm-demo-scope.md)为边界；不恢复已被替代的早期模型链和逐阶段排期。

## 1. 本次明确的方向

1. 总管理默认使用大模型，真正参与事件构思与分配，不把它简化为程序轮流抽卡。
2. 总管理读取当前状态、结算记忆、未完事项、作者资料和执行能力；日度任务安排人物与事件，副本任务安排本趟节点及联动。
3. 两个主要检查点为夜晚结束后的日度安排，以及路线／队伍确定后的出发前副本规划；不是现实时间定时运行，也不每走一个房间重调GM。
4. 事件来源分为固定库与自由库。固定库选用作者内容；自由库允许根据情境构思新事件，不只是给固定卡换标题。
5. 两库共同接受黑名单制度；换来源、标题、人物或实例身份不能绕过同题排斥。
6. 洋馆人物／地点是事件入口；无事件默认无气泡。日志用于追踪、恢复和回看，不代替洋馆的主要发现过程。
7. 到达当前步骤或副本节点后，才由Gemini依据当前场景交接与r8基线演出，随后做中文封装及程序校验。内容22新配置后的洋馆场景与副本均使用Low；已经冻结的旧场景仍按原请求续跑，不追改历史输入。GM不写具体台词，不一次生成整件事件或整趟全文。
8. 只有真实行动、有效事件结果与已读正文进入经历；日程、候选和未读稿不是已经发生的事情。
9. 事件跨多个步骤乃至多个游戏日持续推进。前一步的选择与事实决定下一步是否开放、生成什么；任务反馈和任务收尾是本事件组成部分，不是可有可无的额外后续。
10. 固定与自由共用每日安排预算，不设每日各发一件或固定比例。先保留已有承诺和必要剧情，再判断是否需要新事情；没有合适内容可以不发。
11. 主动排程以一天一个重点、最多附带一个轻量小景为基线。重点可以是旧事件的推进；不为凑数量增加新委托，也不因预算阻止原事件继续或收尾。
12. GM提供条件化计划，小模型结算实际变化。地点、活动与人物状态可以偏离计划，后续使用已经发生并落账的状态，不强行把人物送回GM预定位置。
13. 好感、道具／鉴定品、人物位置／状态均是必须接入的交叉变量，不再把“仅记忆、永不触及数值与资产”作为新版本总边界；具体档位、预算和模板仍需配平。
14. 副本结束不等于关联事件结案。带回目标、返程反馈、实际交付、事件结算分别按真实条件推进；同一变化不重复发奖或增加好感。
15. 当前状态回答“现在怎样”，结算记忆回答“为什么变成这样”，原文保留具体承接依据。三者一致落账，计划不混入经历。

以上及§5.3、§7.1～7.4、§8.6～8.7、§9是本稿确定的职责与闭环。实际模型映射、物品权限及调用流程以[当前运行链](../architecture/LLM_AND_AIRP.md)为准；本稿未落地的数值档位、状态时限及通用工具仍是设计边界，不视为已实现功能。

## 2. 与当前事件流是什么关系

**总管理AI负责提出“发生什么、分给谁、何时及满足什么条件出现”；事件流负责实际触发与步骤推进；结算模型确认叙事变化，程序统一落账；黑名单贯穿日度与副本两个入口。** 不另建与现有任务并行的任务账本。

下表保留GM-A～F之前的基线与v0.3演进方向；当前实现与待补项见[状态页](../DESIGN_DECISIONS_AND_CURRENT_STATUS.md)。

| 部分 | 当前事实 | 新规划的处理 |
| --- | --- | --- |
| 发卡器 | 四型轮转、型内优先较少发放者，同次数按定义顺序 | 新内容版本以总管理的日程接纳替代这段选择逻辑；旧版保持原样 |
| 事件库 | 8张预制涟漪工作稿；事件定义只接受 `tier: ripple` | 保留固定库；新增可持久化、可校验的自由事件定义，不直接向旧Catalog塞模型JSON |
| 发放密度 | 每日最多4件、活动最多4件、每型最多1件 | 新版按一天一个重点＋最多一个轻量小景编排；通常新增0～1件、最多2件，两库共用，旧规则不改 |
| 主题排斥 | 活动同题互斥、终态后256相位冷却、唯一事件去重 | 继续使用；补充“已安排未出现”的占用与自由主题归一，固定／自由跨库生效 |
| 生命周期 | `pending / offered / accepted / ready / resolved / closed`，含拒绝、备用、过期、余波 | 保留行为语义；在上游增加“计划但尚未发放”，不拿 `pending` 冒充内部草案 |
| 事件内步骤 | 已有 `offer / departure / found / target / retry / return / complete` 等手写场景角色，按实际类型使用 | 扩展为同一事件下的步骤进度与按场景生成；不是把多节点剧本替换为一段AI长文 |
| 行动证据 | 出击须真实巡守，牵线须读指定对话，家务／小景须明确完成 | 沿用，不能由总管理一句“玩家完成了”替代 |
| 四阶内容 | 正典、成长／羁绊、回忆分属既有流程；不是统一四阶发卡器 | 先以只读入口／占用适配接入总管理，不迁移重写固定剧情 |
| 在线生成 | 内容18仅艾洛拉药箱归来与一次后续、每档最多2个direct任务 | 须演进为按事件／场景执行的契约；现有能力不能直接冒称支持一整日任意事件 |
| 洋馆标记 | 每个驻在人物常驻同一个白气泡，点击为固定时段闲聊 | 改为真实事件入口的只读投影；无事件不显示标记 |

上述旧涟漪池曾共用庄园接管／艾洛拉可用条件，并将会面统一放在公共休息室；内容19已增加共享位置查询，但仍主要依赖固定时段表。v0.4需要在其上接入实际动态位置／状态，不能只移动日志按钮或把计划位置当作实际位置。

### 2.1 GM、正文、结算与程序职责〔定稿〕

| 层 | 输入与输出 | 不负责什么 |
| --- | --- | --- |
| 总管理AI／Director | 当前状态、记忆、任务、作者资料与能力 → 日度计划或单次副本计划、事件骨架、条件分支、范围内的物品内容 | 不预定玩家选择、实际好感涨跌或最终结果，不直接落账，不写每段台词与情绪轨迹 |
| 游戏事件流与规则 | 校验计划 → 发布、节点触发、真实行动、步骤、终态、预算与黑名单；校验并提交结算结果 | 不替模型判断全部人物语义；不把自由题材退化为固定题材白名单；不运行模型提供的脚本 |
| Gemini正文 | 当前节点意图、最新状态、相关完整作者资料、已读原文与实际选择 → 本场演出、待选回应与差分 | 不重做日度／副本规划，不跨未选分支代办结果，不直接授予资产或数值 |
| 场景GM〔context16〕 | 当前阶段、完整前文与本轮正文、玩家实际输入、事实／记忆与相关全文资料 → 一次判断截止，或给下一轮范围／软篇幅 | 不在写前重复调用，不写台词／逐段大纲，不评文风或自动改稿，不执行接单／出征／交付／结算 |
| 格式化任务 | 已完成正文 → 中文AVG结构、合法标签与态度候选 | 不判断交谈结束，不续写、重规划、结算、改写角色卡或重新生成物品 |
| 小模型结算／Updater | 实际选择、行动／事件结果、已读正文、相关原卡与旧状态 → 好感档位、物品操作、实际位置／状态更新及结算记忆提案 | 不构思新事件、不重抽物品身份、不改GM未发生计划、不以摘要覆盖程序事实 |

结算是独立任务，不是文学审计或“第四段大纲”；可与格式化复用小模型型号，但输入、权限、调用时点与结果记录分开。无需每项职责新增一个模型型号，实际ID由配置映射确定。

GM默认使用大模型；日度、副本与场景任务可复用该模型，但分别编译上下文并保存计划／评估。程序／配置提供奖励预算与数值映射，GM不能自行抬高上限，小模型不能凭正文获得任意状态修改权。

必须区分四个尺度：**GM安排日度／副本骨架；事件流推进多个真实步骤；Gemini演出当前节点；结算层确认实际变化。** r8正文内部的三段ICOT不是三个外部模型，也不能代替事件步骤。

### 2.3 场景GM节奏与收束〔09-24增补〕

每轮先由Gemini创作并做中文封装，再调用一次GM。GM读取本事件完整已读正文、本轮即将展示的正文、玩家实际输入、阶段目的、taskGuide、当前事实／记忆与激活的全文卡书；判断当前交谈是否完成，若继续则同时给出下一轮focus、alreadyCovered、suggestedWords和stopWhen。没有独立写前GM。先前已经解释清楚的继续有效，接单仅补缺项，不用acceptance的详细说明卡住offer。

下一轮Gemini直接读取上轮GM指导与最新实际选择；指导形成于选择之前，不能预设玩家意愿，与实际选择不一致的部分不执行。Gemini保留r8条目顺序、三段ICOT、演出Plan、全文资料与采样；有继承的软篇幅建议时才作既有SETTING长度短语适配。首轮／新阶段无指导时沿用已有事件安排与当前步骤，不额外调用初始化GM，不虚构建议字数。封装只做中文及合法字段。GM不因文风、重复或篇幅短而打回；不形成审计—重写循环。

GM输出complete=true、next=null时，只让玩家读完后结束当前交谈，不执行接受、出征、取得物品、交付或结算；complete=false时next给出下一轮指导，继续同阶段。首轮提出保留一次态度选择。封装不再收到stageContext，额外输出phase也不采用。指导绑定当前事件／阶段／本次发生，只从已读轮继承，不串到接单后的新阶段。

每轮正常3次：正文、封装、GM。各阶段保存输入、原响应、用量与失败，只恢复失败阶段。新帧启用context19，继承17全局输入与18按交流作用收束，附加有限摘要／待办更正；依赖当前正文时读完后生效。旧冻结帧按历史协议续跑，不增加写前GM或逐房间额外GM。

共享上下文提供四人原卡与触发世界书，GM知情与NPC知情分开。正文只继承场景范围与软篇幅，不把alreadyCovered／reason当事实；偏差仍用程序任务指引承接。三种GM、后续正文与结算共同读取有效摘要／待办：原账不覆盖、旧源不复活、新承诺正常记录。当前实现见[运行链与权限](../architecture/LLM_AND_AIRP.md)。

## 3. 检查点：日度与出发前调度；场景级控制见§2.3

### 3.1 什么时候调用总管理

| 检查点 | 首版处理 |
| --- | --- |
| 夜→次日晨的真实游戏时间提交 | 主要检查点：先处理旧事件与到期账本，再冻结次日上下文，申请一次总调度 |
| 首次进入已开放AIRP的自由行动，当前日尚无计划 | 补一次当前日剩余时段的初始计划；不补造过去半天的生活 |
| 玩家确定路线、同行队伍与出发目标，进入副本前 | 冻结最新状态，申请一次本趟副本规划；不重排全天，不要求必须先有洋馆委托 |
| 白天接受、实际出征、阶段反馈、归来、交付、关系变化 | 立即提交事实及相应结算，更新原事件与计划可执行性；后继场景当天即可开放，不等待下一夜，不每步重调GM |
| 计划遇到无法预料的新冲突 | 保留已读与已接受部分，挂起受影响条目；首版通过明确的局部重排操作处理，留下新修订与调用记录 |
| 普通点击、重开洋馆、刷新、读档 | 恢复已有计划，不重新抽卡、不自动补一轮付费请求 |

“后台”仍可由静态网页中的执行器运行。启用日度／副本调度时明确告知相应检查点会请求玩家配置的API；没有Key或页面关闭时不承诺继续工作，不新增云端常驻Agent。再次进入页面显示待继续状态，由玩家明确恢复未完成调用。

### 3.2 一次日度检查点的执行顺序

1. 提交结束上一日／进入新一日的游戏事实，更新旧任务、过期、余波和冷却。
2. 查询可恢复交谈、待交付、仍可接取／已推迟的旧事件、固定剧情与角色占用；这些都是当天负荷，不是待随机抽中的小事。
3. 冻结完整输入及检查点身份，持久化本次总调度尝试，再在存档事务外调用AI。
4. 总管理先保留必要继续与收尾，判断当天的重点及剩余空间；确有新增需要时，依§5.3选择适配固定卡或构思自由卡，提出日程，也可以明确不新增。
5. 校验共享日预算、既有事件负荷、来源、黑名单、人物／地点／时段、互斥和执行方式；自由卡另做主题归一及语义复核。不能只通过数量校验就忽略多步骤负担。
6. 通过后原子接纳整份日程及其主题预占；不静默删除错误条目拼成另一份“AI计划”。失败保留错误与原输出，按有限修复规则处理。
7. 到达条目的可出现时段，重新检查当前状态，通过后才发布事件实例与洋馆入口。
8. 进入当前步骤时再次检查合法性；生成场景冻结当前节点输入，以Low正文与封装交付，在玩家输入／新事实边界前停下；出发前另走§3.3。
9. 玩家选择、执行与阅读分别写来源，行动／事件结算按§9更新状态与记忆，开放合法后继；只有事件达到终态才写对应黑名单。GM在下一检查点读取已落账变化与未完事项。

总管理等待不制造任务完成或耗费额外游戏时间；允许继续不依赖新计划的已有玩法。若等待期间世界已经变化，接纳时复验受影响事实与日程依赖；不能拿过期快照强行发布，也不能因无关的日志读取就重新付费规划。

### 3.3 一次出发前检查点

1. 玩家确定合法路线、同行角色、携带物品与出发意图；程序准备本趟身份和快照，此时尚未声称人物已经出发或消耗物资。
2. 读取最新状态、相关结算与未完事项、当前日程负荷、关联事件、此前同地探索历史及本趟可用节点／动作／奖励范围。
3. GM生成§7.4的条件化副本计划。固定事件复用作者骨架，自由内容在能力范围内构思；没有委托也可安排本趟叙事，不强造一项玩家已接受的任务。
4. 校验路线与人物、节点可执行性、关联事件身份、预算／黑名单、条件分支和物品定义；计划接纳并与本趟身份绑定后，才能开始这趟带叙事规划的探索。
5. 实际出发由程序提交。此后按§8.6推进，不在每个房间、战斗回合或普通移动时重调GM。

刷新和网络重试复用同一检查点／计划；实际另一次出击使用新run并保留旧结果。出发前改变路线或队伍等关键条件时，只复核或重新规划受影响内容；取消出发只取消未执行计划，不产生经历、拒绝或重复奖励。无可用计划时明确提示待生成／恢复；若允许无AIRP内容出发，必须作为明确的降级选择记录，不能伪称GM规划已经执行。

## 4. 总管理应得到哪些上下文

| 输入块 | 必需内容 | 证据与边界 |
| --- | --- | --- |
| 当前状态／Locus | 游戏日和时段、可用房间、人物实际位置／活动／持续状态、可交互性、剧情或远征占用 | 默认日程、GM计划位置与实际位置分开；采用程序事实和已接纳的叙事状态更新，不把未来位置当现状 |
| 玩家当前活动 | 正在进行、刚完成或放弃的行动，出征结果、实际选择和当前目标 | 玩家决定来自真实输入；程序事实优先，叙事补充需通过结算，不从一句候选台词推定“已答应／已受伤” |
| 任务／Agenda | 活动委托的当前步骤、前序选择、待满足条件、待交付、未履行承诺、待处理余波、已解锁固定剧情与相关后续 | 既有承诺优先延续；任务未完成不能被下一日计划删除或从头重发 |
| 结算记忆／Bond | 行动结果、事件总结、未完事项、有效好感变化及依据、共同／私人已知信息、必要原文 | 已结束事件默认读整合结果，进行中读实际进度；小模型摘要可追源，未读候选、未选分支和撤回事实不进入经历 |
| 物品与资产 | 当前持有、任务物、未鉴定状态、已交付／消耗记录及允许奖励范围 | 隐藏鉴定定义供规划核对，不代表玩家或正文角色已知；候选奖品不等于已入库 |
| 本趟副本〔副本任务专用〕 | 确认的路线／队伍／携带物、合法节点与动作、关联事件当前步骤、同地历史、失败／撤离规则 | 日度计划不是本趟实际经历；不凭模型字符串新增战斗机制或可执行路线 |
| 作者资料 | 基础世界观、相关资料、编排范围内人物的完整角色卡与世界书 | 保留原文与来源；不能用管理器摘要替代调整好的角色卡 |
| 固定库 | 合法可选事件及明确的排除理由、固定条件／关键节点／效果边界 | 不改写固定事件核心，也不解锁未允许的主线 |
| 自由库 | 尚可复用的自由卡、可构思范围、近期已用题材、执行接口 | 不限定只能改写8张现有卡 |
| 黑名单与预占 | 主题键、主题语义、来源事件、禁止重发原因、解除时点、同题活动占用、唯一事件完成记录 | 送入AI用于编排，发布时仍由程序复验，不能只靠提示词自觉遵守 |

每个动态条目带来源身份、故事时间、参与者／知情范围和有效性。总管理输出的安排依据引用这些来源；不需要输出隐藏推理或替人物制定详细台词。

作者资料与游玩记忆是两类东西。角色卡与命中世界资料保持全文；本轮只精简结算记录，不摘要作者原文。短Demo先按时间读取结算短记录，将进行中／未完事项与近期变化置前，不引入检索模型或向量库；历史仍留档，黑名单不随摘要取舍消失。必需来源缺失或容量超限明确处理，不静默裁剪资料或向每场正文泄漏全部私有记忆。

## 5. 固定库与自由库

### 5.1 固定库

固定库包含作者预先定义的事件卡和既有固定剧情入口；“固定”指核心事件与条件有作者依据，不表示每个对白槽都必须手写。

- 正典／羁绊／回响：仍由各自的正式条件解锁。总管理可安排已授权的会面窗口与衔接，不能绕过前置或改写固定正文。
- 固定涟漪：如药箱委托，有确定目标与完成证明。可在已授权场景槽调用Low正文与封装，旧版三阶段行为保持原样。
- 固定后续：引用已完成事件和必要记忆，不能借同题后续重新取物或领奖。

现有8张是工作稿，不因纳入库就变成作者定稿。首批正式接入卡仍需内容审定；前轮讨论的6张候选也不随本次选卡与密度规则定稿自动获批。

### 5.2 自由库

自由库包含总管理在合法上下文与黑名单之外构思的事件卡，以及过去尚未曝光、允许再次安排的自由卡。

- 新事件可以有新的生活问题、动机、人物组合和场景切入，不要求预先存在相同题材的固定卡。
- 先提出含流程骨架的事件卡，接纳后保存不可变定义／修订与来源，再安排；不在点击时临时捏造一张未登记任务。骨架定义步骤意图、条件和可能结果，不提前写完各步骤对白或指定玩家一定选择哪条分支。
- 文学题材采取黑名单负约束；可执行玩法仍须绑定游戏已实现的动作、目标和效果接口。这是执行能力边界，不是固定题材白名单。
- 首版自由小景／家务可用阅读与明确行动确认闭环；牵线须能绑定真实目标交谈；自由出击须引用合法路线与目标定义。GM可按§9.3提出新物品内容，但不得靠名称或描述发明未实现的战斗／装备／设施能力。
- 选择、跳转与效果由可信交互和结算模板绑定；模型可在授权范围内提出情境、奖励定义与状态变化，但不发布任意命令、脚本、无预算奖励或未经校验的玩家行动分支。
- 自由卡的 `summary` 只是事件简介，不直接写进经历。完成后的真实结果和已读摘要另行形成。

自由库不是无限积累的全文仓库。内容19已有版本化数量与容量限制；v0.4须按新增副本计划、物品与结算记录重新量测。达到边界暂停新增并保留历史，不自动删除黑名单和已读资料，也不沿用药箱“两场”上限冒充每日事件容量。

### 5.3 什么时候用固定卡，什么时候用自由卡〔定稿〕

**先决定今天是否适合再发生一件事，再决定这件事采用哪种来源。** 固定卡提供经过审定的内容，自由卡回应这一档实际发生的生活；两者不各领一份日额度。

| 当下情况 | 选择规则 |
| --- | --- |
| 原事件尚未结束，正在等目标反馈、归来、交付或结果收尾 | 继续原实例和当前步骤，不另发固定／自由卡 |
| 作者卡的事情、动机、人物与前置适合当前情境 | 使用固定卡，在作者允许范围内承接实际记忆，不改核心事实与完成条件 |
| 当前行动、人物关系或洋馆情况产生了具体的新事情，没有适配的作者卡 | 由总管理构思自由卡；仍须有情境依据、合法执行步骤并通过黑名单 |
| 普通固定卡虽然可用，但自由事件更贴近当前经历 | 可以选择自由卡，不必先耗尽固定库，也不强发固定卡维持比例 |
| 有明确时点或必要收尾的固定剧情 | 先保留其窗口和当天负荷；普通可选固定涟漪没有同等的无条件优先权 |
| 当天已经很满，或没有合适的事情 | 不新增；可只处理旧事件，也可安排平静日 |

- 固定卡合法可用，只表示可以参与比较，不表示必须立即发放；不能把所有已解锁内容一起堆到当天。
- 自由卡不是固定卡耗尽后的补货，也不是每日生成指标。固定库暂时都在冷却时，有真实新情境才构思自由卡，否则留白；不能借自由来源换皮重发。
- 来源选择看动机、当前关联和执行条件，不采用固定／自由轮换、随机比例或按人物轮流配额。安排依据引用实际来源，不输出人物详细台词。
- 固定卡的授权动态对白、原事件的过程反馈仍属于原卡，不因文本现场生成就变成自由新卡。
- 终态后的真正额外后续须先通过§6.5的父事件条件，再参与当天负荷判断；“合法后续”不等于当天必须提供，也不是无限新增入口的豁免。

## 6. 黑名单制度：两库共同遵守的事件排斥

### 6.1 先分清三个维度

- **固定／自由**：事件从哪里来。
- **正典／羁绊／回响／涟漪，以及涟漪四型**：事件属于什么内容、怎样参与。
- **黑名单、当前占用、生命周期**：这件事现在还能不能出现。

黑名单不是另一类事件库，也不是把艾洛拉等人物禁用。它主要阻止已经处理过的核心事件换皮重来；某人的药箱主题被排斥，不等于这个人物不能有其他事情。

### 6.2 原规则保留及新增部分

| 排斥依据 | 何时建立 | 何时解除／怎样处理 | 与现有系统关系 |
| --- | --- | --- | --- |
| 活动同题占用 | 已发放、已接受、待交付的事件存在 | 原事件结束后转终态政策；不能生成第二件同题新任务 | 已有；新增日程接纳后的同题预占 |
| 终态主题黑名单 | 完成、明确拒绝、已见过期、有后果错过 | 从终态相位起256相位，即64游戏日；到期只解除筛选限制，保留历史 | 保留 `themeKey / fromPhase / untilPhase` 原含义 |
| 一次性事件去重 | 已完成的唯一物件／唯一剧情节点等 | 不因64日到期而重置；只有明文的新周目规则能重建 | 保留既有唯一事件去重，不等同全部主题永久禁用 |
| 未曝光惰性备用 | 已正式提供但未展示实际内容，提供期结束 | 不写已发生经历、不加64日终态黑名单；最早下一游戏日重查并创建新实例 | 保留备用规则；固定库引用原定义，自由库保存冻结定义 |
| 已计划未发布 | AI安排已接纳但窗口尚未开放 | 临时预占；取消／日程窗口结束释放，不伪造玩家拒绝或错过 | 新增计划层，不能直接套旧 `pending` 过期 |
| 当前不合法 | 人物外出、场景占用、前置不符、能力不存在等 | 条件变化后重查；不是人物／主题64日黑名单 | 沿用并补足共享条件查询 |

64日主题制度来自既有事件流，本稿不擅自缩短。旧版的冷却历史与源事实不迁移、不覆盖。普通拒绝也不擅自提升为玩家“永久不喜欢此题材”；如以后增加玩家偏好屏蔽，须另立规则。

### 6.3 生命周期如何写黑名单

| 情况 | 世界／任务结果 | 黑名单与再次发放 |
| --- | --- | --- |
| AI候选未入选／校验失败 | 从未发布，没有玩家经历 | 不记终态黑名单；本次失败留诊断，不反复提交同一违规提案 |
| 日程条目取消，尚未发布 | 只是计划作废 | 释放预占；不是“玩家错过了” |
| 已发布，玩家只看到了气泡 | 可接触，不等于打开或读完正文 | 保持未曝光状态，期限已从可提供时点开始 |
| 实际看到事件内容后“稍后再说” | 保留同一事件与已见阅读进度 | 不立即加黑名单、不重置提供期限、不立刻换皮再发 |
| 明确拒绝 | 记录拒绝终态 | 原主题屏蔽256相位 |
| 惰性事件未展示实际内容便到期 | 进入备用，不声称别人完成了它 | 无64日终态屏蔽；重发用新实例，最早下一游戏日 |
| 惰性事件已展示实际内容但未接受便到期 | 保留已见终态，不回收成“从未发生” | 原主题屏蔽256相位 |
| 有后果事件到期未接受 | 按已接纳的后果规则记一次他人处理／公共近况 | 原主题屏蔽256相位；没有奖励、好感惩罚或玩家参与假证据 |
| 已接受 | 跨日保持承诺；不继续使用提供期限 | 活动同题占用持续；不能被每日重新安排取消 |
| 完成并确认 | 写有效完成事实、必要记忆 | 原主题屏蔽256相位；唯一事件额外保持去重 |
| 生成失败／取消请求 | 只是技术失败；未提交玩家拒绝 | 不加终态黑名单、不把模型候选当经历 |

现有8／4相位提供期作为兼容基线保留；新自由卡首版建议沿用惰性8、有后果4，不能让管理AI随意缩成几句对白就过期。真正发放前被剧情／位置条件挡住的内部计划，不提前消耗提供期。

对新生成入口，点击后仍在等待模型、没有展示事件实际内容，不记为内容已曝光。技术失败本身不产生终态；之后若玩家正常推进游戏时间，仍按该事件真实的曝光状态和失效政策处理，不能借刷新或反复生成重置期限。旧版本的曝光提交方式保持原样。

### 6.4 自由事件如何防止“换名绕过”

现有程序只比较规范主题键；面对模型任意新写的键，单靠字符串相等不足以维持黑名单。

新卡须提供：核心事情、涉及的既有对象／承诺、行动目的、预期收束方向、相关历史事件以及建议主题归属。标题、人物名、文风不作为主题身份的唯一依据。

沿用内容19已采用的程序匹配与独立语义复核分工，并覆盖副本中新发的自由题材：

1. 程序先匹配已有定义、稳定对象／任务引用、已登记主题别名及已知重发关系。模型不能自行把已有药箱任务登记为全新主题。
2. 对新增自由题材，以独立的批量语义复核任务比较活动事件与有效黑名单，给出“同题／新题／不确定”及对应来源。真正后续另由程序父槽授权，不由复核模型自封豁免。可复用总管理的模型配置，但与构思输出分开记录；不新建向量库或无界Agent循环。

同题命中即拒绝新发；真正新题由程序分配稳定身份；不确定条目不发布，可在有限修复中换提案。AI自称“没有重复”不能直接通过。语义复核仍可能漏判或误判，必须用同题改写／不同题误伤样例验收，不能宣称JSON校验保证语义零错误。

示例：已经取回并交付药箱后，把标题改成“再去找一只旧盒子”，若核心仍是重复完成同一取物承诺，固定／自由任一来源都应被拦截；但艾洛拉参与另一独立生活主题，不因人物相同被拦截。

### 6.5 黑名单不能把合法后续也封死

本节“额外后续”专指主事件已经结束后新增的延伸内容。接受后的回应、过程反馈、失败重整、任务结果收尾，都是主事件自己的必要步骤，不占用此处的一次额外后续额度。

额外后续必须有受验证的父事件、真实完成／阅读／记忆条件及独立后续槽位：

- 不重新请求或完成父事件同一目标，不重领奖，不重新制造同一承诺。
- 在父事件限定范围内承接新的回应、反馈或后果；不因共享人物、对象、关键词就视为重发。
- 父事件的64日黑名单保持有效；后续是被授权的继续，不是清除黑名单。
- 模型不能仅填写 `isFollowup` 就获得豁免；游戏根据父引用与后续契约核准，次数有界。
- 回看已读内容也不受“禁止新发”拦截，且不再次写终态／冷却。

首版建议每个涟漪最多一个额外生成后续，沿用药箱切片的有界方向；后续自身结束记录去重，不无限派生孙事件绕过冷却。

### 6.6 同一事件的步骤不会被当作同题重发

- 一个事件实例下的接受、反馈、结果场景共享事件身份与主题占用；每一步有自己的步骤／场景身份，但不是新事件卡。
- 接受、一次进度反馈或一场正文读完，都不启动整个事件的64日终态冷却。未完成事件继续占用同题，跨日保留。
- 只有真正的事件终态按§6.3写一次黑名单。普通任务在结果场景读完并经合法交付／完成确认后结束，不能把“取到目标”直接当作整段任务完成。
- 若拒绝／错过等规则先提交终态，绑定该终态的拒绝回应／余波仍能展示；这属于原事件的收尾，不是绕过黑名单重新发卡，不重复提交终态。
- 下一步骤是否能进入，由事件内的条件与来源证明决定，不重新经过“是否再发一个同主题新事件”的抽选。模型不能冒充既有步骤插入无关的新任务。

## 7. 总管理输出：日度计划与副本计划，不是长篇剧本

以下是规划字段，不是当前可导入schema；落地时须新版本reader／validator。

| 对象 | 必需信息 |
| --- | --- |
| 检查点 | 档案／分支身份、边界来源、目标游戏日、规则与资料版本、输入摘要身份、尝试及实际用量 |
| 一日计划 | 固定承诺与保留入口、当天已有负荷／重点、可选轻量小景、各时段安排、空窗或不新增理由、每件事的来源依据、共享额度及计划修订与状态 |
| 单次副本计划 | 本趟身份、路线／队伍快照、关联事件及步骤、叙事重点、条件节点、发现／奖励定义、成功／部分完成／撤离／失败的承接边界 |
| 副本节点 | 稳定节点ID、合法位置／阶段、前置证据与互斥、演员、当前意图、可用行动、物品引用、停止条件与条件后继；不含预写对白 |
| 事件卡 | 固定／自由来源、层级／参与类型、发起人与参与人、地点与窗口、事件简介／动机、主题语义、前置与互斥、执行绑定、失效政策、步骤骨架与事件终态条件 |
| 步骤定义 | 稳定步骤ID、用途、进入条件、角色／地点、需要的输入或动作证据、允许生成／固定演出方式、结束条件、合法后继与结果分支 |
| 步骤进度 | 当前步骤、已提交选择、有效动作证据、各场已读范围／全文引用、尚待条件、场景生成记录；与整个事件终态分开 |
| 后续卡 | 上述字段＋父事件／已读场景／必要记忆引用、合法后续槽位 |
| 展示入口 | 当前可触发的事件身份、人物或地点、标记类别、状态；不包含未来秘密和内部规划说明 |

总管理可以解释“为什么安排”，但不逐人写拟定台词、不做CV演出校正、不预定玩家一定答应。事件目标与收束边界不等于已经发生的结果。

### 7.1 每日密度：一个重点＋最多一个轻量小景〔定稿〕

本节在v0.3取代了“每日新增4件、其中自由2件”的旧建议，内容19已采用共享低密度规则；v0.4继续沿用，不改更早内容包的发卡数值。

| 项目 | 定稿规则 |
| --- | --- |
| 当天重点 | 主动编排以一件重点事情为基线，可以是旧事件推进、出击、重要固定剧情或一件新事件；不是每天必须新接一份委托，也允许没有重点 |
| 附带内容 | 有空间和合适情境时，最多附带一个轻量小景；不要求每天都有，也可以当天只有一个小景 |
| 每日新发 | 通常0～1件新涟漪；一件重点新事件搭配一个轻量小景时最多2件。不安排两件新的复杂事件，也不把未用的重点空间兑换成一批小景 |
| 固定／自由 | 共用上述空间，不设各自保底、额外额度或固定比例；来源不决定内容的轻重 |
| 已有负荷 | 进行中的任务、待交付、必要反馈、仍可接取／已推迟的原事件都计入当日负荷；不能只看今天新增数或已接受数 |
| 忙碌日 | 已有出击、多步骤交付或重要剧情作为重点时，不另添新的复杂事件；轻量小景也可省略 |
| 平静日 | 无合适内容可以零新发；不为维持气泡、四型齐全或模型调用频率补卡 |

“重点”描述编排分量，不是新的事件阶级；“轻量”也不单由模型填写的标签决定。轻量小景可有当场选择与反馈，但不形成新的跨时段承诺，不要求出征、目标人物往返或多场任务交付。需要这些过程的内容按重点处理，不能标成小景绕过额度。这里不设正文硬字数或强制三阶段调用次数。

**这是约束主动新增安排的节奏，不是玩家一天只能处理一件事的行动上限。** 已有合法任务、必要反馈与收尾必须保留；玩家愿意连续推进，按真实步骤开放，不因为“今天已经看了几场”而强制等到明天。若一天实际发生的内容超过预期，应减少／撤下尚未发布的新安排，不删除承诺、改写已读内容或阻断交付。

### 7.2 新发计数与当天负荷分开〔定稿〕

- 新发额度按正式发布的新实例计；同一事件的接受回应、过程反馈、失败重整与结果收尾不重复计数，但总管理必须考虑它们带来的当日阅读、行动与人物占用。
- 跨日继续同一实例不占新发额度；其待接取入口、未完成承诺和预计可达步骤仍计负荷。不能每天给一个尚未处理昨日事件的玩家继续堆新任务。
- 已结束事件的可选额外后续也计当日负荷：轻量的使用小景空间，较重的作为重点考虑。无论是否另建实例，都不能因“不算新委托”而绕过节奏限制；它不同于必须保留的原事件收尾。
- 正典／羁绊／回响不计入新涟漪数量，但其真实推进占据当天重点和人物窗口；不能先安排重要剧情，再以“涟漪名额还没用”为由追加两件新事。仅解锁但尚未安排／推进的入口不等于强制占满全天。
- 初始计划、日内局部重排与实际发布使用同一游戏日账本。接纳计划时检查剩余空间并预留，发布时复验；未发布替换释放原预留，已发布后完成、拒绝、过期不返还当日新发计数。
- 未曝光惰性备用按§6重新发布为新实例时，占再次发布那一天的额度；原实例跨日继续、刷新或恢复阅读不算新发。不能借备用、修订或新来源身份重置同日计数。
- 玩家完成、拒绝或推迟事件后，不立即再抽一件填满空位。日内只发布已安排且仍适合当天负荷的条目；必要的局部重排也不能以“已办完”为由循环补发新的重点。

### 7.3 入口、优先级与人物分配〔定稿〕

- 同时可接触、尚未接受的涟漪入口最多2件，包含跨日仍可接取的原实例；这不是“每天另外再给2件”。每位人物同一时段最多一个可点击事件入口。
- 同时活动出击委托继续最多1件。已存在的承诺不会因为新日程的重点改变而取消；多个旧事件的合法继续入口不受“仅一个重点”粗暴封锁。
- 先恢复已开始交谈、必要反馈／收尾和明确时点的固定剧情；普通可选固定卡与自由卡按§5.3比较，不以固定来源强行插队。
- 同人物窗口冲突时，原任务的必要反馈／待交付优先，可选额外后续和全新事情再依日程安排；其余合法入口排队，未发布时不得因排队被算作玩家错过。
- 人物分配服从当前事情与位置，不让每个角色轮流领取每日名额。无合法事件入口时无气泡。

管理AI仍负责选人、题材、固定／自由搭配和留白；程序校验额度、真实条件与占用。新发数量只是底线，不能用“未超过2件”代替对事件分量和旧任务积压的判断。

### 7.4 本趟副本的叙事计划〔定稿〕

副本GM在出发前回答“这一趟怎样承接当前人物、事件与历史”，不决定玩家一定走哪条路、一定成功，也不把现有战斗引擎替换成自由文本模拟。

| 交接内容 | 最小要求 |
| --- | --- |
| 本趟身份与前提 | 绑定本地档案／分支、本趟run、合法路线、同行队伍、关键出发状态、资料与规则版本 |
| 叙事重点 | 本趟主要处理什么；有委托时引用原事件与当前步骤，无委托时说明本趟独立内容，不伪造已接受任务 |
| 条件节点 | 绑定可用房间、探索阶段或真实行动结果；写清进入条件、演员、节点意图、可行动方向、停止条件及后继 |
| 事件联动 | 哪些节点提供原任务所需证据、哪些只提供线索／反馈、哪些仍需回馆交付；不复制原任务或重新接取 |
| 物品与鉴定 | 使用固定作者定义，或在允许模板／预算内生成并冻结具体内容；发现、取得、带回、交付、鉴定分开，详见§9.3.2 |
| 条件化收束 | 成功、部分完成、提前撤离、失败或未发现时应承接哪些实际结果，不预写全部分支正文 |

节点只提供当前事情与执行条件，不规定每句台词、逐段节奏、人物每一步情绪或必然反转。Gemini收到的是当前已触发节点及必要背景；完整未来流程、隐藏鉴定信息和未触发秘密不能混成当前已知历史。作者角色卡和命中世界书仍保持全文。

本趟规划以一个清楚的叙事重点和少量有作用的节点作为Demo验收规模，不把每个房间或战斗回合都变成模型场景。具体节点容量另行量测，不新增复杂地图、敌人机制或无限支线作为前置。

日度与副本共用事件身份、主题黑名单与新增预算：

- 原委托的副本节点、失败反馈、归来与交付仍属原事件，不重复消耗新发额度，也不另写终态黑名单。
- 在副本中新增独立事件时，同样登记来源、主题和日度额度；不能借“副本内容”绕过一天一个重点与最多一个小景。
- 纯探索表现和必要反馈不自动变成新任务；但不能把独立支线伪装成原步骤以逃避负荷限制。
- 出发占用人物和时间后，日度计划只复验受影响的未发生条目；不重写已接受承诺或已读对白。

## 8. 从日程接到洋馆与现有事件生命周期

### 8.1 状态衔接

下表表达生命周期语义，不是要向现有存档原样插入这些状态名；新契约在CL-A映射实际状态。内容19已有planned／offered等独立Director状态，不能误用旧池的pending名称迁移历史。

| 计划层状态 | 与原事件实例的关系 |
| --- | --- |
| 草案／复核中 | 仅内部记录，无人物气泡、无事件经历、无长冷却 |
| 已安排 | 日程与关联事件身份已保存并预占主题，尚不可接触，不开始提供期 |
| 已发布 | 通过当前条件检查，原计划实例进入可提供状态，开始提供期并显示事件标记 |
| 已请求打开，正在生成 | 绑定当前实例与场景任务，保持独立生成子态；未展示实际内容不记曝光，不允许通过等待跳到完成 |
| 已展示实际内容 | 进入与原 `offered` 对应的可交谈阶段并持久化曝光；接受、逐段已读和完成分别记录 |
| 已接受／执行中／待交付 | 沿用原动作、证据与阅读规则；日程只引用当前实例，不复制成下一日新任务 |
| 已结束 | 终态、黑名单、备用或余波按§6执行；计划保留关联历史 |
| 条件失效，尚未发布 | 等窗口内重查，或作废计划释放预占；不声称世界已经发生了它 |

自由事件仍须映射四型参与方式：出击有本趟与目标证据，牵线有特定对话与交付，家务有行动选择与确认，小景可直接阅读结束。不能因为管理层存在，就把全部内容强制变成“接受任务”。

旧手写入口在 `airp-open` 时已有可展示正文，自由事件并不满足此前提。内容19已区分请求打开、生成接纳和内容曝光；v0.4节点继续保留这些边界，不能让玩家只看过加载界面就被判为已见过期。

### 8.2 气泡消费的是真实入口

- 人物在场但无可触发事件：无气泡；是否保留普通固定闲聊独立处理。
- 入口类别区分正典／羁绊／回响／涟漪；具体图形、颜色尚未定稿，本批不画UI。
- 新事件、待交付、可继续是状态，不与四阶混成同一枚举；头像上的唯一标记对应明确目标。
- 图上人物位置与事件会面位置必须一致，参与者不能同时被安排在不同地点。无法满足时挂起，不“点房间甲却默认在公共休息室”。
- 点击直接进入该事件或其恢复阶段；不先播放与事件无关的默认时段句。
- 标记展示不触发模型请求，也不把正文记成已读；未来时段条目及不可见人物的秘密不提前泄漏。
- 完成、拒绝、过期后撤下本入口；有其他合法入口再按优先级显示。日志保留任务和已读历史。

### 8.3 玩家行动改变当天计划

玩家提前出征、人物变为不可达、固定剧情占用或目标已被完成时，先更新事实，再复验受影响条目：未发布可延期／撤销；已经接受不能随意取消；已经读到的正文不可重写。局部重排不重生成整日已接纳内容，不复活已结束实例。

### 8.4 一件任务的最低闭环：接受—反馈—结束

这三个环节是事件推进的基本职责，不是把一篇长文分成三个标题。它们之间存在玩家选择、游戏动作或新的事实；后面的文本必须等这些输入成立后才能创作。

| 环节 | 进入依据 | 本环节的内容与操作 | 本环节结束后 |
| --- | --- | --- | --- |
| 发起／接受 | 当前事件已发布，人物／地点可达 | 展示事情与当前诉求，停在真实选择前；玩家接受、暂缓或拒绝。接受后的角色回应若依赖所选态度，选择提交后再生成该回应 | 接受写入承诺并进入进行中；暂缓保持当前事件；拒绝进入对应终态与收尾 |
| 执行／反馈 | 已接受，或已提交某个阶段动作／目标对话／探索结果 | 根据实际选择与进展给出回应，可能需要补充行动、再次交谈或失败重整；不预写最终成功 | 更新当前步骤与待满足条件；可以有多次反馈，不因读完一段就完成整个事件 |
| 结束／任务结果反馈 | 本事件定义的结果条件与来源证明成立 | 展示与实际成功、撤离、部分结果或失败相符的收尾；需要交付的仍由玩家明确交付，收益由正式规则处理 | 合法终态确认后结束任务、写终态记忆／黑名单；之后才可能出现额外后续 |

环节数量不硬限为三：牵线可以包括委托人提出、目标人物反馈、返回委托人收尾；出击可以包括接受回应、出发、发现、重整、归来、交付。纯小景不伪造出征／交付，但仍要有清楚的参与与结束边界。

**任何依赖玩家输入或新事实的分界，都不能让模型一次性跨过去写完。** 例如提议阶段不能顺便写“你答应后取回药箱，她已收下”；当时只知道玩家有机会接受，尚不知道选择、途中结果与最终交付。

### 8.5 流程骨架、步骤推进与条件分支

首版以有界步骤序列／条件分支描述事件，不做任意可执行脚本：

- 总管理在编排事件时给出关键步骤意图、依赖和可能收束；固定库复用作者骨架，自由库提出经校验的骨架。没有输入依据的未来场景只保留“若发生则怎样承接”的条件，不生成全文。
- 每个步骤明确等待的是玩家选择、真实游戏动作、目标角色交谈、时间窗口还是当前场景读完。程序验证该条件成立后，才开放对应后继。
- “待触发／可进入／等待生成／可阅读／已读待确认／步骤完成”属于步骤状态；“任务进行中／待交付／已结束”属于事件状态；GM、writing、formatting、settlement等另属模型任务状态。它们不得混成一个完成标记，旧planning任务保持原版本含义。
- 一场生成可以服务一个步骤，也可以只服务一个步骤中某次玩家输入之前或之后的片段。选择按钮由合法交互定义提供，正文不能自行解析成命令。
- 前序接受安排是事实，未来结果是分支条件。例如“优先从侧门撤回”不保证实际撤离；归来场景依据真实结算分支生成，而非照着最早计划写。
- 已接受事件跨日延续。下一夜总管理看到的是“当前在第几步、已发生什么、还等什么”，可安排剩余会面窗口，但不把已做步骤改写或当成新事件重新接受。
- 确需增加或调整未发生步骤时，提交有来源的流程修订并校验承诺、权限与终态条件；不能由正文模型在台词里悄悄增加强制任务。首版不允许无界自动追加步骤。
- 机械反馈和固定短演出可直接使用作者内容；需要文学展开的可达场景走Low正文与封装。不为每次点击或系统提示增加调用，也不把多个因果阶段合成一份预写全文。

### 8.6 从副本规划到回馆的交接闭环〔定稿〕

| 时点 | 交出什么 | 谁接手／形成什么 |
| --- | --- | --- |
| 出发准备 | 最新当前状态、结算记忆、原任务、路线／队伍、合法节点与奖励范围 | 副本GM提出本趟条件计划；程序校验并绑定本趟身份 |
| 实际出发 | 已接纳计划、真实出发提交、同行者与携带物 | 程序开始本趟玩法并更新确定的位置／占用；计划本身不消耗物资或生成经历 |
| 探索到达节点 | 当前房间／行动证据、节点前置及最新状态 | 程序确认是否触发；未到达、未调查或已失效的节点不发生 |
| 当前节点演出 | 节点意图、实际已知、选择与前文、当前演员完整卡和相关资料 | Gemini生成本场，格式化只封装中文；停在玩家输入或新事实边界 |
| 节点行动／反馈完成 | 实际选择、程序结果、已读正文、旧状态与来源 | 小模型按需要提出增量结算；程序落账后，下一节点使用新状态 |
| 撤离／失败／副本结束 | 本趟真实终局、完成／未完成节点、带回与损失、已有结算回执 | 程序先保存确定结果，小模型整理叙事补充和本趟记忆；未完成委托仍保留 |
| 回馆与交付 | 实际返回人员／位置／状态、原事件当前步骤、已带回物与待办 | 按实际会面条件继续原事件，生成反馈与收尾，明确交付后才结案 |
| 下一次GM | 已落账的状态、事件总结、未完事项及原文来源 | 日度或下一趟副本GM据此规划；不按上一份计划重置人物与物品 |

后续场景立即使用已经更新的状态，不等到夜间才“记住”。程序已知的战斗、房间、撤离与库存事实无需让小模型重新猜；叙事中的位置／活动变化由小模型据实际内容判定并经程序接纳。

同一动作可以为原委托提供证据，但“动作完成”“副本结束”“委托交付”是不同完成条件。副本中途已经接纳的物品或好感变化，最终汇总仅引用，不重复施加；未到交付条件的事件不能因副本终局而提前关闭。

### 8.7 实际过程偏离计划

- GM给出的是计划和条件分支，不是必须实现的剧本。跳过房间、未取得线索、提前撤离、失败或实际人物位置变化都按事实承接。
- 普通偏离先通过节点条件和收束分支处理，不每步重调GM。失去成立条件的可选节点可失效；必要任务保留未完事项，不能为继续演出伪造完成。
- 需要新的规划时，只针对尚未发生、受影响部分显式重排；已曝光、已读、已结算内容不重写。不要求在每个偏离点立即增加一次大模型调用。
- 小模型更新当前实际位置／活动，不顺手重排明天日程；GM读取此状态后才能安排新内容。GM计划中的“晚些时候去某处”不能由小模型当成已经到达。
- 技术重试继续同一节点／run；玩家实际再出发是新的run。旧失败记忆保留，新计划不能借重试重复领取旧收益或重置同题规则。

## 9. Low场景、交叉变量与结算记忆〔定稿〕

### 9.1 每个可达场景独立生成

1. 事件接纳时冻结流程骨架、约束、参与人和来源，不提前生成全天或整件任务的对白。
2. 当前步骤／副本节点满足条件后，投影本场职责、必要事件背景、已提交选择、最新有效状态、相关完整角色卡／世界书与合格历史。未来流程不能不加区分地混入本场事实。
3. Gemini按r8基线独立演出当前场景，保留该预设内部结构；不增加外部逐场大纲、审计或修订循环。格式化只提取已有中文、封装AVG和差分，不将双语创作过程或Plan展示为玩家正文。
4. 前序本事件中符合当前知情范围的已读正文以原文承接，并带来源／实际选择；不只传一个“任务成功”标签或管理AI的事件简介。未读尾段、未选择分支和未来计划不能冒充经历，其他人物私有内容不泄漏给当前演员。
5. 已生成但未读的内容保留生成身份；开始阅读后恢复原文，不因新一日计划更新重写。进入下一场是新步骤场景，不是重试上一场，也不是重新发一个事件。
6. 固定剧情、固定短反馈按作者内容播放。新配置内容22的洋馆与副本使用Low；旧版本和已冻结旧三阶段请求继续按原版本执行，不能改写历史请求或伪造planning阶段。

### 9.2 最小记忆基础设施：状态、结算记录、原文

只保留三部分，不另造长期记忆平台：

- **当前状态：**复用程序状态与已接纳模型变量，说明现在的任务、人物、资产与关系。不是由模型重写的第二套Campaign。
- **结算记录：**行动结算简记“做了什么、实际结果、推进到哪里、还缺什么”；事件结算重点记“最终选择与结果、有效影响、留下的未完事项”。事件总结整合行动记录，原记录仍保留，不重复计算变化。
- **原文档案：**保存真实选择、行动证据和完整已读正文；摘要仅作GM便捷输入，不替代原文、作者卡或世界书。

结算记录最少带故事时间、事件／行动／run身份、涉及人物、结果要点、未完事项、知情范围和来源。未完事项在实际解决后关闭，不因跨日清空；没有新证据就不更新，不把本场没提到当成消失。

| 写入时点 | 程序立即记录 | 小模型是否参与 |
| --- | --- | --- |
| 接受／推迟／拒绝／选择做法 | 真实选择、来源与任务状态 | 按钮本身无需一次摘要调用；有独立叙事影响时并入相应结算 |
| 行动真实结算 | 成败、资源／位置等确定变化、步骤证据 | 纯机械结果直接模板化；有新增叙事信息或交叉变量时整理一次 |
| 行动反馈读完 | 已读原文与知情范围 | 与对应行动结算合并或补充，不重新执行已落账效果 |
| 事件正式结束 | 合法终态、时间、冷却等 | 整理事件总结与到期应结算的好感等；无新叙事变化的简单关闭可使用程序记录 |
| 夜间或出发前GM | 冻结最新有效状态与结算输入 | 不再额外调用一层“每日回忆重写”；未完成的结算明确标示，不能假装已更新 |

行动与事件在同一节点结束时可合并一次整理，避免重复调用。程序已经发生的行动不等待对白生成成功才成为事实；需要阅读才成立的角色知情则按实际阅读记录，未读尾段不被召回。跨日未完成任务仍保留过程，不等 `resolved` 才建立记忆。

记忆轻重按“是否影响后续事情、人物知情或待办”判断：

- **重点：**真实选择／承诺、实际结果、任务进度与终态、影响后续的新信息、明确而未处理的请求，以及已接纳变量变化的依据。
- **适当：**有明确证据且有后续用途的个人偏好、态度表达或互动细节；记具体事实，不升格成无依据的关系突破。
- **不单独记：**普通寒暄、重复叮嘱、环境修辞、一般动作、瞬时表情、对玩家心理的猜测；GM计划、ICOT／Plan、未选回应与候选稿不是经历。

“某人声称”不自动等于世界事实，“提出邀请”不等于玩家已接受。在场也不等于知道所有内心旁白；沿用来源与知情字段，不引入复杂认知图谱。短Demo可以直接读取全部结算短记录；先突出进行中和近期变化，已结束事件避免将总结、全部中间摘要和原文重复堆入GM。黑名单与一次性去重始终独立保留。

**记忆接纳不采用“一句台词引用就整批拒绝”。** 混合旁白／台词的摘要或待办按场景记录保存，保留原句、全部引用和逐项发言归属，不冒充已证实世界事实，也不因此阻断合法结算。资产与数值仍以程序授权及回执为准；记忆文字不是物品发放或移动命令。旧失败原稿可显式离线复验，历史失败和用量不重写，不新增模型调用。

### 9.3 程序变量、模型变量与三类交叉变量

程序负责确定性的时间、战斗、资源、选择、任务阶段和预算；模型负责需要理解人物与叙事的判断。交叉变量不是只存在于文字中的备注：模型提出变化，程序校验后改变真实状态，并同步相应记忆。

| 交叉变量 | GM／作者卡的事前职责 | 小模型的事后职责 | 程序职责 |
| --- | --- | --- | --- |
| 好感 | 依据现有关系安排人物动机与事件分量，不预定玩家表现或涨跌 | 用完整当事角色卡、实际选择、相关历史与结果，判定方向／档位及依据 | 档位映射、范围限制、唯一结算与持久化；不自动等同成长等级或剧情解锁 |
| 道具／鉴定品 | 在授权模板与预算内确定来源、获取条件和具体内容；冻结隐藏身份与鉴定结果 | 确认实际获得／交付／消耗／鉴定，引用既定定义，不另编奖励 | 唯一物品实例、数量与归属、库存、领取／鉴定条件、价格／效果及去重 |
| 位置／活动／持续状态 | 安排日程、会面、活动及预期持续范围；保存的是计划 | 从真实行动与已读场景确认当前变化和结束条件，不改排未来日程 | 程序事实优先、合法地点／占用／时限校验、实际状态与入口一致 |

#### 9.3.1 事件好感度

- Demo先采用每位角色对玩家的一条好感量表，不拆信任、依赖、爱情等多轴；不改既有Lv.1～3成长含义。
- 小模型判断正向／不变／负向及少量变化档位，程序按配平表映射数值。具体数值以对应内容版本的规则表为准，后续配平单独审定，不把本稿例子当已批准参数。
- 判断依据是角色本人对这次真实经历的看法，不采用接受必加、拒绝必扣、成功必加的通用规则；不知道该事的角色不能凭全知历史结算反应。
- 以事件结算为主，每个角色在同一结算范围内只处理一次；普通台词、点头和每个按钮不刷分。需要按独立阶段结算时必须有明确作用域，最终汇总不能再加同一份变化。
- 好感与一条简短依据共同保存。不因一次微量增减自动升级关系阶段、开放正典或替玩家确定情感态度。

#### 9.3.2 事件／副本道具与鉴定品

- 固定事件沿用作者定义；自由事件／副本的物品内容主要归GM，包括名称、外观、来历、类别及鉴定内容。小模型不承担二次创作或临时重抽身份。
- 可生成新的具体物品内容，但须使用已实现模板和预算。程序／配置规定数量、品质、经济范围与效果接口；模型不能自行抬高奖励上限，字符串描述不能变成未实现能力。
- 未鉴定物在生成／接纳定义时冻结真实身份和品质；玩家只看到允许公开的外观信息。鉴定揭露同一结果，不因刷新、重试或再次问模型而变值。
- 发现、取得、带回、交付、消耗、鉴定分别有实际条件；“看见”“答应赠送”不等于已经入库。既有副本掉落不因AIRP联动再次发放。
- 正文演出必须与可接纳的物品结果一致。已有固定奖励在场景输入中明确；未授权赠物不能仅凭一句正文自动生成资产，必要的修复／处理要显式记录，不留下正文已赠送而库存无记录的静默矛盾。

#### 9.3.3 人物当前的位置和状态

- 最小状态为当前位置、当前活动、可交互／占用情况、影响后续的持续状态及结束条件；地点到地图节点即可，不模拟逐步走路或每句表情。
- 默认日程提供通常去向，GM保存计划覆盖；实际出发、到达房间、回馆等程序事实直接更新确定部分，小模型补充叙事中实际成立的位置／活动／状态变化。
- “稍后去温室”是安排，不是已到达；需要实际行动或相应游戏时段条件成立才改变当前位置。已接纳的实际状态可以偏离GM计划，后续场景与气泡必须使用实际状态。
- 临时状态有明确时限或解除条件，结束后再回到适用日程；不能永远卡在忙碌，也不能每场开头无条件重置。影响战斗、血量等已有程序值时必须走相应玩法接口，不能以叙述覆盖战斗事实。
- 小模型不顺手创造次日安排；GM下一次根据最新位置、状态和未完事项规划。人物不能同时占据两个冲突场景，合法性由程序检查。

### 9.4 统一结算任务与交接契约

一个小模型结算任务可以同时提出三类变化与记忆，不拆成三个独立模型，也不为每个字段增加一次调用。它不评价文风、不改稿、不规划下一场，不能与被暂停的正文审计混淆。

| 小模型输入 | 用途 |
| --- | --- |
| 本次事件／行动／run身份、实际选择、程序结算与证据 | 确定结算范围和已经发生的结果，不接受旧run或未选分支冒充 |
| 相关已读正文与段落来源 | 提取叙事新增信息；未读稿和未来分支不作为经历 |
| 当前状态、该事件旧记忆与未完事项、已接纳结算回执 | 增量更新、关闭真实已解决事项，避免重复施加效果 |
| 当事角色完整卡、关系基线与必要历史 | 好感与人物反应判断；不能只有摘要卡就替角色裁决 |
| 授权奖励／物品定义、当前库存、合法地点、状态与数值范围 | 只在可执行范围内提出物品操作和状态变化，不加载文学预设要求其创作 |

最小输出为“来源身份＋好感变化提案＋物品操作提案＋人物状态变化提案＋结算要点／未完事项”。各组可以为空；不要求每次凑满三项。此处为字段语义，具体JSON与验证器随新契约实施，不直接视作可导入schema。

落账与恢复边界：

1. 确定的程序行动／副本终局先正常保存，不等待小模型才承认真实玩法结果。
2. 小模型任务绑定这次结算来源及相关状态版本；程序检查身份、权限、范围、前置和重复，合法的模型变化及对应记忆一起提交。数值映射由程序产生，记忆引用实际接纳值，不保留一份与库存／好感相矛盾的“模型权威结果”。
3. 同一效果在节点、行动、副本终局和事件收尾之间有明确归属；已施加回执仅被汇总引用，不能借新摘要ID再发一次奖励或再计同一好感。
4. 未完成整理保留待处理状态与来源，失败不伪装为“无变化”。能依靠程序事实继续的玩法可继续；依赖缺失好感、物品或人物状态的场景／GM条目等待处理，或使用事先明确的事实／原文降级路径，不能默默采用过期状态。
5. 保存失败只重试保存已有结果；模型失败显式续跑同一任务，迟到或跨档结果不能写入。校验通过不等于语义正确，仍须对照人物原卡、已读文本与真实游戏事实进行内容验收，具体待办见[状态页](../DESIGN_DECISIONS_AND_CURRENT_STATUS.md)。

### 9.5 终态与幕后后果

- 只有有效行动、合法事件结果与符合阅读／知情条件的内容进入对应记忆；总管理计划、事件简介、未来后果分支、创作过程与未选回应不是已经发生的历史。
- 结果反馈是原事件必要收尾，不能省掉后包装成可选额外闲聊。需要交付的事件仍需真实确认，不由一句“收下了”直接结案。
- 已接纳的有后果事件到期，由游戏按已登记规则触发一次有来源的幕后处理；不能由GM看到“没点”就自由补造。Demo不因未点击自动罚好感或授予玩家收益，关系／资产变化仍须有独立授权条件。
- 未读余波可以是合法世界事实，但不能写成玩家已知／亲历；角色知情与玩家阅读分别保存。
- 旧药箱Updater、旧仅记忆奖励和历史已读文本保持原协议；新结算任务不通过放宽旧reader隐式安装。本轮不修改任何预设、角色卡、世界书或r8冻结内容。

## 10. 持久化、调用恢复与版本

- 检查点身份来自档案／epoch、真实游戏边界与规则版本：日度绑定目标日，副本绑定本趟run与出发快照；不靠浏览器当前时间或render次数生成。
- 一日只有一个有效计划；修订有明确来源和替代范围。已提交日程、事件预占与合法定义原子保存，不出现气泡有了而实例没存下的状态。
- 一趟副本只有一份当前有效叙事计划；节点与物品定义有稳定身份。出发前修订记录替代范围，开始后保留已触发／已读／已结算部分；取消未执行计划不产生世界后果。
- 总管理任务保存实际输入身份、输出、校验结果、尝试、用量与失败状态。保存失败时只重试保存已有输出，不重调模型；未知结果不当作零费用。
- 一个事件持有多个步骤和场景记录。场景身份绑定事件、流程版本、步骤、实际触发来源与本次发生序号；网络重试另记attempt，不把真实的第二次出征反馈与第一次失败重试混成同一场，也不能刷新一次就多造一场。
- 每个场景保存实际使用的任务输入／输出、阅读游标、步骤确认与来源；旧三阶段历史按旧版本保存，Low不伪造一个已成功planning阶段。读档恢复原节点和已接纳结算，不能重新接受、交付、加好感或重抽鉴定品。
- 多标签页同档锁与提交版本检查共同防止重复调度；切档／删档／跨日迟到结果不能污染当前档案。
- 配置分别映射日度GM、副本GM、场景GM一次交接、Gemini正文、格式化、结算及必要主题复核任务；GM沿用planning槽，任务可以共享型号，不共享职责或混用请求记录，不硬编码或擅自换型号。
- 正常每个日度检查点一次GM、每趟出发前一次GM；新增自由主题按需批量复核。context16洋馆每轮一次正文、一次封装、一次场景GM；副本节点仍按原正文／封装。结算按实际变化触发并可合并；不为普通移动、每句对白或夜间重复摘要增加调用，不建立后台无限循环。
- 调用按日度、副本、场景、结算分别记账。多场事件不能算作“一次生成”，Low也不等于没有GM／结算成本；不沿用旧三阶段每场三次的估算，也不恢复正文审计作为必经步骤。
- 无API／调度失败：保留旧任务、固定剧情和可玩世界，提示对应日度／副本计划待生成；结算失败按§9.4保留已发生事实和待处理状态。离线或无AIRP降级必须显式记录，不能同时启用旧轮转器与新GM发卡。
- 新功能使用新内容／契约版本，具体版本号在实现时登记。内容17／18／19、旧10及历史已读档案保持原身份／规则，不静默升级或重算历史好感／收益。
- 新版只有一套事件接纳／发布writer；日度与副本两个规划入口都通过它登记独立新事件。旧轮转器只在旧版本或明确选择的离线模式工作，不能共同补卡。
- 自由定义、日度／副本计划、节点状态、物品冻结定义、交叉变量、结算回执、记忆来源和黑名单都进入合法导出／重放。未鉴定品的公开上下文不得泄密；纯本地存档不承诺防玩家查看隐藏数据。导入仍校验来源和规则，不凭模型JSON直接授予效果。
- 继续使用玩家自备API与页面内存Key，不把凭据放入日程、日志、URL或构建包。页面关闭不推进世界，也不在重新打开时批量补造现实时间内“错过的日子”。

## 11. 一轮示例：验证关系，而不是新增正典

以下仅为机制测试情境，不是待写回的正式剧情稿。

前提：第D日药箱已真实交付，归来已读且记忆整理成功；父主题处于64日黑名单；另有一条尚未处理的已接受牵线任务。

| 时点 | 总管理／事件流行为 | 黑名单与气泡结果 |
| --- | --- | --- |
| 第D日夜结束 | 读取上述事实，以原牵线任务的推进为D＋1日重点；另有合适情境才安排一个自由轻量小景，不新增复杂任务 | 旧任务不重发；本日最多新增这个小景，未发布安排只预占 |
| 总管理核对固定药箱额外后续 | 父阅读与记忆符合后续槽位，但本例选择小景作为唯一附带，因此不同时安排药箱后续 | 合法不等于当天必发；不清除父主题黑名单、不再次取药箱；未发布后续不制造错过 |
| 若候选提出自由“再找一个同样药箱” | 归一为重复同一承诺，校验拒绝；只在有限修复中替换违规候选或留空，不加发另一件重点 | 不因自由库、新标题或新人物获得豁免 |
| D＋1日晨 | 牵线目标可达，优先提供原任务的继续入口 | 不与同人新小事争抢入口，不消耗新的涟漪发放名额 |
| D＋1日昼 | 一件合法的新自由小景到达窗口，参与者在场 | 创建事件实例、开始提供期、显示涟漪标记；此时还没有全文 |
| 玩家点击小景 | 冻结当下节点，以Low生成／封装，读完后确认并按需结算 | 只把实际已读与确认内容记入历史；完成后写该主题黑名单 |
| 牵线或小景完成后 | 保留读后事实，撤下已完成入口；不因空出位置立即补发新事件 | 不返还当日新发计数，回看不重结算 |
| 下一夜 | 总管理读取更新后的事实、任务、记忆、预占和黑名单，再判断次日是否需要新事 | 不重复上述处理，不靠换名重新塞同题，也不固定每天同时发固定与自由 |

替代分支：若玩家在小景发布前出征，使其人物／窗口或当天负荷不再合适，则先挂起，窗口内复验，无法发布便取消；不另补一个小景，也不把这项未发布安排记成玩家拒绝或他人已处理。已发布旧事件的过期与余波仍按§6.3处理，不因低密度规则改写其真实生命周期。

### 11.1 同一件牵线事件怎样分阶段生成

本例使用现有牵线玩法说明时序，不新增正式人物对白。

| 时点 | 当前步骤与生成范围 | 明确不能做的事 |
| --- | --- | --- |
| 夜间编排 | 安排一件牵线事件：委托人提出 → 玩家选择 → 目标人物反馈 → 返回委托人报告 → 结果确认；只存流程与条件 | 不生成所有台词，不认定玩家已经接受或目标人物已经答复 |
| 玩家点委托人 | 生成当下提议场景，停在可选择位置 | 不把所有选择后的回应和最终道谢一并写成已发生正文 |
| 玩家接受并选定做法 | 提交选择；若需要差异化接受回应，再以该选择生成本段反馈，保存进行中事件 | 不等下一夜才推进，不因读完接取就写完成黑名单 |
| 玩家实际找到目标人物 | 用前序已读内容、实际选择与目标角色知情，生成这一轮目标对话／反馈 | 不凭打开任意人物窗口完成，不提前写委托人已收到答复 |
| 目标对话完成 | 写这一步的阅读／答复证据，事件变为可回报／待交付 | 不把此步反馈误当成整件任务已结束 |
| 玩家回到委托人 | 用真实答复及前序已读原文生成任务结果收尾；读完后明确确认完成 | 不重新问是否接受，不把必要收尾计为“额外后续” |
| 完成后 | 写一次终态与64日主题黑名单；真正额外后续需同时满足父条件与日程空间，另行安排 | 不让中间每一场分别产生同题终态，不重发新事件领取同一结果，不因完成即刻补卡 |

如果玩家中途跨日，下一次总管理只能接续其尚未完成的步骤；不会把这个表从头重新执行。如果玩家最初拒绝，进入拒绝收尾，后面的目标对话与成功回报都不生成。

### 11.2 日度—副本—结算—回馆的完整机制例

以下用药箱工作稿演示关系，不给原工作稿补正式剧情、额外奖品或已批准的好感值。

1. 日度GM保留药箱事件；玩家实际接受，当前状态记录承诺，尚未取回目标。
2. 玩家选定路线与队伍。副本GM读取该承诺、当前人物状态、以往同地经历及路线能力，安排目标节点和少量条件化反馈；同一事件ID贯穿本趟，不新发第二个药箱任务。
3. 玩家实际到达目标并取得有效证据，跳过了一个可选叙事节点。程序与小模型分别记录确定结果和叙事变化；未触发的叙事不进入记忆。当前委托实物由实际战斗或层结算触发，不能把跳过叙事等同于取消物品发放，详见[实物交付规则](../audits/2026-09-25-airp-commission-physical-rewards.md)。
4. 玩家提前撤离但满足带回政策。本趟结算为实际撤离及目标带回，不写成全清；委托进入待交付，尚未结束，也不提前写终态黑名单。
5. 回馆后按委托人实际位置／可交互状态生成反馈，而不是强迫她出现在GM原先预测地点。前文和本趟结算共同进入场景，不能重新接受同一委托。
6. 玩家明确交付，事件正式收尾。授权的好感变化由结算模型据实际经历判定，程序映射并保存；任务物操作、事件记忆与回执一致，已计入的效果不再施加。
7. 下一夜GM读到“已交付、实际人物状态、有效关系变化、仍存在的其他未完事项”，再决定留白或安排新事；不按原副本计划补发被跳过的内容。

失败变体：如果未满足带回条件，保留失败行动与真实损失，任务保持可重试／未完成状态；下一趟使用新run和新副本计划，沿用同一未结束承诺，不能用前一趟或接受前的证据结案。
